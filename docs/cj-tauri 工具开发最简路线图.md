# 一、先明确"最简"的判定标准

这份路线图的目标不是"学会一个框架"，而是在 14 天内发布一个能被别人下载、并且愿意转发的小工具。因此"最简"有明确的边界，越界就不叫最简了：

- 只用官方脚手架与仓库已有示例，不自造构建系统、不自写 WebView 绑定、不发明权限模型。
- 第 2 天窗口必须出来、第 5 天必须能收发数据；如果一条链路卡超过一天，说明选型或边界划错了。
- 产物必须是免安装单文件可执行程序：静态链接、不带运行时的浏览器内核、双击即用。

与之配套的是三条发布线（达不到就不要发，见第八章）：可执行文件 ≤ 8MB、空载内存 ≤ 30MB、冷启动 ≤ 1 秒。

## 1.1 旗舰选题：为什么是串口 / 网络二合一调试助手

选品只按四条标准筛，四条都过得去才值得投入：

- 受众够大，而且聚在同一个圈子里。同一个圈子里的人会互相转发，这比"总量大但分散"更划算。
- 痛点明确，且已经有人替你把痛点写在网上了。现成竞品越老、越臃肿、越难定制越好——你只要"做小、做干净"就能形成对比。
- 后端逻辑正好落在仓颉最擅长的地方：字节序、分帧、CRC 校验、时序调度这类静态类型语言的主场。
- 仓库里存在可抄的参考实现。这一步能直接把"最简"从口号变成事实。

按这四条，旗舰选题定为 **cj-Link：串口 / 网络二合一调试助手（单文件绿色版）**。

- 对标对象：串口调试助手（UartAssist）、SSCOM、NetAssist，以及把串口与网口合二为一的 TCPCOM 这一类工具。
- 差异化只打三刀：不安装（单文件、免驱动、免运行时）、不捆绑（无广告、无会员、不强制联网）、跨平台（Windows 与 Linux 用同一套代码）。
- 参考实现已存在：仓库 `examples/` 下已有串口助手与 Modbus 主站两个可跑示例，第一天就有能对照的代码。
- 传播渠道天然存在：嵌入式、工控、硬件工程师社区对"轻量、免安装、可定制"的调试工具极其敏感。

## 1.2 备选方向与选型对照

**表 1　候选工具方向对照（复杂度越低、越容易先跑通发布链路）**

| 方向 | 目标受众 | 开发复杂度 | 破圈潜力 | 建议 |
| --- | --- | --- | --- | --- |
| 串口 / 网络调试助手 | 嵌入式、工控、硬件 | 中（有示例可抄） | 高（技术社区传播强） | 首选 |
| 本地 Markdown 笔记 | 通用办公、学生 | 低（fs 插件即可） | 中（竞品太强） | 备选 |
| 无广告本地音乐播放器 | 泛大众 | 中偏高（音频解码） | 高（大众向） | 备选 |
| 本地 API 接口调试工具 | 后端、测试 | 中 | 中高 | 备选 |
| 极简剪贴板历史管理器 | 程序员、通用 | 高（系统钩子/托盘） | 高 | 放到二期 |

结论：先用调试助手把"发布链路"完整跑通一次。它最容易做出"确实比现有工具小一个数量级"的直观对比，而这种对比正是传播的燃料。

# 二、技术底座速览：30 分钟建立正确心智模型

## 2.1 一句话定位

cj-tauri 是用华为仓颉语言实现的类 Tauri 2 混合开发框架：仓颉做后端、静态编译成原生可执行程序，界面交给操作系统自带的 WebView 渲染，两者之间是一条 JSON IPC 通道。它与 Electron 的根本差别只有一句：**不把 Chromium 打包进去**。界面代码仍然是普通的 HTML / CSS / JS，Windows 上跑在 WebView2 里，Linux 上跑在 WebKitGTK 里。

## 2.2 四层架构

- **前端层**：HTML / CSS / JS，通过 `window.__CJ_TAURI__` 的 invoke / listen / emit 与后端通信。
- **IPC 消息桥**：`src/ipc_hub.cj`，负责命令注册、分发与校验；整个往返的实测开销在亚毫秒级。
- **能力安全模型**：`src/capability.cj`，读取 `capabilities/` 下的 JSON 白名单，没声明的一律拒绝。
- **WebView 宿主**：`src/host.cj` 加各平台 C 桥（`native/bridge_*.c`）。Windows 走 Win32 + WebView2，Linux 走 GTK + WebKitGTK，鸿蒙仅有预留位。

这条分层的实践含义是：业务流程逻辑写在仓颉侧，界面只负责显示。把边界划在前面，后面每一步都会省力。

## 2.3 与 Tauri 的严格对位关系

**表 2　cj-tauri 与 Tauri 2 的概念对位（写过 Tauri 可零成本迁移）**

| Tauri 2 概念 | cj-tauri 对应物 | 它负责什么 |
| --- | --- | --- |
| tauri::Builder | TauriApp | 装配应用：窗口、命令、插件 |
| #\[tauri::command\] | CommandHandler 接口 | 前端可以调用的后端函数 |
| @tauri-apps/api | window.\__CJ_TAURI_\_ | 前端 invoke / listen / emit |
| capabilities/\*.json | capabilities/\*.json | 命令与事件白名单 |
| tao + wry | src/host.cj + native/bridge\_\*.c | WebView 宿主（平台差异只在这一层） |

没写过 Tauri 也不要紧：把 Tauri 的官方文档当作"可以照抄的说明书"来读，概念一一对应，错误也能对号入座。

## 2.4 平台现状：这些点上不要浪费时间

- **Windows + WebView2**：已实机跑通，是首发主平台。
- **Linux + WebKitGTK**：已实机跑通，跨平台叙事靠它立住。
- **鸿蒙 ArkWeb**：目前只有架构预留位，尚未实现——不要把它写进这一期的功能清单。
- **macOS**：公开资料与仓库示例都未覆盖，不要把它作为首发目标平台。

## 2.5 三条铁律

- **命令驱动**：应用对外的能力边界就是一张"命令表"。前端不直接碰文件、串口、网络，只能 invoke 命令。
- **默认拒绝**：capabilities 清单里没有声明的命令，调用直接被拒，报 `command not allowed`。
- **清单先行**：先定能力清单，再写实现。顺序反过来，就会反复撞权限报错、把时间浪费在定位"到底漏了哪一处"。

# 三、阶段 0：环境就绪（30–60 分钟）

## 3.1 依赖清单

**表 3　环境依赖与平台差异（版本会迭代，动手前先看仓库使用文档与 npm 最新版）**

| 组件 | 版本基线 | Windows | Linux | 作用与注意点 |
| --- | --- | --- | --- | --- |
| 仓颉 SDK | 1.0.5+，实测 1.2.0 | 需要 | 需要 | 官网下载需登录华为账号，没有匿名直链 |
| stdx 扩展库 | 实测 1.2.0.1 | 需要 | 需要 | JSON 走它（标准库暂没有 std.json） |
| C 编译器 | llvm-mingw / mingw gcc（Win） | 需要 | 需要 | 用于编译 C 桥；解压即用，路径不能含空格 |
| WebView2 Runtime | Win11 自带 | 需要 | — | Win10 老版本与精简版可能缺失，需单独补 |
| WebView2 SDK | 不得高于本机 Runtime | 编译 C 桥需要 | — | 版本高于 Runtime 会"编得过、跑不起来" |
| WebKitGTK | libwebkit2gtk-4.1-dev | — | 需要 | 一条包管理器命令即可装好 |
| Node.js | 18 及以上 | 可选 | 可选 | 用 vue/react 模板或 npm 版脚手架时才需要 |

## 3.2 装好仓颉侧：两个环境变量定生死

- 把 SDK 解压到没有空格的路径下；有空格会在链接阶段给你制造很难猜的报错。
- `CANGJIE_HOME` 指向 SDK 根目录即可，PATH 由 cj-tauri 启动器按 SDK 的目录布局自动补齐，不需要手工拼四个目录。
- `CANGJIE_STDX` 必须指到 `dynamic/stdx` 这个动态库目录，不是包根。指错的表现非常有迷惑性：配置检查能过，到生成工程、执行构建时才炸。

`# 最小配置：只设 SDK 根目录，其余交给启动器补齐`\
`CANGJIE_HOME=<仓颉 SDK 根目录>`\
\
`# 关键：指向 dynamic/stdx（动态库目录），不是包根目录`\
`CANGJIE_STDX=<SDK>/.../<平台>/dynamic/stdx`

## 3.3 两道门禁，过不去就不要往下走

`cjc --version        # 第一道门禁：编译器能在当前终端里跑通`\
`cjpm build --help    # 第二道门禁：包管理可用`\
`cj-tauri info        # 总门禁：逐项告诉你哪一环还没就位`

`cj-tauri info` 是排障的第一入口。它的价值在于缺什么就说什么，而不是甩给你一句"命令找不到"。

## 3.4 最容易劝退的症状：退出码 127，且一行输出都没有

- **现象**：执行构建直接返回 127，终端一片空白，很容易误判成"工具链装坏了"。
- **真因**：PATH 不全——缺少 `runtime/lib/<平台>`、`bin`、`tools/bin`、`tools/lib` 中的任意一个就会这样。
- **加重因素**：在 Git Bash 里用盘符形式的 PATH 传给原生进程，同样会出现 127 且无输出。
- **处置**：只设 `CANGJIE_HOME` 让启动器补齐；构建命令优先在 Windows 原生命令行或 Linux 原生 bash 里执行，不要用 Git Bash 跑构建。

# 四、阶段 1：先让窗口出来（约 40 分钟）

## 4.1 create 的三条规矩（先记住，能省一次返工）

- **项目名要能推出合法包名**：字母开头，只含字母、数字、连字符、下划线与点；分隔符后面的首字母会自动转大写（例如 `my-app` 推出 `myApp`）。推不出来会直接报错退出。
- **目标目录必须不存在**。脚手架不覆盖已有目录，想在原地"重跑一遍看输出"是做不到的，只能换个名字。
- **模板四选一**：`app`（默认，内联 HTML 单文件、零 Node 依赖）、`vue`（Vue 3 + Vite）、`react`（React 18 + Vite），也可以直接写仓库里自建模板的目录名。

## 4.2 三条命令起一个工程

`# 安装脚手架（0.8.0 起：Windows cmd、Git Bash、Linux bash 用同一条命令）`\
`npm i -g cj-tauri`\
\
`# 起工程：内联 HTML 模板，零 Node 依赖，最容易先跑通`\
`cj-tauri create cj-link --template app`\
`cd cj-link`\
`cj-tauri dev`

日常用到的子命令只有几个：`create` 起工程、`dev` 开发、`build` 构建、`run` 运行、`info` 体检。记住这五个就够。

## 4.3 生成物与各自作用

**表 4　脚手架生成物与修改时机**

| 生成物 | 作用 | 你什么时候会改它 |
| --- | --- | --- |
| cjpm.toml | 仓颉依赖与构建配置 | 换机器、新增依赖时 |
| capabilities/ | 能力清单：命令与事件白名单 | 每加一条命令都要改 |
| src/（仓颉侧） | 应用装配、命令实现、核心逻辑 | 写后端逻辑的主要战场 |
| 前端入口 | app 模板为内联 HTML，vue/react 模板为 ui/ 工程 | 写界面 |
| 启动与构建脚本 | dev / build / run 的落地入口 | 一般不动 |

一个必须记住的副作用：换机器后 `cjpm.toml` 里的框架依赖路径、以及 stdx 的 `path-option` 都是本机绝对路径。所以要么重新 `create` 一次，要么手动改这两处，否则新机器上一定构建失败。

## 4.4 验收标准

- 窗口能弹出来，且尺寸、标题符合模板预期。
- 内联 HTML 里点一个按钮，能走完一次完整的 IPC 往返并拿到后端返回值。
- 退出时进程干净结束，不留残留子进程（用 vue/react 模板时尤其要确认这一点）。

## 4.5 第一天就把开发契约写下来（强烈建议）

在仓库根目录建立 AI 助手会读取的契约文件（约定名为 `AGENTS.md`），把下面四类内容固定进去：框架约定（命令驱动、默认拒绝、三处联动）、本机环境路径、命令表、已经踩过的坑。

这一步的必要性在于：没有这份文件，每次新开会话，助手都要重新猜你的项目结构，于是猜出不存在的接口、注册了命令却忘了声明权限、构建过了就宣布"完成"而窗口其实没起来。有了它，隐性的开发知识就变成了可复用的硬约束，这是把返工率压下去的最低成本手段。

# 五、阶段 2：先画命令表，再写代码（约 2 小时）

## 5.1 为什么必须清单先行

cj-tauri 的能力模型是默认拒绝：一条命令必须在三个地方同时存在才真的可用（详见第六章）。如果先写实现、最后才补清单，你会依次撞上两种报错——`command not allowed` 和 `command not registered`——而每次都要重新判断"是哪一处漏了"。先把表画出来，这类往返就全部省掉了。

## 5.2 旗舰工具的起步命令表：10 条以内

**表 5　cj-Link 起步命令表（前 10 条即可覆盖核心场景）**

| 命令 | 参数 | 返回 | 归属 |
| --- | --- | --- | --- |
| port:list | 无 | 可用串口列表 | 串口能力 |
| port:open | 端口、波特率、数据位、停止位、校验位、流控 | ok / 错误码 | 串口能力 |
| port:close | 端口 | ok / 错误码 | 串口能力 |
| serial:send | 端口、负载（HEX 或文本） | ok / 错误码 | 串口能力 |
| serial:onData | 无（事件推送） | 收到数据的帧 | 串口能力（事件） |
| tcp:connect | 主机、端口 | ok / 错误码 | 网络能力 |
| tcp:send | 负载 | ok / 错误码 | 网络能力 |
| tcp:close | 无 | ok / 错误码 | 网络能力 |
| log:export | 路径、内容 | ok / 错误码 | 官方 fs 插件 |
| config:save / config:load | 面板配置 | ok / 错误码 | 官方 fs 插件 |

选择原则：一条命令只做一件可以一句话说清的事；参数校验全部留在命令层；重活交给核心模块。命令数控制在 10 条以内，是为了让权限清单一眼能读完——这也是能力模型的价值所在。

## 5.3 三层职责边界：写错这一条，工具就再也测不准

- **表现层（前端）**：收发区、HEX/ASCII 双显、时间戳、日志列表、面板配置。只负责展示与交互，不解析协议字节。
- **桥接层（命令）**：参数校验、超时控制、线程切换、错误码转换。不做协议解析。
- **逻辑层（仓颉核心）**：分帧、字节序、CRC 计算、周期调度。只把干净的字节序列交给上层。

为什么这条边界不能破：调试工具的可信度完全建立在"我看到的时序就是设备真实的时序"之上。协议逻辑一旦漏进前端，前后端就不再共享同一条时间线，测量结果从那一刻起不可信。

# 六、阶段 3：三处联动加命令（约 1 天）

## 6.1 三处联动与漏项的报错特征

**表 6　加一条命令的三处联动（漏哪一处，报错都不同）**

| 步骤 | 做什么 | 漏了它的报错 |
| --- | --- | --- |
| ① 实现 | 写一个 CommandHandler，把命令名与处理函数对应起来 | 无（只是命令不存在） |
| ② 装配 | 在应用装配处注册，或通过插件机制 .plugin() 接入 | command not registered |
| ③ 声明 | 在 capabilities/ 的 JSON 白名单里加入这条命令 | command not allowed |

把这张表贴在显示器边上。出现 `command not allowed` 就直接去看第③处，出现 `command not registered` 就去看第②处，不要从业务代码开始找。

## 6.2 第①处：实现处理函数

处理函数只做三件事：解析参数、调用核心模块、把结果或错误码返回。下面只是说明结构，字段名以仓库 `docs/使用文档.md` 为准：

`CommandHandler {`\
`  name:   "port:open"            // 前端 invoke 时使用的命令名`\
`  handle: (args) => {            // 参数校验 → 调核心模块 → 返回结果或错误码`\
`      // 不要在这里做协议解析、不要在这里做长耗时阻塞`\
`  }`\
`}`

## 6.3 第②处：装配（应用级命令与插件命令）

- **应用级命令**：在 TauriApp 的装配处集中注册，一处能看清应用暴露了哪些能力。
- **插件命令**：实现 Plugin 接口后用 `.plugin()` 接入。官方自带 fs、shell 两个插件——上文命令表里的 `log:export` 与 `config:save/load` 直接复用 fs 插件，不用自己写文件读写。
- 插件只声明"我提供什么"，不会自动放行任何命令。放行仍然由 capabilities 清单决定，这个设计要保留，不要图省事去放宽。

## 6.4 第③处：capabilities 声明

`{`\
`  "commands": [`\
`    "port:list", "port:open", "port:close", "serial:send", "serial:onData",`\
`    "tcp:connect", "tcp:send", "tcp:close", "log:export", "config:save", "config:load"`\
`  ]`\
`}`

JSON 的实际结构以仓库为准。这里的重点是：清单是可读的、可以被逐条核对的——它同时也是你对外介绍安全模型时最有说服力的一张图。

## 6.5 最小验证：跑通一条命令的完整往返

先用最简单的一条（例如 `port:list`）走完全链路：前端 invoke → 宿主投递 → IPC 桥 → 能力校验 → 处理函数 → 结果注入页面 → 前端 Promise resolve。

这一条跑通之后，剩下每一条命令都只是复制粘贴改名字。所以不要把第一天花在同时开五条命令上，先把这一条彻底钉死。

## 6.6 并发与长耗时操作的处理原则

- 不要在命令处理函数里做阻塞式长操作（例如等待设备到位的轮询等待）。命令层应立刻返回，进度用事件推给前端。
- 多路轮询优先复用连接：同一台设备的多组查询用同一条连接串行下发，而不是为每组数据各开一条连接——否则设备侧会被打出一堆连接，这是同类工具最常见的现场问题。
- 周期轮询的时序稳定性是核心指标：这也是选择静态编译语言做后端的理由，解释型脚本在高频轮询下的帧间隔抖动会吃掉时序余量。

# 七、阶段 4：前端界面（2–3 天）

## 7.1 模板决策

- 界面简单、想彻底不要 Node 依赖 → 用 `app` 模板（内联 HTML）。
- 要组件化、要热更新 → 用 `vue` 或 `react` 模板。
- 建议节奏：先用 `app` 模板把"收发链路"跑通（此时任何问题都只可能出在链路本身），确认无误后再迁到 react——表格、面板、日志滚动这类界面，用组件框架写省下的时间会超出迁移成本。

## 7.2 热更新开发流

vue / react 模板下，`cj-tauri dev` 会接管 Vite dev server 并注入开发地址，改前端源码直接在窗口里热更新，不需要重启应用；退出时 dev server 会一并收掉，不留残留进程。这条流一旦跑顺，界面部分的迭代速度就是纯前端的速度。

## 7.3 三个必做的界面件

- **收发区**：HEX 与 ASCII 双模式切换，或同屏双显。二进制协议必须能直接看原始字节——用 ASCII 模式看二进制帧，屏幕上全是乱码，然后人会开始怀疑硬件。
- **帧监视**：每一帧的收发方向、十六进制内容、相对时间戳，支持过滤与导出。这是把工具从"能用"提升到"能定位问题"的分水岭。
- **面板化**：一个面板 = 一组定义（端口、波特率、周期、显示格式），可自由加减并铺满窗口，状态存本地，下次打开接着跑。用"面板"取代传统多窗口设计，是同类老工具最难受的地方，也是你最容易做出口碑的地方。

## 7.4 前端红线（都是实机踩出来的，抄进契约文件）

- 仓颉的三引号字符串会吃掉 JS 的反斜杠转义：不要把需要原样透传的 JS 字符串塞进这种字符串里，改为走 JSON 参数传递。
- ArrayList 的长度是属性，而 JSON 对象的长度是函数：两者写法不同，不要写混，否则在运行期才报错。
- 常量收不了数组字面量：需要数组就用可变量。
- Linux 上原生下拉框的浅色样式会盖掉页面配色：select 一类原生控件必须自定义样式，否则在 Linux 上界面配色会突然崩掉，而 Windows 上一切正常——这种"只在另一个平台出现"的问题最容易拖时间。

# 八、阶段 5：构建与单文件打包（约半天）

## 8.1 build 做了两件事

- **前端**：用单文件打包插件把整个前端收敛成一个 `ui/dist/index.html`。
- **后端**：用 `cjpm build` 把仓颉代码编译成原生产物，再与前端资源合成最终可执行文件。

`cj-tauri build        # 一条命令完成前端单文件化 + 后端原生编译`

## 8.2 Windows 免安装单文件 exe 的关键一步

- **坑点**：Windows 下的 C 编译器默认按 console 子系统出产物，双击会先弹出一个黑色命令行窗口。
- **好消息**：脚手架在生成工程时就已经写好了对应的子系统开关（`--subsystem=windows`），这类坑不用你再踩一遍——这也是坚持用脚手架、不要手搭工程的实际理由。
- **目标产物形态**：静态链接、不带浏览器内核、双击即用、不需要用户安装任何运行时。对照示例的单文件产物实测体积约 5.59MB。

## 8.3 产物验收：四条硬指标

**表 7　发布前必须实测的四条指标（括号内为仓库同类示例的实测基线）**

| 指标 | 目标线 | 参照基线与说明 |
| --- | --- | --- |
| 可执行文件体积 | ≤ 8MB | 同类示例实测 5.59MB；这是宣传语里最有力的一句数字 |
| 空载内存 | ≤ 30MB | 同类示例实测 5.6MB；对比同类 Python 打包方案 60MB 以上、Qt/C++ 约 15MB |
| 冷启动耗时 | ≤ 1 秒 | 双击即出窗口，不做任何预热等待 |
| IPC 往返开销 | 亚毫秒 | 实测约 0.39ms；这是界面不卡顿的底层保证 |

把这四个数字做成一张对比表放进 README 第一屏。体积与内存的对比本身就是最好的传播素材，不需要形容词。

# 十一、固定避坑清单

下面每一条都来自实机验证，建议原样抄进仓库的开发契约文件，让每次新会话都自动读到：

- **退出码 127 且无输出**：PATH 不全，或 Git Bash 把盘符形式的 PATH 传给了原生进程。只设 `CANGJIE_HOME`，改用原生终端。
- **配置检查能过、构建才炸**：`CANGJIE_STDX` 指到了包根，应指向 `dynamic/stdx` 动态库目录。
- **command not allowed**：漏了 capabilities 声明（第③处）。
- **command not registered**：漏了装配（第②处）。
- **双击弹出黑色命令行窗口**：产物出成了 console 子系统，需要 windows 子系统开关（脚手架已默认写好，手搭工程才会遇到）。
- **WebView2 初始化失败**：C 桥用的 SDK 版本高于本机 Runtime，降到不高于 Runtime 的版本。
- **Linux 上页面配色被盖**：原生下拉框等控件用系统浅色样式，需自定义控件样式。
- **前端字符串被吃掉反斜杠**：仓颉三引号字符串会转义，需原样透传的内容改走 JSON 参数。
- **长度取值写法报错**：数组长度是属性、JSON 对象长度是函数，不要写混。
- **换机器后构建失败**：`cjpm.toml` 与 stdx 的路径是本机绝对路径，重新 create 或手改这两处。
- **create 报"目录已存在"**：脚手架不覆盖，换个项目名。
- **项目名推不出包名**：只能字母开头，仅含字母、数字、连字符、下划线、点。

# 十二、失败模式速查表

**表 10　症状 → 根因 → 处置（按症状查，不要按猜测查）**

| 症状 | 根因 | 处置 |
| --- | --- | --- |
| 命令找不到编译器或包管理器 | 环境变量未配置 | 设置 CANGJIE_HOME 指向 SDK 根目录 |
| 构建返回 127 且零输出 | PATH 不全 / Git Bash 路径形式 | 用 npm 版脚手架；改用原生终端 |
| 配置检查通过但构建失败 | stdx 指向了包根 | 改指 dynamic/stdx |
| 前端报 command not allowed | 权限清单未声明 | 补 capabilities 声明 |
| 前端报 command not registered | 命令未装配 | 在装配处注册或经插件接入 |
| 双击弹出黑色控制台窗口 | 产物为 console 子系统 | 启用 windows 子系统开关 |

| Linux 界面配色异常 | 原生控件样式覆盖 | 自定义原生控件样式 |
| 界面收到乱码 | 用 ASCII 模式查看二进制协议 | 切到 HEX 模式或双显 |
| 设备侧连接数暴涨 | 每组数据各开一条连接 | 同设备复用连接、串行下发 |
