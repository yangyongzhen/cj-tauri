## 二、这轮做完了什么（每项都带实测证据）

起点是 `433ef16` 之前的状态：Windows / Linux MVP、仓颉原生 CLI、能力安全模型、窗口图标、CI 门禁都已就绪。

### M1 热重载（提交 `9242c30`）

- API：`TauriApp.runUrl(url)`（**独立方法**，与 `run(html)` 平行，共用同一段装配）、
  `TauriApp.devUrl()`（读环境变量 `CJ_TAURI_DEV_URL`，空则返回 `None`）、`TauriApp.reload()`；
  前端对应 `window.__CJ_TAURI__.reload()`。
- 桥：Windows 加 `cj_bridge_load_url` / `cj_bridge_reload`（`Navigate` / `Reload`），Linux 同签名实现已写。
- 实测证据链：`load url: http://127.0.0.1:…/` → `Navigate -> hr=0x00000000` → 两次 `js -> native` →
  `frontend requested reload` → `Reload -> hr=0x00000000` → 重载后再次 invoke。

### M2 前端模板 + dev server 接管（提交 `433ef16`，版本进 0.4.0）

- 模板 `cli/templates/app-vue/`：Vue 3 + Vite，配 `vite-plugin-singlefile`，产物是**单个**
  `ui/dist/index.html`——框架把页面读成字符串交给 WebView，页面没有基准路径，发布态必须单文件。
- `cj-tauri create <工程名> [--template vue|react]`，缺省仍是 `app`（内联 HTML 的零 Node 样板，老用法不受影响）。
- `cj-tauri dev` 的接管链：`ui/node_modules` 不存在时先 `npm install` → 后台 `npm run dev`
  （日志写 `ui/dev-server.log`）→ 探活等日志里的 `Local:` 行（阈值 180 秒）→ 注入 `CJ_TAURI_DEV_URL`
  启动应用 → 应用退出后收掉**整棵** dev server 进程树。没有 `ui/package.json` 的工程完全不碰 Node。
- 实测：dev 接管全链路 + 收尾日志 `应用退出（exit=1）` → `dev server 已收掉（pid=6792/2356/11972）`，
  收尾后 `node.exe` 无残留。

### M3 React 模板（提交 `1ef953b`）

## 三、HMR 的完整结论（此前唯一的缺口，现已取证）

原先三次「观测不到 HMR」是**判据错了**，不是功能坏了：Vite 的模块图要**客户端请求过页面之后**才建立，
当时没有客户端连上来，日志里只有 `[no modules matched]`。

服务端判据（`DEBUG=vite:hmr` + 有客户端请求过页面）：

```text
vite:hmr [file change] src/App.vue
vite:hmr [self-accepts] src/App.vue
vite:hmr [vue:update(template)] ui/src/App.vue
[vite] (client) hmr update /src/App.vue
```

窗口内判据（不需要截图）：把工程 `ui/src/App.vue` 换成每秒
`invoke('greet', { name: 'TICK--' + <h1 的真实文案> })` 的探针，再覆盖成文案更长的版本：

```text
覆盖前  js -> native (76 bytes)
覆盖后  js -> native (173 bytes) / (174 bytes)   ← 页面跑的是新代码
Navigate = 1（全程没变）  Reload = 0            ← 整页没有重载
```

即「HMR 更新已下发 → 窗口里的页面跑起新代码 → 且没有整页刷新」三点同时成立。
这条判据对两个模板都适用（React 模板换成改 `src/App.jsx`）。

## 四、关键决策与理由（这轮定的，别再翻案）

| 决策 | 理由 |
|---|---|
| `runUrl` 做成**独立方法**，不给 `run` 加可选参数 | 老的 `run(html)` 调用点零改动；两者共用同一段装配 |
| dev 走**环境变量** `CJ_TAURI_DEV_URL` | 应用代码不必知道自己在开发态；CLI 自动接管与手动起 dev server 共用一条路径（Tauri v2 也是这风格） |
| `reload` 用**整页** `Reload()` | 框架层不需要理解前端框架的 HMR 协议，交给 Vite；代价是后端状态不保留，已在文档写明 |
| 模板**进仓**（`cli/templates/app-vue` / `app-react`） | `create` 一条命令拿到能跑的单文件产物；模板随 CLI 同版本走 |
| `create` 缺省仍 `app` | 老用法不受影响，`--template` 是纯增量参数 |
| Node 路径只在有 `ui/package.json` 时触发 | 零 Node 的 `app` 模板与 `examples/hello` 完全不被牵连 |
| 产物用 `vite-plugin-singlefile` 打成单文件 | 与「读文件 → `run(html)`」的模型对齐，发布态不需要 URL 与基准路径 |
| 测试放 `src/tests/` 子包（`package cjTauri.tests`） | 实测 `cjpm` 不扫描顶层 `tests/` 目录，放外面会静默变成 0 个用例 |
| dev server 收尾：Windows `taskkill /F /T`，其他平台 `p.terminate()` | Windows 上 npm→node 是进程树，必须连带杀；非 Windows 分支是直接子进程 terminate（**未实机验证**，见 5.1） |
| 双仓双推：`origin` 挂两条 pushurl | 一次 `git push` 同时同步 AtomGit 与 GitHub |
| `.bat` / `.ps1` 一律纯 ASCII | cmd.exe 的 OEM 码页与 PowerShell 5.1 会吃坏中文注释（已实际踩过） |

## 六、换到 Linux 机器怎么接（本章是重点）

### 6.1 先装依赖

```bash
# 1) 仓颉 SDK / stdx：按官方说明安装（本仓默认假定 /opt/cangjie/cangjie，装到别处就改 cj-env.sh）
# 2) WebView 依赖 —— native/build_linux.sh 会检查，缺了会直接报错退出
sudo apt install gcc pkg-config libwebkit2gtk-4.1-dev libgtk-3-dev     # Debian / Ubuntu
# Fedora: sudo dnf install gcc pkgconf-pkg-config webkit2gtk4.1-devel gtk3-devel
# Arch:   sudo pacman -S gcc pkgconf webkit2gtk-4.1 gtk3
# 3) 前端模板需要 Node 18+（本会话用的是 Node 24 / npm 11）
```

### 6.2 拉代码与自检

```bash
git clone https://atomgit.com/qq8864/cj-tauri.git && cd cj-tauri
source cj-env.sh                       # 设 CANGJIE_HOME 与 LD_LIBRARY_PATH；路径不同就改它
bash scripts/check-static.sh           # 静态门禁，不需要 SDK，先确认仓是干净的
cd native && ./build_linux.sh && cd .. # 产出 native/libcjtbridge.so
cjpm build                             # 框架编译
bash scripts/test.sh                   # 单测，预期 23/23
```

### 6.3 跑起来（与 Windows 三条路一一对应）

```bash
# A) 仓内示例（最快，不用脚手架）
cd examples/hello && cjpm build
LD_LIBRARY_PATH=../../native:<stdx 路径>:$LD_LIBRARY_PATH ./target/release/bin/main
# 注意：应用以「工程目录」为工作目录（ui/ 与 capabilities/ 都是相对路径读的）

# B) 用 CLI（推荐）
./cli/cj-tauri.sh info                              # 先自检：框架/项目/stdx/SDK/cjpm/桥 是否都解析得到
./cli/cj-tauri.sh create myapp --template vue       # 或 react；不给则 app（内联 HTML，零 Node）
cd myapp && ../cli/cj-tauri.sh dev                  # 自动 npm install + 起 Vite + 注入 CJ_TAURI_DEV_URL
```

平台差异（Windows 有、Linux 没有）：没有 `run_win.bat`；启动器是 `cli/cj-tauri.sh` 而不是 `.bat`；
动态库靠 `LD_LIBRARY_PATH` 而不是 `PATH`；dev server 收尾从 `taskkill /T` 换成 `p.terminate()`（见 5.1）。
`cj-tauri.sh` 的 `dev` / `build` / `run` 会自己拼好「桥 + stdx + 仓颉运行时」的动态库路径，一般不必手拼。

### 6.4 到 Linux 后的建议验证顺序（按缺口大小排）

1. 环境没退化：`./build_linux.sh` 能编译 → `examples/hello` 出窗口 → `invoke` / `tick` 往返
   （这几项 2026-08-21 过过，先确认可复现）；
2. M1 热重载：`runUrl` + 前端 `reload`（Windows 上的日志形态是 `Navigate -> hr=…` / `Reload -> hr=…`，
   Linux 看 `bridge_linux.c` 的对应输出行）；
3. 窗口图标：`iconPath` 走 GTK 的 `gtk_window_set_icon_from_file`；注意 GTK 更偏好 PNG，`.ico` 不一定吃；
4. `cj-tauri dev` 的前端接管，重点看**退出后有没有残留**（`pgrep -af vite` / `pgrep -af node`）。
   如果 `terminate()` 杀不干净，改法是把 Linux 分支换成「杀进程组」：`launch` 时 `setsid` / `setpgid`，
   收尾时 `kill(-pgid, SIGTERM)`——改动点就一处：`cli/src/project.cj` 的 `stopDevServer`；
5. HMR 窗口内取证：复用第三节的探针做法（改 `App.vue` → 看 `js -> native` 的字节数变不变）。

### 6.5 Linux 侧会咬人的坑

- 仓颉运行时目录名不同：Linux 是 `runtime/lib/linux_x86_64_cjnative`，Windows 是 `..._windows_x86_64_cjnative`。
- `cj-env.sh` 只设了 `CANGJIE_HOME` 与 `LD_LIBRARY_PATH`，**没有**设 `CANGJIE_STDX`；
  用到 stdx 的示例/模板需要自己 `export CANGJIE_STDX=<stdx 路径>`。
- 应用必须在**工程目录里**运行，否则读不到 `capabilities/` 与 `ui/`。
- WebKit 的宿主调用必须在 C 桥创建的原生 pthread 内执行：仓颉 M:N 轻量线程的堆上协程栈会被 JSC 的
  栈边界校验 abort（`bridge_linux.c` 已按此实现，改动时别破坏这个约束）。
- WebView2 的「SDK 版本不得高于本机 Runtime」规则是 Windows 专属，Linux 不适用。

### 9.3 ⚠️ 本轮最重要的结论：Linux 上「一宿主一 GTK 线程一 `gtk_main`」起不了第二个窗口

- 探针 `examples/multi-window/`（两窗、两页**同一份 HTML**、角色由自己的 label 推出，`MW_MODE=single`
  是单窗对照）双窗 **3/3 次 `exit=134`**；最小对照 `native/tests/gtk_threading_probe.c` 修好判定逻辑后
  **8/8 致命失败**（多数 `exit=139` SIGSEGV + `Gtk-CRITICAL`，一次 `exit=134` abort，一次两条线程都
  卡在 `gtk_init` 里）。
- 反证很硬：**纯 GTK** 下 N=2 条 `gtk_main`（串行起）**干净退出** → 不是 GTK 的锅；最小对照里
  **没有我方代码照样崩** → 不是仓颉/桥的锅。根因是 **WebKitGTK 不能被两条线程各自使用**
  （串行起也逃不掉，属不被支持的用法，不是可以靠时序回避的竞态）。
- 推论：Linux 上要做多窗口 UI，得先把宿主改成「**单主循环 + 多窗口**」（一条 GTK 线程跑唯一的
  `gtk_main`，N 个窗口都在它里面），并且必须和 §7.5 的残余项「**回调带宿主 id**」一起做。
  完整判定与证据链见 `docs/架构演进-多平台与多窗口.md` §8。
- **Windows 不受这条约束**（Win32 允许每窗一条 UI 线程 + 自己的消息循环，WebView2 的 controller
  只被创建它的线程访问）→ 这正是本次去 Windows 要验的第一件事，见第十章。

### 11.6 同日补测：两窗回调并发（探针断言 8 → 18 条）

批次 2 只验到「各宿主各自 boot + 广播/定向投递」，没碰两个窗口**同时**落回调时的共享状态。探针补了
两个阶段，`run.bat` 默认模式 **18/18 断言全过、`exit=0`**；单窗对照 **6/6、`CONTROL PASS`**：

| 断言（桥 stderr 逐字） | 它证明什么 |
|---|---|
| `window=second ASK which=second kind=info inflight=1`、`window=main ASK which=main kind=info inflight=2` | 两窗各自向**自己的宿主**要原生消息框；第二条进栈读到 `inflight=2`，说明第一条**还没出栈**（框要等人关才返回）——两个框真的同时在开。谁先进由调度决定，**不钉顺序**（首轮教训：钉顺序的断言会假红） |
| `both boxes open`（`ASK-DONE which=main ok=true` / `which=second ok=true`） | 两框都返回；自动确认脚本日志 `FIRST batch: 2 dialog(s) open` 独立佐证「同一时刻两个 `#32770` 都开着」 |
| `closed only second` → `main still up` → `close phase done` | 只关 `second`：应用**没有**因为少一个窗口就返回——`after run` 仍在其后打出、两宿主各一次 `host destroyed`、`exit=0` |

原生框得有人点：新增 `examples/multi-window/dismiss-dialogs.ps1`（`run.bat` 双窗模式自动起、单窗模式不起），
按「窗口类 `#32770` **且**属于目标进程」双重筛选后 Post `WM_COMMAND/IDOK`，并在**看到第一个框后等 4s**
再作答——那 4s 正是两框重叠的窗口，也是 `inflight=2` 能被观测到的原因。日志按状态变更记
`POLL pids=… dialogs=…`，答不上时能区分「没进程 / 有进程没框 / 出错」。
**PowerShell 绑定坑**：把 `[uint[]]` 转给 `Find(uint[])` 会直接抛异常（脚本静默什么都不点），形参写
`int[]` 更稳——本机踩过，脚本里已注。

**结论与残余**：对话框状态在 C 核里本就是 **per-host**（`h->dlg_busy` / `dlg_lock` / `dlg_cur`，跨宿主
不互斥）、退出是**逐窗判**的（`app.cj` 的 `allWindowsExited`）——这两条由「潜在」变实测事实。**仍未清**
的两处是代码层（不是「没测」）：① `HostGlobals.onDestroy` 静态单槽、且**不在 `WebViewHost` 接口上**
（应用侧装不进去，现在恒 no-op）；② 文件框结果走共享单槽 `HostGlobals.dialogResult`（两窗同时开文件框时，
先返回者读到的可能是后返回者写的值——本用例用 message 框绕开了它，因为 message 框的结果就是返回值、
不经槽位）。两处都要与「回调带宿主 id」一起做。

### 13.3 关键决策（别翻案）

1. **前端是独立 `ui/index.html`，不内联进仓颉 `"""`**：三引号字符串会处理反斜杠转义、`${}` 又与插值同形，
   整页 UI 塞进去必踩 `AGENTS.md` §4 记的那两个坑；独立文件还能过 `node --check`。
2. **封面一律走宿主命令 `movie:image`**：图源按 `Referer` 放行，**失败形状是「HTTP 200 + 0 字节」**，
   页面侧 `<img src>` 直连必全灭且无解（`Referrer-Policy` 只能减少 Referer、不能替换；内联页来源还是
   opaque）→ 由仓颉侧带 Referer 取回、转 `data:` URL。取不到时用**生成式占位**（标题首字 + 按标题散列
   的色相渐变）而不是破图。
3. **`movie:image` 必须做地址白名单**：参数是页面可控字符串，不放行就等于把后端变成「替页面请求任意地址」
   的 SSRF 跳板。
4. **页面自检经 `report` 命令落 stderr**：实机验证不必开 devtools；未授权对照组（`movie:nope`）是固定项。

## 二十二、2026-10-06 第八轮：官方 `serial` 插件（Linux 实机）

诉求是「框架要能开串口」。转手第一件事是**先侦察、别先写**：仓颉 `std` / `stdx` **都没有串口库**，
`std.posix` 也没有 ioctl / fcntl / termios（符号是从本机 `std.posix.cjo` 里读出来的），所以波特率那一套
只能交给 C——三条路里选了 **CFFI**（另一条 `std.fs.File` 开设备节点只能读写字节、参数得靠外部 `stty`）。

### 22.1 形状：能力落 C 桥，白名单留 core

- **C 桥五个同名导出** `cj_bridge_serial_{open,read,write,close,last_error}`（桥产物 22 → **27** 个
  `cj_bridge_*`）。core 侧放**路径白名单 + 参数校验**，平台侧只放句柄表与 termios——平台实现只是
  `cj_plat_serial_*`，与菜单那轮同一套分层，所以 Windows 能先给**同名桩**（导出名一致，上层没有分叉点）。
- **白名单是唯一闸门**：页面递进来的是页面可控字符串，只放行设备节点类前缀（`/dev/tty*` · `/dev/pts/*` ·
  `/dev/serial/by-{id,path}/` · `COM<N>`），**含 `..` 一律拒**——否则 `/dev/ttyUSB0/../../etc/shadow`
  前缀命中就能穿越；`COMfoo` 靠「前缀后必须全数字、最多 3 位」挡掉。
- **错误串放线程局部**：命令各自跑在 worker 线程上，C 侧静态单槽会被并发调用互相覆盖（§4 那条坑的同类）。
- **零第三方依赖**：没链 `libserialport`，Linux 用 POSIX termios 自己开——MIT 口径不变，
  不必往 `AGENTS.md` 里登记第三方许可证。
- 前端走 `window.__CJ_TAURI__.serial.*`（shim 由宿主**预执行脚本**通道注入，页面第一行可读）；
  命名集 `serial:readonly`（open/read/close）与 `serial:default`（另含 write），**集声明 ≠ 放行**照旧。
  示例清单故意**两种写法混用**（命名集 + 明文 `serial:write`），顺手把这条再证一遍。

### 33.2 一条容易读错的语义：文件框结果不是返回值

`showFileDialog*` 的返回值只是「读本宿主的结果位读到了什么」。真正的落地路径是**桥按宿主句柄**经
`onDialog` 回调写进**本宿主自己的** `dialogResult`——`host_webview2.cj` 的 `prepareHost()` 里
`registerHostRoute(this.handle, … , { path => this.dialogResult = path })`，另一头是
`cj_bridge_set_dialog_callback(this.handle, dialogOnResult)`。所以多窗同开文件框的判据必须是
「每窗拿回自己预置的名字」：若路由退化成共享单槽，先返回者会读到后返回者写的值。
**消息框不受此影响**（结果是 `showMessageDialog` 的返回值、不经槽位）——两者别混为一谈。

另有一条实机教训：预置名要配**保存**语义（`OFN_OVERWRITEPROMPT`）。打开语义带 `OFN_FILEMUSTEXIST`，
预置的 `probe-*.txt` 本不存在，自动确认会被弹回、框**卡住不退**。

| 现象 | 指向 |
|---|---|
| `EACCES` / 打不开 | 权限或签名：`ACCESS_DDK_USB*` 没启用，或普通调试证书装包被挡 |

### 41.8 权限取证：裸 open 路线对三方应用不成立（2026-10-24）

这一节是 §41.7 结论的**反面补充**，决定后续路线，别只看「FFI 通路成立」就以为能用了。

四条实测（同一台真机 `3QC0124B20000048`）：

1. `/dev/ttyS0` 是 `0666 root:root` —— `open` 能过，`tcgetattr` 才报 `I/O error`。
   **说明卡点不在文件权限位**（否则 0666 早该成功），是「这个节点不是可用串口」。
2. `/dev/bus` 与 `/sys/bus/usb/devices` **连 `hdc shell`（uid 2000 / `u:r:sh:s0`）都进不去**：
   `ls` 与 `stat -L /dev/bus/ttyUSB0` 一律 `Permission denied`。真实 USB 串口节点的 `open`
   因此回 `EACCES` —— 这是**目录层**（SELinux/DAC）整体不可达，不是某个文件少了 chmod。
3. `ohos.permission.ACCESS_DDK_USB_SERIAL`：`grantMode` = **`SYSTEM_GRANT`**、
   `availableLevel` = **`SYSTEM_BASIC`**（`hdc shell "atm dump -d -p <权限>"` 实测）。
   `SYSTEM_GRANT` 意味着**只能由系统授予 / 或签名 profile 带 ACL**，普通调试证书走不到。
   这就是「装包 9568289」与「运行期 EACCES」的同一个根。
4. 正路在 SDK 里：`@ohos.usbManager.serial.d.ts`（namespace `serialManager`）**没有 `@permission` 注解**，
   提供 `getPortList()` → `hasSerialRight()` / `requestSerialRight(portId)`（弹用户授权）→
   `open(portId)` → `setAttribute()` / `read()` / `write()` / `close()`。
   **框架代管设备节点，全程不碰 `/dev/bus`** —— 三方应用碰 USB 串口就该走这条。
   但仓颉 SDK（`~/.cangjie-sdk/6.1/cangjie/api`）**没有 usb 绑定**，要用得走 Cangjie↔ArkTS 互操作
   （`cangjie-arkts-interop` skill 覆盖这条路）。

**所以**：`src/plugins/serial/serial_ohos.cj` 现有的「NDK FFI 直连 musl libc + 裸 `open`」路线，
只在「已被授权 / 系统签名」的环境里成立；**对普通三方应用不成立**。要真机可用有两条路，都得先做选择：

- **A. 改走 `serialManager`**（推荐）：应用侧 ArkTS 调 USB 串口 API，经 Cangjie↔ArkTS 互操作把
  `list/open/read/write/close` 暴露给 `serial:open` 等命令。代价：多一层互操作，且 ohos 侧命令实现
  要重写成「跨语言调用」形态；好处：不需要系统签名，用户点一下授权就能用。
- **B. 补 ACL 签名**：给 profile 加 `ACCESS_DDK_USB_SERIAL` 的 ACL、用系统级证书签。
  代价：要华为的系统级签名材料，普通开发者拿不到；好处：现有裸 `open` 代码一行不用改。

一条判据留在这里，免得下次又走弯路：**「open 返回 EACCES」不等于「设备没权限位」**，
先 `stat -L` 看权限位、再 `ls` 看目录可不可进，两者能立刻分开「节点问题」与「域问题」。

### 41.9 路线 A 落地：串口改走 `serialManager`（2026-10-24）

用户裁定走 A（不碰系统签名）。本轮把它写完并做到**编译取证**，代码在
`src/plugins/serial/serial_manager_ohos.cj`（全新，`@When[env == "ohos"]` 全覆盖）。

**接入方式（页面无感，命令面一行没改）**：

| 入口 | 现在的行为 |
| --- | --- |
| `serial:open` | 先按原样 POSIX `open`；打不开（`EACCES`/`ENOENT`）就转 `serialManager`，两条都失败时把两侧原因一起写进错误槽 |
| `serial:read` / `:write` / `:close` | 按**句柄空间**分流：`h >= 1_000_000_000` 走 USB（句柄 = 基数 + `portId`），否则走原 POSIX 的 `fd + 1` |
| `serial:list` | `/dev` 扫描结果 + `serialManager.getPortList()` 合并去重（USB 端口只有它看得见） |

**三条实现约束**（都是互操作库的形状，别再试别的写法）：

1. **`JSRuntime` 线程绑定** —— 互操作库要求「runtime 只由创建它的线程使用」。串口命令跑在 IPC 的
   worker 线程上、不同命令还可能落在不同线程，所以这里**起一个专用 owner 线程**持有 runtime，
   其余线程建 `UsbSerialJob` 投队列、轮询等结果（`UsbSerialDispatcher.submit`）。
   **不要**改成「谁调谁建」的懒建共享单例——那正是跨线程用 runtime。
2. **`JSBoolean` 取不出值** —— 库里只有 `toJSValue()`，没有 `toBoolean()`。所以「有没有授权」
   **不查 `hasSerialRight`**，而是「直接 `open`，抛错就 `requestSerialRight`、再按 15s 窗口重试
   `open`」，判定依据是可捕获的异常。
3. **`JSFunction` 只能 `call`、不能 `new`** —— 构造不出 `Uint8Array`，而 `readSync`/`writeSync` 要的
   正是它。解法：`@ohos.buffer` 的 `buffer.from(arrayBuffer)` 拿到**共享同一块内存**的 Buffer 视图
   （Buffer 是 Uint8Array 子类），JS 侧写完再 `JSArrayBuffer.readBytes()` 把字节取回仓颉侧。

**取证状态（重要，别把编译当成能用）**：

- ✅ 桌面 `cjpm build` 零警告（新文件整体门禁在 `ohos`，桌面侧不参与）。
- ✅ 鸿蒙 `hvigor` 的 `CompileCangjie` 通过，hap 重打 2 097 601 字节。
  **顺带回答了一个悬着的问题**：`ohos.ark_interop` 在**纯仓颉 entry**（非混合工程）里可用——
  最小探针 `JSRuntime()` + `ctx.requireArkModule("@ohos.usbManager.serial")` + `getPortList()`
  能编过、能链接，**不需要把骨架改成 ArkTS entry + Cangjie**。
- ❌ **运行期三项全未验**（本轮设备在途中断开，`hdc list targets` 一直 `[Empty]`，连
  `hdc kill`+`start` 也没回来）：
  ① 仓颉自建的 runtime 里 `requireArkModule` 真能加载系统 NAPI 模块吗；
  ② 本进程**没有事件循环**替 Promise 推进，`requestSerialRight` 那一跳到底会不会解析
     （不解析时 `open` 会一直拒绝，用户点了授权也白点——这条最可能真机上要先修）；
  ③ owner 线程绑定在设备上的实际表现（`postJSTask` 有没有被隐式需要）。
- ❌ 真实 USB 串口的收发回环未取证（需硬件在位 + 授权通过）。

**下一步（设备接回来后的顺序）**：装新 hap → `probeLog` 看 `serial:list` 有没有 USB 端口
→ 点一次 `serial:open`，看系统授权框是否弹出、授权后 `open` 是否转成功 → 再试 `read`/`write` 回环。
若 ② 卡住，落法是改成**混合工程**（ArkTS entry 持有 runtime 与事件循环，仓颉侧经 `JSRuntime`
回调），或把授权那一跳挪进应用自身的 ArkTS 页面侧完成——但先测再改，别提前重写。

### 41.10 路线 A 被真机否掉：纯仓颉进程建不了 `JSRuntime`（2026-10-24 晚，设备已回连）

设备回连（`3QC0124B20000048`、API 26、已解锁）后装 §41.9 那版 hap，**启动即 `signal:6`（SIGABRT）**：
hilog 停在 `startApp begin (business = serialAssistant.build())` 之后，连骨架的 `initScripts` 都没打。
没有先改代码，而是做了三组对照——每次都重打 hap、装机、启动，只换串口后端：

| 产物 | 内容 | 字节 | 真机结果 |
| --- | --- | --- | --- |
| 有互操作、真去用 | `spawn` 出 owner 线程建 `JSRuntime()` | 2 097 601 | 启动即 SIGABRT，日志停在 `startApp begin` |
| 只有互操作、从不执行 | 同名符号全留，owner 线程刻意不起 | 2 095 085 | **正常启动**：`pidof` 有、`page end label=main`、自检跑完 |
| 互操作整段摘掉 | 纯 POSIX 空桩 | 2 013 936 | 同样正常启动 |

第二组是判据所在：`llvm-objdump -p <模块.so>` 里 **`libohos.ark_interop.so` /
`libohos.ark_interop_helper.so` 两条 `NEEDED` 都在**、还有 4 个 `JSRuntime` 未定义符号，
而应用照跑——**链接无害，执行 `JSRuntime()` 才 abort**。

再补一个探针把创建点挪到 UI 线程（`onWindowStageCreate`，与 ArkTS 同一条线程）：
hilog 只出现 `runtime probe begin [ui-thread]`，结论行永不出现、进程当场消失。
于是「Cangjie 轻量线程没有 VM」也被排除：**整个纯仓颉进程没有 ArkTS VM**。

**结论（推翻 §41.9 的前提）**：`JSRuntime` 能不能建，取决于**进程里有没有 ArkTS 运行**，
与代码放在框架包还是应用业务包**无关**（放业务包一样 abort）。所以 §41.9 里
「最小探针能编过 ⇒ 不需要混合工程」这个推断**只证明了编译期**，运行期不成立。
`@ohos.usbManager.serial` 只能由真正的 ArkTS 侧发起（混合工程 / 应用自宿主 ArkTS 模块），
框架只留接口——这正是 D-022 第 4 条预留的下沉方案。

**当前落地**：`src/plugins/serial/serial_manager_ohos.cj` 改为**如实降级**（六个同名导出一律报
不可用、原因进错误槽，**不再 import `ark_interop`**）。真机复验：应用正常启动（`pidof` 有、
`page end label=main`），自检 6 条候选路径 errno 照旧如实分流
（`/dev/bus/ttyUSB*` = `Permission denied`、`/dev/ttyUSB*` = `No such file`、
`/dev/ttyS0` = `tcgetattr I/O error`）。POSIX `/dev/ttyS*` 通路不受影响。

**排查路上两个别再踩的坑**：① 本机 SDK 的 `third_party/llvm/bin/` **没有 `llvm-nm.exe`**
（只有 `llvm-objdump.exe`），拿 `llvm-nm … | grep -c cj_bridge` 判符号干净会得到「0 = 干净」的假绿，
因为命令根本没跑起来；先 `llvm-objdump -h <so>` 校准工具可用，再用 `-p`/`-T` 出结论。
② 这台机器上 `aa start` 之后若立刻 `pidof` 读不到进程，别急着判定「没起来」——
崩溃发生在 UI 线程初始化期时，日志停留点（`startApp begin` 有、`initScripts` 无）比 pid 更有判别力。

## 四十四、2026-10-25：补回漏掉的通知能力位，并给「两侧表对齐」装上机制（`HEAD = d833e55`）

**这轮解决的问题**：`system:host` 的返回里根本没有 `notification` 键。

### 缺陷形状（比「少一个字段」更难看）

`native/core/bridge_core.h` 早有 `CJ_CAP_NOTIFICATION = 8`，而且**不是摆设**：

   排列（`menu/tray/dragDrop/notification/hotkey/subtitle`）——顺序跟 header 一致，以后漏位至少
   在阅读时更容易撞见。注意 `init` 多了一个必填位置参数，外部若有应用直接 `new` 会编译失败

   也不要静默错位。
2. **`src/tests/system_host_test.cj`**：两处既有用例补 `notification == false`；新增
   `testSystemHostMapsNotificationBitIndependently`——只置第 8 位，断言 `notification=true` 且

3. **`scripts/check-static.sh` 第 8b 项（新）**：按名字比对 `bridge_core.h` 的 `#define CJ_CAP_*`
   与 `src/host.cj` 的 `public const CJ_CAP_*`，**多一位 / 少一位 / 同一位数值不同**都红。
   真正的教训不是这一位，而是「契约只写在注释里＝没有机制拦着」，所以补的是机制。

## 四十五、2026-10-25：`http` 插件打通鸿蒙系统网络栈（`HEAD = 2a16fef`，分支 `feat/ohos-http`）

**这轮解决的问题**：`http` 插件在鸿蒙上只有一半能用——`http://` 照旧，`https://` 全灭。

### 缺陷形状（与 Windows 漏 libssl 同形，容易读错方向）

仓颉运行时在鸿蒙上装不了 OpenSSL 3：`stdx.net.http` + `TlsClientConfig()` 从第一步就失败，
真机 hilog 是 `MUSL-LDSO: load libcrypto_openssl.z.so failed … namespace=moduleNs_default, errno=2`
（`libssl_openssl.z.so` 同样）。表象极具误导性：后台 http 接口一直正常，**只有 https 资源没了**，
页面回退成色块 / 空图，很容易被读成网络或权限问题。

`examples/ohos/ohos-movie` 早前已经绕过一次——但那只救了**示例**（在它自己的命令实现里改走
系统网络栈），**框架的 `http` 插件本身仍是死的**，任何应用想在鸿蒙上取 https 都会失败。

### 落法：传输层抽成契约，平台差异只落在实现文件

按 AGENTS §2「平台差异只允许出现在 `@When` 条件编译」这条办理，把「怎么发」从「发什么」里剥出来：

| 文件 | 行数 | 职责 |
|---|---|---|
| `src/plugins/http/http_backend.cj` | 131 | 契约：`HttpReply{status,contentType,body,truncated}`、`httpReplyJson`、`parsePageHeaders`、`headerValueOf`（大小写不敏感取头） |
| `src/plugins/http/http_desktop.cj` | 195 | `@When[env != "ohos"]`：stdx.net.http + 显式 TLS/SNI（`tlsConfigForHost` / `isIpLiteralHost`） |
| `src/plugins/http/http_ohos.cj` | 204 | `@When[env == "ohos"]`：`ohos.net.http` 系统栈，TLS / 证书链 / 代理交给 OS |
| `src/plugins/http/plugin_http.cj` | 310 | 命令面 + 主机白名单判定（瘦身前约 513 行，移出约 203 行传输实现） |

两条不变量：

1. **命令名、入参、返回值、主机白名单判定两平台完全一致**——判定只在 `plugin_http.cj` 与
   `parsePageHeaders` 各一份，平台实现里**不重判**，前端一行都不用改。
2. **鸿蒙 `http:postStream` 当场拒绝并说明原因**（系统栈一次回整包、没有增量块，仓颉绑定上的
   `requestInStream` 未验证），不返回假句柄——「发后即忘返回成功」那种骗法不能再犯。

调用形状照抄已真机验证过的 `ohos_movie_image.cj`：`client.request(url, options) { err, resp => … }`
（位置参数 + 尾随闭包）、`HttpDataType.ArrayBuffer`、`resp.responseCode` / `resp.result` / `resp.header`、
收尾 `client.destroy()`。**阻塞等回调是允许的**：命令 handler 跑在 worker 线程（不是 UI 线程），
