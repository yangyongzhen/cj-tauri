# cj-tauri 前端入门教程

面向第一次接触 cj-tauri 的人。跟着做完，你会得到一个能跑起来的桌面应用，并且知道三件事：
**前端代码写在哪里、怎么和仓颉后端通信、出问题时先看哪里**。

读之前请确认环境已就绪（仓颉 SDK、stdx、Windows 上的 WebView2）。没装好先看
[使用文档 §2 环境准备](使用文档.md)，或者直接跑 `cli/cj-tauri.bat info`——它会把「框架 / 项目 / stdx / SDK /
cjpm / C 桥」逐个解析出来，缺什么一眼可见。

前端 API 的完整参考在[使用文档 §6 开发应用](使用文档.md)；本教程只讲怎么把它用起来，
所以更啰嗦一些，每一步都给可运行的完整代码。

## 1. 五分钟跑通：从空目录到一个窗口

假设 cj-tauri 框架克隆在 `E:\code\cj-tauri`，你要在 `E:\code\myapp` 建一个应用。

```bat
cd /d E:\code
E:\code\cj-tauri\cli\cj-tauri.bat create myapp
cd myapp
E:\code\cj-tauri\cli\cj-tauri.bat info       :: 自检：路径、SDK、桥是否都找得到
E:\code\cj-tauri\cli\cj-tauri.bat dev        :: 构建 C 桥 → cjpm build → 启动窗口
```

窗口弹出来时，你已经有了一个完整应用：一个输入框、一个 `greet` 按钮、一个「启动后端事件推送」按钮。
点 `greet`，页面上会出现 `invoke OK: Hello, world! 来自仓颉后端`——这行字符串是**仓颉侧**拼出来的。

> `dev` / `run` 会自动为应用准备好「C 桥（Windows 上含 `native\webview2\`）+ stdx + 仓颉运行时」的动态库
> 搜索路径，这是用 CLI 相比手工构建最省事的地方；手工构建时的 `PATH` / `LD_LIBRARY_PATH` 怎么拼，
> 见 [使用文档 §5 手工构建](使用文档.md)。

**改前端 → 看效果**：编辑 `ui\index.html` 存盘，关掉窗口，重新跑一次 `dev`。
cj-tauri 没有热重载（对标 Tauri 的 dev server 还没做），所以调试期的循环就是「改文件 → 关窗口 → `dev`」。

## 2. 一个应用只有三个文件需要你关心

`create` 生成的工程长这样：

```text
myapp/
├── cjpm.toml                   # 构建配置：依赖 cj-tauri 框架 + 平台链接段，一般不用动
├── src/main.cj                 # 仓颉后端：注册命令、装配应用、启动
├── ui/index.html               # 前端页面（HTML/CSS/JS 随便写）
└── capabilities/default.json   # 能力白名单：允许前端调用哪些命令、接收哪些事件
```

前端同学的日常工作，基本就是改 `ui/index.html`；需要后端提供数据或能力时，再去 `src/main.cj` 加一个命令，
并在 `capabilities/default.json` 里放行它。

**页面是谁加载的？** 不是 WebView 自己去找文件，而是**后端读文件后交给宿主**：

```cangjie
// src/main.cj 的最后两行
let html = String.fromUtf8(File.readFrom("ui/index.html"))
app.run(html)
```

这里有个必须记住的约定：**应用以「项目根目录」为工作目录**，`ui/` 和 `capabilities/` 都是按相对路径读的。
换到别的目录启动，就会找不到页面或能力清单。所以：

- 用 `cli\cj-tauri.bat run` 或 `run_win.bat` 启动，它们会自己切到项目根；
- 手工跑 `target\release\bin\main.exe` 时，必须先 `cd` 到项目根。

顺带一提，`app.run(html)` 收的是**字符串**，不是文件路径。所以「前端」不一定非得是 `ui/index.html`：
你也可以把 Vite / React 的构建产物拷进 `ui/`（入口仍是后端读的那个文件），甚至把 HTML 内联在
`main.cj` 里——仓库里的 `examples/hello` 就是内联写法，方便一处看全前后端。

（本节涉及的文件内容在下一节给全。完整目录清单与每个文件的职责见[使用文档 §5](使用文档.md)。）

## 3. 认识桥：window.__CJ_TAURI__

宿主会在页面脚本执行**之前**注入一小段 JS，把 `window.__CJ_TAURI__` 挂到页面上，功能对标
`@tauri-apps/api`。你不需要 `import` 任何东西，也不需要在 `index.html` 里引任何文件，直接用就行。

| API | 方向 | 说明 |
|---|---|---|
| `invoke(cmd, args)` | JS → 仓颉 | 返回 Promise，resolve 的值就是后端 `return` 的那个 JSON |
| `listen(event, cb)` | 仓颉 → JS | 订阅后端事件，**返回一个取消订阅的函数** |
| `emit(event, payload)` | — | **当前版本是占位实现，不会生效**，原因见 §8.3 |

### 3.1 拿不准桥在不在：先探测再调用

桥是页面脚本执行前注入的，正常情况下你第一行就能用。稳妥写法（模板里就是这么写的）是探测一下，
避免注入时机或平台差异带来的偶发 `undefined`：

```js
function withBridge(cb) {
  if (window.__CJ_TAURI__) { cb(window.__CJ_TAURI__); return; }
  setTimeout(function () { withBridge(cb); }, 50);
}

withBridge(function (tauri) {
  // 从这里开始用 tauri.invoke / tauri.listen
});
```

### 3.2 invoke：一次调用在协议上长什么样

返回值是 Promise，`.then` / `.catch` 或 `async/await` 都可以：

```js
tauri.invoke('greet', { name: '仓颉' })
  .then(function (data) { console.log(data); })      // Hello, 仓颉! 来自仓颉后端
  .catch(function (err) { console.error(err.message); });
```

`args` 必须是**对象**（省略则视为 `{}`）。要传数组就包一层：`invoke('batch', { items: [1, 2, 3] })`。

底下走的是 JSON over postMessage，排错时看懂它很有用。一次成功调用在协议上只有两条消息：

| 方向 | 消息 |
|---|---|
| JS → 仓颉 | `{"type":"invoke","id":1,"cmd":"greet","args":{"name":"仓颉"}}` |
| 仓颉 → JS | `{"type":"resolve","id":1,"ok":true,"data":"Hello, 仓颉! 来自仓颉后端"}` |

失败时第二条变成 `{"type":"resolve","id":1,"ok":false,"error":"..."}`；后端推事件则是
`{"type":"event","event":"tick","payload":{"n":1}}`。`id` 由桥自增维护、用来把响应配回对应的 Promise，
所以并发调用不会串，你不需要自己管序号，也不需要维护回调表。

### 3.3 失败时你会拿到什么

`invoke` 被拒绝时 `catch` 拿到的是一个 `Error`，`err.message` 就是后端给的原因。新人最常遇到的几种：

| err.message | 含义 | 怎么修 |
|---|---|---|
| `command not allowed: xxx` | 命令没在能力清单里放行 | 把 `xxx` 加进 `capabilities/default.json` 的 `commands` |
| `command not registered: xxx` | 放行了，但仓颉侧没注册 | 在 `main.cj` 里 `.register("xxx", XxxCommand())` |
| `command failed: ...` | 命令内部抛了别的异常 | 看后半段异常信息，桥的 stderr 里也有 |
| `invoke failed` | 后端没给具体原因 | 翻桥的 stderr 日志（见 §7） |
| 你自己抛的 `CommandException("...")` 文本 | 业务失败 | 按消息内容改参数/流程 |

前两条要记住它们的区别，因为报错文本很像、修的地方却完全不同：
**`not allowed` 去改 json，`not registered` 去改 `main.cj`**。

还有一个反直觉的点：**内置命令也要声明**。`system:version`、`system:ping`、`system:echo`、`system:devtools`
是框架自带的（`run()` 时自动注册），但同样必须在能力清单里放行，否则一样报 `command not allowed`。

## 4. 加一个自己的命令：三处联动，缺一不可

这是 cj-tauri 最容易忘的规矩，先记牢「加命令要动三个地方」：

1. 写一个 `CommandHandler` 实现（`src/main.cj`）；
2. `.register("命令名", 处理器)`（`src/main.cj`）；
3. 命令名写进 `capabilities/default.json` 的 `commands`。

漏了第 3 步 → `command not allowed`；漏了第 2 步 → `command not registered`。

下面做一个最小的真实需求：前端传两个数，后端算和并返回。

**第一步，实现处理器**（写在 `src/main.cj` 里）：

```cangjie
/**
 * add 命令：把前端传来的两个数相加
 * 前端：tauri.invoke("add", { a: 2, b: 3 }) -> 5
 */
public class AddCommand <: CommandHandler {
    public init() {}

    public func handle(cmd: String, args: JsonObject, ipc: IpcContext): JsonValue {
        var a: Int64 = 0
        var b: Int64 = 0
        if (let Some(x) <- args.get("a")) {
            match (x.kind()) {
                case JsonKind.JsInt => a = x.asInt().getValue()
                case _ => ()
            }
        }
        if (let Some(y) <- args.get("b")) {
            match (y.kind()) {
                case JsonKind.JsInt => b = y.asInt().getValue()
                case _ => ()
            }
        }
        return JsonInt(a + b)
    }
}
```

这里有两处值得留意，它们决定了「参数拿不到」时不会崩、只是悄悄地用默认值：

- 先 `args.get("a")` 拿到 `Option`，用 `if (let Some(x) <- ...)` 解包，**不要**假设参数一定存在；
- 再 `match (x.kind())` 确认类型是数字才 `asInt()`。前端的 `2` 是 JS number，到仓颉侧是 `JsonInt`；
  如果你传的是字符串 `"2"`，就会走到 `case _` 分支，`a` 保持 0——这种「传了但没用上」最容易误判，
  所以后端入口的参数校验尽量显式写出来。

**第二步，注册它**（`main()` 里）：

```cangjie
main(): Int64 {
    let app = TauriApp()
        .window(WindowConfig("我的应用", 1000, 700))
        .register("greet", GreetCommand())
        .register("add", AddCommand())            // ← 新增这一行

    let html = String.fromUtf8(File.readFrom("ui/index.html"))
    app.run(html)
    return 0
}
```

**第三步，放行它**（`capabilities/default.json`）：

```json
{
  "identifier": "default",
  "windows": ["main"],
  "commands": ["greet", "add", "system:version"],
  "events": ["tick"]
}
```

**前端调用**：

```js
withBridge(function (tauri) {
  tauri.invoke('add', { a: 2, b: 3 })
    .then(function (sum) { console.log('2 + 3 =', sum); })     // 2 + 3 = 5
    .catch(function (err) { console.error(err.message); });
});
```

改完 `.register` 与 json 后要重新 `cj-tauri dev`（权限清单是启动时加载的），改后端也要重新构建——
所以开发期通常是「改 `main.cj` / json → 关窗口 → `dev`」，只有纯前端改动才可能省掉构建那一步。

## 5. 后端推、前端收：事件

命令是「前端问、后端答」，事件是「后端主动说」。有明确返回值的用命令，连续变化的状态（进度、日志、
定时数据）用事件。

后端侧有两个发事件的口子：

- **在命令里发**：`handle` 的第三个参数 `ipc` 就是上下文，`ipc.emit("事件名", payload)` 推给当前窗口；
- **在应用层发**：`app.emit("事件名", payload)`，向所有窗口广播。

payload 必须是 JSON 值，用 `JsonObject` 拼对象最方便。下面是一个「每秒推一次」的完整命令：

```cangjie
public class TimerCommand <: CommandHandler {
    private var counter: Int64 = 0
    private var started: Bool = false

    public init() {}

    public func handle(cmd: String, args: JsonObject, ipc: IpcContext): JsonValue {
        if (!this.started) {
            this.started = true
            spawn {                                  // 起一个后台线程持续推事件
                while (true) {
                    sleep(Duration.second)
                    this.counter += 1
                    var payload = JsonObject()
                    payload.put("n", JsonInt(this.counter))
                    ipc.emit("tick", payload)
                }
            }
        }
        return JsonString("timer started")
    }
}
```

这段有几个值得学的点：

- **命令只负责启动，线程负责持续推。** `invoke('timer')` 立刻返回 `"timer started"`，
  之后每秒推一次 `tick`，前端不会因为这次调用被挂住；
- `started` 标志保证重复点按钮不会起出第二个线程——否则每秒收到的 tick 会越来越多；
- `spawn` 出来的线程里访问 `this.counter` / `this.started`，和 `handle` 在同一个对象上，
  这是示例和模板一贯的写法。真要多个线程同时改同一份状态时，记得用锁或通道把它包起来
  （AGENTS.md 里记了这条约定）。

前端订阅：

```js
var off = tauri.listen('tick', function (payload) {
  document.getElementById('tick').textContent = '第 ' + payload.n + ' 次';
});

// 不再需要时取消订阅（页面切换、组件卸载）
off();
```

同一个事件可以挂多个回调，`listen` **返回的是取消订阅的函数**——参考手册的表格里没强调这一点，
但长时间运行的应用需要它，否则回调会越积越多。

三个常见坑，事件「没反应」时按顺序排查：

1. **先查能力清单。** 未在 `events` 里声明的事件会被后端**静默丢弃**，前端只看到「什么都没发生」；
   桥的 stderr 上会留一行 `[cj-tauri] event not allowed: xxx`。
2. **注册监听要早于事件发出。** 事件不排队、不重放，`listen` 之前发出的事件就丢了。
   先把 `listen` 挂上，再 `invoke` 触发。
3. **别用 `emit` 当广播。** 前端侧的 `tauri.emit(...)` 目前是占位实现：消息会发到后端，
   但因为 `type` 不是 `invoke`，被判为非法消息丢弃（stderr 打 `invalid IPC message`），也不会回到页面。
   页面内部通信请直接用回调或原生 `EventTarget`。

## 6. 能力清单：默认最小权限

`capabilities/default.json` 决定**前端能调什么、能收什么**，对标 Tauri 的 capability：
默认什么都不许，写进去才放行。

```json
{
  "identifier": "default",
  "windows": ["main"],
  "commands": ["greet", "add", "system:version", "system:ping"],
  "events": ["tick"]
}
```

| 字段 | 必填 | 作用 |
|---|---|---|
| `identifier` | 是 | 清单名。**整份清单缺了它会被跳过**并在 stderr 告警 |
| `commands` | 否 | 放行的命令名，精确匹配，**不支持 `*` 通配** |
| `events` | 否 | 允许投递到页面的事件名，精确匹配 |
| `windows` | 否 | 目标窗口名。当前是保留字段：校验只比对命令与事件，写 `["main"]` 与现状一致 |

几条运行规则，都是当前版本的实测行为：

- **启动时自动扫描 `capabilities/` 下的所有 `*.json`**（在 `run()` 里做），多份清单**合并**生效——
  任一清单放行了某命令或事件就算通过。所以可以按功能拆：`default.json` 放通用的，
  `feature-chart.json` 只放图表要用的。
- **显式挂载优先**：一旦用了 `app.loadCapabilities("config/caps")` 或 `app.addCapabilityJson(...)`，
  目录自动扫描就不再执行。
- **一份清单都没有不会报错退出**，但所有 `invoke` 都会失败、所有事件都送不出去，stderr 上是
  `[cj-tauri] 未挂载任何 capability，且没有 capabilities/ 目录`。「代码明明写对了却全被拒」，
  八成就是这里。
- 单个清单写坏了只影响它自己：`capability JSON 解析失败 <路径>: ...`，其它清单照常加载。

发布前顺手把清单过一遍，只留这个应用真正用到的命令与事件。它同时也是**给读者看的权限声明**。

## 7. 出问题了看哪里

### 7.1 前端调试：打开开发者工具

界面上放个按钮 `tauri.invoke('system:devtools')`（这条 invoke 要 `system:devtools` 在清单里），
或在后端 `app.openDevTools()` / 命令里 `ipc.openDevTools()`（这两条不走能力校验）。

开发者工具默认是开启的；把 `WindowConfig.devTools = false` 之后宿主会拒绝打开。打开后是标准
Chromium DevTools（Windows 走 WebView2 的 `OpenDevToolsWindow`，Linux 走 WebKit Inspector），
Console / Elements / Network 都在。窗口标题形如 `[DevTools - about:blank]` 是**正常**的——
页面是用 `NavigateToString` 交给 WebView 的，本身没有 URL（这一点在 §8.1 还会用到）。

窗口图标是同一个套路：`cfg.iconPath = "icon.ico"`（Windows 只认 `.ico`），路径同样按运行目录解析。
图标加载失败只会回到系统默认图标，不会让应用起不来——所以换图标这种小事不用怕改坏。

在 Console 里先跑这两行，能一次性确认「桥通不通、后端活没活」：

```js
window.__CJ_TAURI__        // 应该是对象，不是 undefined
await window.__CJ_TAURI__.invoke('system:version')
// {name: "cj-tauri", version: "0.3.0", cangjie: "...", platform: "windows"}
```

### 7.2 后端日志：桥的 stderr

窗口是 GUI，后端的话都在**启动它的那个终端**里——所以开发和排错都用 `cli\cj-tauri.bat dev` 启动，
别双击 exe。优先搜这几个关键词：

| 日志 | 含义 |
|---|---|
| `[cj-tauri] 已自动加载 capabilities/：N 个清单` | 清单加载成功；没有这行或 N=0 说明没加载上 |
| `[cj-tauri] 未挂载任何 capability...` | 没有能力清单，所有 invoke 都会被拒 |
| `[cj-tauri] invalid IPC message: {...}` | 收到非 invoke 消息（前端用了 `emit`，见 §5） |
| `[cj-tauri] event not allowed: xxx` | 事件没在清单的 `events` 里，被丢弃 |
| `[cj-bridge] set window: title=... size=...` | 窗口配置已生效 |
| `WebView2 runtime: hr=0x00000000 ver=122...` | WebView2 运行时创建成功；`hr` 非 0 就是失败原因 |
| `[frontend] ...` | **你自己打的前端日志**，见下 |

最后一条是个实用套路：前端不方便开 Console 时，加一个命令把前端信息回传后端打 stderr——

```cangjie
public class ReportCommand <: CommandHandler {
    public init() {}
    public func handle(cmd: String, args: JsonObject, ipc: IpcContext): JsonValue {
        if (let Some(line) <- args.get("line")) {
            match (line.kind()) {
                case JsonKind.JsString => eprintln("[frontend] " + line.asString().getValue())
                case _ => ()
            }
        }
        return JsonBool(true)
    }
}
```

```js
tauri.invoke('report', { line: 'tick 收到了 ' + n });
```

后端日志统一用 `eprintln`（输出到 stderr），不要在会阻塞的地方用 `println` 打调试信息。
仓库里的 `examples/hello` 就是靠这套自检跑出 `[verify] ALL DONE` 的。

### 7.3 现象 → 原因 → 处置

| 现象 | 多半是 | 处置 |
|---|---|---|
| 窗口没弹，终端有报错 | C 桥没构建 / WebView2 运行时缺失 | 看 `WebView2 runtime: hr=` 那行，先 `cli\cj-tauri.bat info` |
| 窗口弹了但一片白 | 页面 HTML 没读到 | 确认在**项目根**启动，`ui/index.html` 能按相对路径读到 |
| 启动就抛 `File.readFrom("ui/index.html")` | 工作目录不对 | `cd` 到项目根再启动（§2） |
| 所有 invoke 都 `not allowed` | 没有能力清单 | 补 `capabilities/default.json`，对照 §6 |
| 个别 invoke `not registered` | 忘了 `.register` | 补注册（§4 第二步） |
| 事件不到页面 | 清单没声明，或 `listen` 挂得太晚 | 照 §5 的三条坑排查 |
| 改了前端没变化 | 页面是启动时读入的 | 关窗口重新 `dev`（没有热重载） |

### 7.4 报错要看原文

报错里带着命令名、事件名、文件路径，别只看截图的头几个字。去 issue 提问或写 PR 时，
按 [CONTRIBUTING.md](../CONTRIBUTING.md) 的要求附上：操作系统、仓颉 SDK 版本、WebView2 版本、
复现步骤，以及**桥的 stderr 日志原文**。

## 8. 前端工程化与已知限制

### 8.1 页面是怎么交到 WebView 的（决定了资源怎么放）

`app.run(html)` 把 HTML **字符串**交给宿主：Windows 上是 WebView2 的 `NavigateToString`，
Linux 上是 WebKit 的字符串加载。这带来几个很具体的后果，写前端时要记着：

- **页面没有 URL、也没有基准路径**（所以 DevTools 标题是 `about:blank`）。依赖基准地址的写法
  不要用：`fetch('./data.json')`、相对路径的 `<script src="app.js">`、`<img src="./logo.png">`
  都会被解析到 `about:blank` 上而失败。
- **内联最稳**：CSS 写在 `<style>` 里、JS 写在 `<script>` 里、图片用 data URI 或在线地址。
  模板工程与 `examples/hello` 都是这个形态，实机验证过。
- **在线 CDN 理论上可用**，但依赖网络；仓库里没有验证过 CDN 场景，建议先用内联把功能跑通再加外部依赖。
- 要用真正的多文件前端，就靠构建工具**打成单文件**（例如 Vite 搭配单文件插件），再把产物作为页面交给后端。

### 8.2 用 Vite / React / Vue 的产物

流程不变，只是多一步构建：

1. 前端照常写，构建输出到临时目录；
2. 把产物整合成单文件，覆盖 `ui/index.html`（或换成别的文件名，见第 3 步）；
3. 后端读的文件名对了就行——它永远是「读文件 → `app.run(html)`」这两行。

后端那一侧不用为前端框架做任何改动，这也是 cj-tauri 与 Tauri 一致的地方：**前端是什么框架，
后端不关心**。

### 8.3 `emit` 是占位实现（已知限制）

桥里暴露了 `tauri.emit(event, payload)`，但**它现在不工作**：

- 消息确实发到了后端，协议上的 `type` 是 `emit`；
- 后端只认 `type: "invoke"`，其余一律按非法消息丢弃，stderr 上会打
  `[cj-tauri] invalid IPC message: {"type":"emit",...}`；
- 它也不会回到页面，所以**页面内广播同样不生效**。

页面内部要广播，用原生方式就行，不必绕后端：

```js
// 页面内部通信：标准 DOM 事件
document.dispatchEvent(new CustomEvent('my-app:refresh', { detail: { n: 1 } }));
document.addEventListener('my-app:refresh', function (e) { console.log(e.detail.n); });
```

跨进程的通知（仓颉 → 前端）请走「`ipc.emit` + `listen`」，那条链路是完整可用的。
要让前端 `emit` 真正跑通，需要在后端补一个「`emit` → 回投为 `event`」的环路并接上能力校验；
这不需要改 C 桥，欢迎按 [CONTRIBUTING.md](../CONTRIBUTING.md) 提 PR。

### 8.4 官方的 Vue / React 模板：从「单文件内联」升级到 dev server

8.1–8.2 讲的都是「先把产物打成单文件，再交给后端」。脚手架把这条路径做成了两个开箱模板：

```bash
cj-tauri create my-app --template vue     # Vue 3 + Vite
cj-tauri create my-app --template react   # React 18 + Vite
cd my-app && cj-tauri dev                 # 接管前端 dev server：改前端源码不重启应用
```

`create` 缺省仍是不带 Node 的 `app` 模板（内联 HTML），老用法不受影响。

- `ui/` 是标准 Vite 工程：`vite.config.js` 固定 `127.0.0.1:5173` 并开 `strictPort`（端口被占直接报错，
  免得应用连上一个意外端口），同时挂了 `vite-plugin-singlefile`。
- **开发态**：`cj-tauri dev` 起 dev server 并把地址注入 `CJ_TAURI_DEV_URL`，页面来自真实 URL，
  所以改 `.vue` / `.jsx` 保存即生效；改后端 `src/*.cj` 仍要重新 `dev`（框架不承诺后端进程内热替换）。
- **发布态**：`cd ui && npm run build` 产出**一个** `ui/dist/index.html`（js/css/图片全内联），
  后端依旧只是「读文件 → `run(html)`」；`cj-tauri build` 会自动先跑这一步。

两个模板的后端代码、能力清单、`dev` / `build` 用法完全一样，区别只在 `ui/` 里是 Vue 还是 React。

排查 HMR 时先记住这条判据：Vite 的模块图是**客户端请求过页面之后**才建立的，
没有页面连上来时改文件，日志只会出现 `[no modules matched]`——那不是 HMR 坏了。
让页面（窗口或浏览器）真的连上 dev server 后，改 `ui/src/App.vue` 的实测日志形态是：

```text
vite:hmr [file change] src/App.vue
vite:hmr [self-accepts] src/App.vue
vite:hmr [vue:update(template)] ui/src/App.vue
[vite] (client) hmr update /src/App.vue
```

（`vite:hmr` 这几行要起 dev server 时带 `DEBUG=vite:hmr` 才打印。）

## 9. 完整实战：写一个待办清单

前面几节把零件讲完了，这一节把它们拼成一个真东西。目标：输入框添加待办、列表展示、点 × 删除、
底部显示条数。三种通信都用上——`invoke` 取数据与改数据、事件通知前端重绘、能力清单控制权限。

先把 `src/main.cj` 整个替换成下面的内容（模板自带的 `greet` / `timer` 可以删掉），
再改 `capabilities/default.json`，最后写 `ui/index.html`。三份文件都给了完整代码，可以直接抄。

### 9.1 后端：一个共享状态 + 三个命令

关键设计是**状态放在一个对象里，三个命令共用它**（模板把状态放在各自的命令里，
那是因为 tick 计时器本来就只属于一个命令）。

```cangjie
package myapp

import cjTauri.*
import std.collection.*
import std.fs.File
import stdx.encoding.json.*

/**
 * 待办数据：三个命令共用同一份内存状态。
 * 说明：示例里所有改动都发生在处理 IPC 请求的线程上，所以没加锁；
 * 一旦你从别的线程（比如定时器）也来改它，就要自己加锁或用通道。
 */
public class TodoStore {
    private var items: ArrayList<String> = ArrayList<String>()

    /** 追加一条，返回当前条数 */
    public func add(text: String): Int64 {
        this.items.add(text)
        return this.items.size
    }

    /** 按下标删除；越界返回 false，不抛异常 */
    public func remove(index: Int64): Bool {
        if (index < 0 || index >= this.items.size) {
            return false
        }
        var next = ArrayList<String>()
        var i: Int64 = 0
        for (t in this.items) {
            if (i != index) {
                next.add(t)
            }
            i += 1
        }
        this.items = next
        return true
    }

    /** 转成 JSON 数组，直接交给前端 */
    public func toJson(): JsonValue {
        var list = ArrayList<JsonValue>()
        for (t in this.items) {
            list.add(JsonString(t))
        }
        return JsonArray(list)
    }

    public func count(): Int64 {
        return this.items.size
    }
}

/** 广播当前列表：前端 listen("todo:changed") 收到后重绘 */
func broadcast(store: TodoStore, ipc: IpcContext): Unit {
    var payload = JsonObject()
    payload.put("items", store.toJson())
    payload.put("count", JsonInt(store.count()))
    ipc.emit("todo:changed", payload)
}

/** todo:add { text } -> 新条数 */
public class TodoAddCommand <: CommandHandler {
    private let store: TodoStore

    public init(store: TodoStore) {
        this.store = store
    }

    public func handle(cmd: String, args: JsonObject, ipc: IpcContext): JsonValue {
        var text = ""
        if (let Some(v) <- args.get("text")) {
            match (v.kind()) {
                case JsonKind.JsString => text = v.asString().getValue()
                case _ => ()
            }
        }
        if (text.size == 0) {
            // 抛 CommandException：前端 .catch 里收到的 err.message 就是这句话
            throw CommandException("text 不能为空")
        }
        let n = this.store.add(text)
        broadcast(this.store, ipc)
        return JsonInt(n)
    }
}

/** todo:remove { index } -> true/false */
public class TodoRemoveCommand <: CommandHandler {
    private let store: TodoStore

    public init(store: TodoStore) {
        this.store = store
    }

    public func handle(cmd: String, args: JsonObject, ipc: IpcContext): JsonValue {
        var index: Int64 = -1
        if (let Some(v) <- args.get("index")) {
            match (v.kind()) {
                case JsonKind.JsInt => index = v.asInt().getValue()
                case _ => ()
            }
        }
        let ok = this.store.remove(index)
        broadcast(this.store, ipc)
        return JsonBool(ok)
    }
}

/** todo:list -> { items: [...], count: N } */
public class TodoListCommand <: CommandHandler {
    private let store: TodoStore

    public init(store: TodoStore) {
        this.store = store
    }

    public func handle(cmd: String, args: JsonObject, ipc: IpcContext): JsonValue {
        var obj = JsonObject()
        obj.put("items", this.store.toJson())
        obj.put("count", JsonInt(this.store.count()))
        return obj
    }
}

main(): Int64 {
    let store = TodoStore()
    let app = TauriApp()
        .window(WindowConfig("待办清单 · cj-tauri", 900, 640))
        .register("todo:add", TodoAddCommand(store))
        .register("todo:remove", TodoRemoveCommand(store))
        .register("todo:list", TodoListCommand(store))

    let html = String.fromUtf8(File.readFrom("ui/index.html"))
    app.run(html)
    return 0
}
```

两个值得注意的写法：

- **状态通过构造函数注入**（`TodoAddCommand(store)`），三个命令天然共享同一份数据，
  不需要全局变量；
- **失败用 `throw CommandException("...")`**，前端 `.catch` 收到的 `err.message` 就是这句话；
  而「越界删除」这种可预期的结果用返回值表达（`false`），不抛异常——**预期内的分支用返回值，
  预期外的失败才抛异常**，前端处理起来最省事。

`capabilities/default.json`：

```json
{
  "identifier": "default",

```

`todo:` 只是命名习惯（框架内置命令用 `system:`），不影响校验——校验是**按完整字符串精确匹配**。

### 9.3 前端：`ui/index.html`

```html
<!DOCTYPE html>
<html>
<head>
<meta charset="utf-8">
<title>待办清单</title>
<style>
  :root { color-scheme: dark; }
  body { font-family: system-ui, "Segoe UI", sans-serif; background: #16161d; color: #e6e6e6;
         margin: 0; padding: 32px; display: flex; justify-content: center; }
  .card { width: min(520px, 92vw); background: #1f2029; border: 1px solid #2e3140;
          border-radius: 14px; padding: 24px 28px; }
  h1 { margin: 0 0 18px; font-size: 20px; color: #7ce7ff; }
  .row { display: flex; gap: 8px; }
  input { flex: 1; font-size: 15px; padding: 9px 12px; border-radius: 9px;
          border: 1px solid #2e3140; background: #141821; color: #e6e6e6; }
  button { font-size: 15px; padding: 9px 14px; border: none; border-radius: 9px;
           background: #e94560; color: #fff; cursor: pointer; }
  ul { list-style: none; margin: 18px 0 0; padding: 0; }
  li { display: flex; align-items: center; justify-content: space-between; gap: 10px;
       padding: 10px 12px; border-radius: 9px; background: #171a22; margin-bottom: 8px; }
  li button { background: #2b3040; padding: 4px 10px; }
  #count { margin: 14px 0 0; font-size: 13px; color: #9aa0b4; }
</style>
</head>
<body>
  <div class="card">
    <h1>待办清单</h1>
    <div class="row">
      <input id="text" placeholder="要做什么？">
      <button id="add">添加</button>
    </div>
    <ul id="list"></ul>
    <p id="count"></p>
  </div>

  <script>
    function withBridge(cb) {
      if (window.__CJ_TAURI__) { cb(window.__CJ_TAURI__); return; }
      setTimeout(function () { withBridge(cb); }, 50);
    }

    withBridge(function (tauri) {
      var textEl = document.getElementById('text');
      var listEl = document.getElementById('list');
      var countEl = document.getElementById('count');

      // 唯一的渲染入口：拿到一份完整数据就重画一次
      function render(payload) {
        listEl.innerHTML = '';
        payload.items.forEach(function (text, i) {
          var li = document.createElement('li');

          var span = document.createElement('span');
          span.textContent = text;                  // 用 textContent，不要拼 innerHTML

          var del = document.createElement('button');
          del.textContent = '删除';
          del.onclick = function () {
            tauri.invoke('todo:remove', { index: i })
              .catch(function (err) { console.error(err.message); });
          };

          li.appendChild(span);
          li.appendChild(del);
          listEl.appendChild(li);
        });
        countEl.textContent = '共 ' + payload.count + ' 条';
      }

      // 后端每次改动都会推这个事件；前端只管重绘，不自己维护副本
      tauri.listen('todo:changed', render);

      document.getElementById('add').onclick = function () {
        var text = textEl.value.trim();
        if (!text) { return; }
        tauri.invoke('todo:add', { text: text })
          .then(function () { textEl.value = ''; })     // 只清输入框，刷新交给事件
          .catch(function (err) { alert(err.message); });
      };

      // 首次进入拉一次全量
      tauri.invoke('todo:list')
        .then(render)
        .catch(function (err) { countEl.textContent = '加载失败：' + err.message; });
    });
  </script>
</body>
</html>
```

这份前端有两个刻意的设计，值得照抄到自己的项目里：

- **唯一的真相在后端**：点添加之后前端只清输入框，**不自己往列表里塞一条**，界面靠
  `todo:changed` 事件重绘。这样前端永远显示后端认可的数据，不会出现「界面上有、后端没有」的假状态。
- **只有一个渲染入口**：全量数据和事件推来的数据走同一个 `render(payload)`，不存在两套渲染逻辑要走同步。
- 删除按钮用 `render` 时的下标 `i`：因为每次重绘拿到的都是后端最新数组，下标一定对得上。
- 列表项用 `textContent` 赋值而不是拼 HTML 字符串——待办内容是用户输入的，拼 HTML 等于自己给自己开 XSS。

## 10. 常见问题

**必须用纯 HTML 写界面吗？能用前端框架吗？**
可以。后端只认「一个 HTML 字符串」（§8.1），React / Vue / Svelte 都行，只要最终产出单文件。
但要注意资源路径限制：不要出现依赖基准路径的 `fetch` 与相对路径静态资源。

**前端能直接读文件、连数据库吗？**
不能，也不建议绕。WebView 里只有页面本身；凡是要碰文件、网络、系统能力的事，都在仓颉侧写命令，
前端通过 `invoke` 拿结果——这也是 Tauri 的模型：**前端负责显示，后端负责能力**。
安全收益很直接：能力清单（§6）能一句话收回权限。

**能开多个窗口吗？**
当前版本是单窗口（窗口名固定 `main`），`capabilities` 里的 `windows` 字段是保留字段，
还没参与窗口级校验。多窗口在路线里，暂时不要基于它设计应用。

**有热重载吗？怎么调最快？**
没有 dev server，改完要重启（改前端 → 关窗口 → `dev`）。所以最省事的做法是：把后端命令先写全、
用 DevTools Console 手动 `invoke` 验证，前端界面最后再接——比反复重启快很多。

**localStorage / IndexedDB 能用吗？**
不要依赖。页面是 `NavigateToString` 交给 WebView 的，没有稳定的 URL 与来源，
存储行为不在本仓库的保证范围内（也没有验证过）。要持久化就写一个后端命令落文件，
下次启动时读回来——数据放在仓颉侧，也方便以后换宿主（鸿蒙等）。

**`command not allowed` 和 `command not registered` 怎么一眼分辨？**
`not allowed` = 能力清单没放行 → 改 `capabilities/*.json`；
`not registered` = 仓颉侧没注册 → 改 `main.cj`（§3.3、§4）。

**事件收不到？**
按这个顺序：清单里有没有 `events`（stderr 会打 `event not allowed`）→ `listen` 是不是挂晚了 →
后端那次 `ipc.emit` 到底有没有执行。

**`alert()` 弹不出来或界面卡住？**
`alert` 会阻塞渲染线程，调试时能用，正式代码换成页面内的提示区（示例都是往 `#result` 里写文本）。
另外注意别在 `while (true)` 循环里做重活，`spawn` 的线程也一样会吃 CPU。

**为什么页面里没有 URL、DevTools 显示 `about:blank`？**
页面是字符串交给 WebView 的，没有经过 http 服务（§8.1）。好处是没有端口冲突、不用担心本地服务被占用；
代价就是没有基准路径，见上面第一条。

## 11. 用插件少写样板：一行接入官方 fs（v1）

前面每一节都在讲「自己写命令」。如果某个能力框架已经提供了，就不用自己写——**插件**是「一组命令 + 可选事件 +
可选前端 JS」的打包，装一行就能用（对标 Tauri v2 的 `.plugin(...)`）：

```cangjie
// src/main.cj 的装配处
let app = TauriApp()
    .window(WindowConfig("我的应用", 1000, 700))
    .plugin(FsPlugin())          // ← 就这一行：读文件 / 写文件 / 判断存在
```

框架自带 `fs` 插件（`src/plugin_fs.cj`），命令是 `fs:readText`、`fs:writeText`、`fs:exists`
（`writeText` 是覆盖写：文件存在就截断，不存在就创建）。前端用独立命名空间，不碰 `invoke`：

```js
window.__CJ_TAURI__.fs.readText({ path: 'ui/index.html' }).then(function (text) {
  console.log(text.length + ' 个字符');
});
window.__CJ_TAURI__.fs.exists({ path: 'ui/index.html' });   // Promise<boolean>
```

**它和 §4「加命令三处联动」是一回事，只是第 1、2 步由插件包办了**：你仍然要在
`capabilities/default.json` 的 `commands` 里放行 `"fs:readText"` 这些**全名**——插件只声明「我提供什么」，
**不会自动放行**。忘了放行不会静默失败：启动时框架会打印已装配的插件清单，并逐条提示缺哪个：

```text
[cj-tauri] 已装配 1 个插件：
  fs  fs:readText, fs:writeText, fs:exists
[cj-tauri] 插件 fs 的命令 fs:writeText 尚未授权，前端调用会被拒绝
[cj-tauri]   请在 capabilities 目录的 json 里把 "fs:writeText" 加进 commands
```

页面里调用没放行的命令，`catch` 拿到的就是 `command not allowed: fs:writeText`。

两个要注意的点：

- **插件 JS 在页面脚本之前就绪**：插件的 `jsShim()` 由框架汇总成一个 `<script>` 块插到 `</head>` 之前，
  所以页面的第一行就能读 `window.__CJ_TAURI__.fs`。但用 `app.runUrl(...)`（dev server、远程页面）时
  HTML 不在后端进程里，框架没法插进去，只能在 stderr 提示——那种场景照 §3.1 的 `waitForBridge` 等桥。
- **自己写插件也很短**：实现 `Plugin` 接口，必写 `name()` 与 `commands()`，`events()` / `jsShim()` / `setup(app)`
  都有默认实现（不写就是「没有事件、没有前端片段」）。可跑样板见 `examples/plugin-fs/`；
  想自己写一个（含事件、`setup`、打包成独立包）看 [插件体系教程](插件体系教程.md)，
  接口设计取舍见 [RFC-001 插件体系](RFC-插件体系.md)。
