# 平台能力矩阵

> 回答一个问题：「我想要的命令 / 插件 / 宿主能力，在我的目标平台上到底能不能用？」
> 状态口径与 `docs/需求追踪.md` 一致：**没有实机证据的状态不标可用**（AGENTS §1 门禁 4）。
> `未验证` ≠ 不支持——只是没人带着证据跑过；欢迎按 `CONTRIBUTING.md` 补实机取证。

## 三层判据

一个能力在某个平台上「能用」，分三层，别混为一谈：

1. **宿主基元**——建窗、页面装载、IPC 双向桥。三平台均已闭环（鸿蒙 2026-10-19 真机）。
2. **宿主能力位**——菜单 / 托盘 / 快捷键 / 拖放 / 原生对话框 / 通知。见下表。
3. **插件**——框架之上的命令实现，多数不依赖 C 桥，但依赖 stdx 与平台库。

| dialog | ✅ 实机 | ✅ 实机 | ❌ | 依赖宿主能力位（鸿蒙 0） |

| clipboard | ✅ 实机 | ⚠️ 未实机 | ✅ 真机 | 鸿蒙走系统 pasteboard FFI |
| notification | ✅ 实机 | ⚠️ 桩 | ❌ | |
| mqtt | ✅ 实机（E2E 27/27） | ⚠️ 未验证 | ⚠️ 未验证 | 明文 TCP，stdx socket；不碰 TLS |
| redis | ✅ 实机（E2E 47/47） | ⚠️ 未验证 | ⚠️ 未验证 | 明文 TCP（RESP2）；不碰 TLS |

## 鸿蒙侧为什么这么多 ❌

鸿蒙平台**不走 C 桥**：宿主直接写在仓颉侧（`src/host_arkweb.cj`），核心 FFI 一律 `@When[env != "ohos"]`
门禁 + 如实降级。宿主能力位按「没有实机证据不许上报」的口径保持 0——不是「做不到」，
是「还没带着证据做」。补齐路径与真机判据见 `native/platforms/harmonyos/README.md` 与
`docs/鸿蒙ArkWeb接入踩坑.md`。

**「不可用」是当前状态，不是平台硬限制。** 鸿蒙 NDK 本身有完整的 C 接口（设备上是 musl libc，
termios / open / read 都在；`libpasteboard.so` 等系统库都能链），插件能力的现成补齐路径是
**NDK FFI 直连 + 清单 `[links]` 链接**——剪贴板已照这条路落地（`OH_Pasteboard_*` 直连，
不经 C 桥、无能力位），`[links]` 段（2026-10-24 加入）让应用自带的原生库也能走同一机制。
依赖 `cj_bridge_*` C 桥导出的能力（串口 termios/DCB、`launchHidden`、日志 fd 接管）要落鸿蒙，
同样可以给鸿蒙写一份 FFI 实现；卡点不在「有没有 C 接口」，在**设备侧取证**——
串口设备节点权限、SELinux 策略这些必须真机验过才能按门禁上报可用。

## 计划

- 鸿蒙：托盘 / 快捷键 / 拖放 / 原生对话框的通知能力位按需求排期（真机在手时可做）。
- Windows：拖放、通知、剪贴板、log 从桩升到实机取证。
- 平台状态变化同步更新本表与 `docs/需求追踪.md` 对应行。
