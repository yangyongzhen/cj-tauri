# 扩展 cj-tauri：三条路径与原生能力接入指南

> 定位：这是一篇**决策 + 操作手册**。看完你应该能判断自己的需求属于哪一类、需要动哪些文件、
> 以及怎么验证它真的通了。
> 单点实战（读设备电量的完整代码）见 `docs/实战-自定义插件读取设备电量.md`；
> 插件设计取舍见 `docs/RFC-插件体系.md`；宿主能力现状见 `native/platforms/harmonyos/README.md`。

## 1. 先把三个概念分开

混在一起是绝大多数「加不上能力」的根源。

| 概念 | 是什么 | 谁定义 |
|---|---|---|
| **插件**（`Plugin`） | 一组命令 + 可选事件 + 可选前端 JS 片段的打包单位，命令全名 `<插件名>:<短名>` | 任何一方都能写 |
| **命令**（`CommandHandler`） | 一次前端 `invoke` 落到的处理函数，跑在 worker 线程 | 插件 / 应用自己 |
| **能力位**（`CJ_CAP_*`） | **宿主（窗口那层）原生支持什么** 的位图，驱动 `hostCapabilities()` | **只有框架能改** |

最关键的一条：**能力位回答的是「宿主支持什么」，不回答「应用能做什么」**。
读电量、查传感器、发 HTTP 请求都不需要任何能力位；托盘、全局快捷键、拖放才需要。
所以「能力位是 0」不等于「这个功能做不了」——先看它是不是根本不需要位。

## 2. 决策树：你的需求走哪条路

```
你的能力需要宿主句柄（窗口 / WebView）或必须跑在宿主 UI 线程吗？
├─ 不需要 ──→ 需要画 ArkUI 组件（@Component / Web / 声明式弹窗）吗？
│             ├─ 不需要 ──→ 【情况 A】自定义插件（不改框架）★ 绝大多数需求在这一类
│             └─ 需要   ──→ 【情况 C】应用侧 ArkUI（框架包禁止引用 kit.ArkUI）
└─ 需要   ──→ 【情况 B】扩宿主能力（改框架，走一能力一 PR）
```

再补一条判断：**这个能力会不会改变 cj-tauri 自己承诺的能力位语义？**
会，就是情况 B；不会，A / C 都能做到。

## 3. 情况 A：纯数据能力——自定义插件（不改框架）

这一类包括：设备信息、传感器、电量、剪贴板（读数据）、网络请求、加解密、文件处理、调用别的进程……

### 3.1 三种子情形，先认清

| 子情形 | 前置条件 | 额外工作 |
|---|---|---|
| A1：SDK 有仓颉绑定 | 例：`kit.NetworkKit`、`kit.PerformanceAnalysisKit.Hilog` | 直接 `import`，**零链接配置** |
| A2：SDK 没绑定，但有原生 C API | 例：battery、pasteboard | `foreign func` + 清单 `[links]` 补库 |
| A3：连 C API 都没有 | 极少数 | 自己写 C 桥，或放弃该能力 |

判断 A1 / A2 的一条命令：

```bash
ls <SDK>/api/lib/linux_ohos_aarch64_cjnative/{ohos,kit} | grep -i <关键词>
```

查得到就是 A1。查不到再去 sysroot 找头文件（`find <sysroot>/usr/include -iname "*<关键词>*"`），
有头文件就是 A2。

### 3.2 最小可运行插件（骨架）

```cangjie
package yourApp

import cjTauri.*
import std.collection.*
import stdx.encoding.json.*

public class MyCommands <: CommandHandler {
    public func handle(cmd: String, args: JsonObject, ipc: IpcContext): JsonValue {
        let _ = args
        let _ = ipc
        match (cmd) {
            case "hello" => return JsonString("hello from native")
            case _ => throw CommandException("my: unknown command " + cmd)
        }
    }
}

public class MyPlugin <: Plugin {
    public func name(): String {
        return "my"
    }

    public func commands(): HashMap<String, CommandHandler> {
        let m = HashMap<String, CommandHandler>()
        m.add("hello", MyCommands())        // ← 写短名！框架补前缀
        return m
    }
}
```

装配一条链：

```cangjie
TauriApp()
    .plugin(MyPlugin())
    .run()
```

放行（`assets/capabilities/*.json`）：

```json
{ "identifier": "my", "commands": ["my:hello"] }
```

前端：

```js
const msg = await window.__CJ_TAURI__.invoke('my:hello');
```

**四条铁律**（漏一条就是一个具体错误）：

1. `commands()` 的键写**短名**，写全名会得到 `my:my:hello` → `command not registered`；
2. 装配在 `run()` 之前；
3. 能力清单必须写 `my:hello`，否则 `command not allowed`；
4. handler 里抛 `CommandException("...")` 是**正常失败路径**，前端 `catch` 能拿到这句话；
   别用 `return JsonNull()` 冒充失败。

### 3.3 插件还能声明什么（按需）

`Plugin` 接口的成员都有默认实现，多数插件只写 `name()` + `commands()`：

| 成员 | 用途 | 何时需要 |
|---|---|---|
| `events()` | 声明可能推送的事件短名 | 要往页面推事件（配合 `ipc.emit`） |
| `jsShim()` | 一段前端 JS，定义 `window.__CJ_TAURI__.<插件名>` | 想让前端有更顺手的 API 封装 |
| `permissions()` | 命名权限集：短集名 → 成员 | 命令多、想让用户一次放行一组 |
| `scopeAware()` | 声明本插件的路径参数吃 `scopes` 白名单 | 命令参数里有文件路径 |
| `describe()` | 自描述：`supportedHosts` / `requiredCapabilities` | 插件只在部分宿主可用 |

三个容易误解的点：

- **`jsShim()` 必须在 `start()` / `startUrl()` 之前注册**，它走 document-start 注入通道。
  `runUrl()`（页面不在本进程）场景下无法并入，框架会在 stderr 提示；
- **`permissions()` 声明 ≠ 放行**。集是给清单「引用」用的语法糖，清单不引用一条也不生效；
- **`scopeAware()` 默认 false 表示「全量放行 + 启动打一行提示」**，声明 true 后必须在自己 handler 里
  对页面可控的路径参数调 `ipc.resolveScopedPath(插件名, 原文)`，别在平台实现里另判一份。

### 3.4 两个必须记住的线程事实

1. **命令是异步分发的**：`handleInvoke` 只做校验，通过校验的命令 `spawn` 到 worker 线程执行。
   所以慢命令不会冻窗口，但**同一命令并发调用不保证顺序**，前端按 promise id 匹配。
2. **worker 线程里只能经 `jsSink` 回投**，不能直接调 GTK / WebKit / ArkUI——
   仓颉轻量线程的堆上协程栈会被 JS 引擎的栈边界校验 abort。

## 4. 情况 B：宿主能力——必须改框架

触发条件：能力需要**窗口句柄 / WebView 句柄**，或必须跑在**宿主 UI 线程**上。
例：托盘、全局快捷键、文件拖入、原生菜单、窗口可见性、原生对话框。

**为什么应用侧写不出这类能力**：宿主句柄在框架的 `HostGlobals` 里，应用的插件拿不到；
而且这类能力还要维护「平台差异只在两处」的架构契约（`@When` 条件编译 + `native/platforms/*`）。

### 4.1 四处改动（顺序不能乱）

```cangjie
// ① 扩接口：src/host.cj
public interface WebViewHost {
    // ... 已有成员 ...
    func setMyCapability(flag: Bool): Bool
}
```

```cangjie
// ② 各平台实现（平台差异只在这里出现）
// src/host_webview2.cj（Windows）、src/host_webkit.cj（Linux）、src/host_arkweb.cj（鸿蒙）
// 鸿蒙侧未实现就如实失败 + 打一行 stderr，返回 false
```

```c
// ③ C 桥：native/core/（导出在 core，分叉在 cj_plat_* 原语里）
int32_t cj_bridge_set_my_capability(struct cj_host *h, int32_t flag);
// native/platforms/linux|windows/bridge_*.c 各实现一份，两平台同名同签名
```

```cangjie
// ④ 能力位：native/core/bridge_core.h 的 CJ_CAP_* 与 hostCapabilities()
#define CJ_CAP_MENU      (1u << 0)
#define CJ_CAP_TRAY      (1u << 1)
#define CJ_CAP_HOTKEY    (1u << 2)
#define CJ_CAP_DRAGDROP  (1u << 3)
#define CJ_CAP_DIALOG    (1u << 4)
#define CJ_CAP_NOTIFIC  (1u << 5)
#define CJ_CAP_SUBTITLE  (1u << 6)
```

### 4.2 三条硬约束

1. **能力位只在真机取证之后才置 1**。没验证过就置 1 等于对外撒谎，
   前端会以为能用、拿到的是静默失败。
2. **回调一律按句柄路由**。C 侧每个宿主注册的是同一个函数指针，仓颉侧若把「本窗回调」写进静态单槽，
   后装配的窗口会覆盖先装配的——先装配的窗口从此收不到事件。走 `registerHostRoute` / `hostRouteOf`。
   **唯一例外是消息回调**（报文自带 window label，框架给所有窗装同一只派发器）。
3. **预置类能力（菜单、拖放策略）必须在 `start()` 之前定稿**，运行期再改走
   `setMenuItemState` 这类按 id 找的增量接口。

### 4.3 宿主能力落地后的验收

- 桥的 stderr 有你的能力行，且 `hr=` 为 0 / 或明确的拒绝原因；
- `system:host` 返回的位图里该位变了，页面能读到；
- 真机一轮页面自检的 PASS 明细条数与聚合行计数一致（日志行序不保证，别按「最后一行是 DONE」判）。

## 5. 情况 C：ArkUI 界面——只能在应用侧

要画 `@Component` / `Web` / 声明式弹窗？**框架包绝对不能引用 ArkUI**。

原因是一条实测过的崩溃链：框架包作为独立编译单元引用 `kit.ArkUI` 时，合并进应用动态库后
初始化链里的 `bl _CGP9kit.ArkUIiiHv@plt` 会跳到坏地址 → **启动即 SIGSEGV**（白屏或秒退）。

落法：ArkUI 只写在应用侧（如 `entry/src/main/cangjie/index.cj`），框架只导出 **ArkUI-free** 的
桥接函数（`javaScriptProxy` 回调里调它们）。另外记住鸿蒙侧的两条已知形状：

- **`javaScriptProxy` 的返回值传不回页面**（返回固定串也是 `null`），所以「页面拉、原生答」的同步模型
  不成立，回投必须由**原生推**；
- **页面触发的弹窗只能用声明式 overlay**：`showAlertDialog` / `showPromptAction().showDialog`
  在该回调的同步栈上调用会被**静默丢弃**（不抛异常、窗口不画）。做法是回调里只置 `@State`，
  `build()` 里按状态渲染根 `Stack` 的最后一个子节点。

## 6. 原生库链接：两种情形，别混

| 情形 | 判据 | 落法 |
|---|---|---|
| 库由框架**已经链上** | `-lpasteboard -ludmf` 这类在框架默认值里 | 什么都不用做 |
| 库要你自己加 | 生成物里没有 | 清单 `[links]` 段 |

```toml
# cj-tauri.toml
[links]
  ohos            = "-lohbattery_info"
  desktop-linux   = "-lcamera"
  desktop-windows = "camera.lib"
```

三条语义（都是实测过的）：

1. **追加不覆盖**：框架必需项（`-lcjtbridge` / `-lpasteboard` / `--subsystem=windows`）顶不掉；
2. **写三端各一份**：同一个库在三端名字通常不同；
3. **不写就逐字节不变**：老工程升级 CLI 不会被判漂移。

**为什么不能改框架自己的 `cjpm.toml`**：最终链接发生在 `targets/*` 那一层（桌面 executable、
鸿蒙 entry dynamic），框架包是 static，写在框架里的 `link-option` 到不了最终链接。
这是「编译过、启动崩」的经典形状。

## 7. 能力位与权限：谁改得动，谁改不动

| 你想做的事 | 能不能做 | 说明 |
|---|---|---|
| 应用自己加一个 `CJ_CAP_*` | **不能** | 能力位是框架契约，只有框架改 |
| 插件自动放行自己的命令 | **不能** | 插件只声明「我提供什么」，放行在应用清单 |
| 应用按清单放行某插件命令 | 能 | `capabilities/*.json` 的 `commands` |
| 应用按命名权限集放行 | 能 | `permissions: ["fs:readonly"]` |
| 应用运行期加路径白名单 | 能，**但要用户确认** | `allowScopePattern`，只该在取得确认后调 |
| 应用强行改「宿主支持什么」 | **不能** | 那是平台实现的事实，不是配置 |

最后一条的现实意义：`hostCapabilities()` 返回 0 的平台上，相关调用会**如实拒绝**，
这不是配置能绕过的。要做就得走情况 B。

## 8. 验收与调试清单

- [ ] 命令三处联动齐全（实现 + 注册 + 能力清单）
- [ ] 清单改了跑过 `sync`，生成物里能 grep 到你的库
- [ ] 模块 `.so` 的 `DT_NEEDED` 里有那个库（鸿蒙侧是启动崩溃的分水岭）
- [ ] 桌面端如实失败而不是返回默认值
- [ ] 页面 `invoke` 都带 `catch`
- [ ] 真机日志：hilog 里能看到你自己的抽点（框架 `stderr` 不上设备）
- [ ] 构建零警告（新代码不带警告交付）

调试优先级（从便宜到贵）：

1. **看能力清单与命令名**——`command not allowed` / `command not registered` 占了新手问题的大半；
2. **看生成物**——清单没错但生成物没变，就是忘了 `sync`；
3. **看运行时日志**——鸿蒙上前提是 hilog，且要**流式**抓（缓冲会滚掉启动瞬间的行）；
4. **最后才怀疑代码**——尤其「改了没变化」时，先怀疑产物陈旧（hvigor 与 cjpm 各有一份增量缓存）。

## 9. 常见错误对照表

| 错误串 | 真因 | 修法 |
|---|---|---|
| `command not registered` | 没装配 / 没在 `commands()` 登记 / 键里重复写了前缀 | 见 §3.2 |
| `command not allowed` | 能力清单没写该命令 | 加进 `commands` |
| `command rejected (<名>): …` | handler 抛了 `CommandException`（**正常业务失败**） | 看括号里的原因 |
| `command failed (<名>): …` | handler 抛了非预期异常 | 修 handler |
| 启动即 SIGSEGV，`llvm-nm -D` 里有 `U cj_bridge_*` | 该平台没有 C 桥，FFI 声明漏了 `@When` | 给声明与薄包装同一口径的条件编译 |
| 启动即 SIGSEGV，`U OH_xxx` 无处解析 | 库没进最终链接 | 清单 `[links]` |
| `undeclared identifier 'std'` | 正文写了限定名 `std.collection.X` | 加 `import` 并用短名 |
| `undeclared identifier 'TlsClientConfig'` | 少 `import stdx.net.tls.*` | 补 import |
| `[links] ohos 不能含双引号` | 值里混进了引号 | 去掉引号 |
| 桌面读 `0%` | 桌面分支没如实失败 | 抛 `CommandException` |
| `error: undeclared identifier 'defer'` | 本机仓颉没有 `defer` | 显式 `Destroy` / 手动释放 |
| 清单报 `path-option` 相关错 | toml 里写了反斜杠 | 用正斜杠 |

## 10. 一页速查

```
要加能力
  ├─ 不需要宿主句柄
  │    ├─ SDK 有绑定 ──── import 直接用（A1）
  │    ├─ 有 C API ────── foreign func + [links]（A2）
  │    └─ 要 ArkUI ────── 应用侧组件（C）
  └─ 需要宿主句柄 ─────── 扩 WebViewHost + 三实现 + C 桥 + 能力位（B，一能力一 PR）
```

记住三句话：

1. **能力位是宿主的事实，插件是应用的扩展**——两者别混；
2. **插件只声明，不自动放行**——放行永远在应用清单里；
3. **符号进最终链接**——库写在清单 `[links]`，框架的 `cjpm.toml` 到不了那一层。
