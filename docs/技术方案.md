# 仓颉版 Tauri（cj-tauri）技术方案

> 现行版本：**2.2.0**（2026-11-12）｜初稿：2026-08-21（MVP 阶段，仅 Linux）
> 环境基线：仓颉 SDK **1.2.0** + stdx **1.2.0.1**；Linux WebKitGTK 4.1 / Windows WebView2 / 鸿蒙 ArkWeb
> 文档定位：讲**现在怎么做的、为什么这么分**。最初那份 MVP 方案与今天的偏离逐条列在 [§9](#九与原初稿的偏离)。

本文的事实基线：单测 349 用例全绿、C 桥桩自检 263 项断言、三端能力位取自各平台 `cj_plat_host_capabilities`。
数字与代码同轮核对，改动行为时请同步本文。

---

## 一、目标与现状

用仓颉语言实现 Tauri 形态的混合开发框架：**仓颉后端（静态编译）+ 系统 WebView 前端（HTML/CSS/JS）**，
三件套对齐——WebView 宿主（对应 tao/wry）、IPC 双向桥（invoke/resolve/event）、能力安全模型（capability 白名单）。

初稿只承诺 Linux 桌面端跑通、鸿蒙只留接口位；实际推进到今天的三端状态：

| 端 | 宿主 | 状态 | 宿主能力位（`CJ_CAP_*`） |
|---|---|---|---|
| Linux | WebKitGTK 4.1（C 桥） | 实机跑通 | MENU·DRAG_DROP·NOTIFICATION·HOTKEY·SUBTITLE（编译进托盘再置 TRAY） |
| Windows | WebView2（C 桥） | 实机跑通 | MENU·DRAG_DROP·NOTIFICATION·TRAY·HOTKEY（副标题那一行无自绘区，SUBTITLE 不置位） |
| 鸿蒙 | ArkWeb（宿主写在**仓颉侧**，不走 C 桥） | 真机闭环 | 仅 MENU（其余五项如实为 0） |

平台矩阵的验收判据与证据文件见 `docs/需求追踪.md`（`scripts/e2e-evidence.sh` 落 `dist/e2e-evidence/<平台>-<名字>.json`）。

## 二、总体架构

```
┌──────────────────────────────────────────────────────────┐
│ 前端 HTML/CSS/JS                                          │
│   window.__CJ_TAURI__.invoke / listen / emit              │
└───────────────┬──────────────────────────────────────────┘
                │ JSON 报文（宿主消息通道；桥 JS 在 document-start 注入）
┌───────────────▼──────────────────────────────────────────┐
│ 宿主层  src/host.cj（接口）+ 各平台实现                    │
│   host_webkit.cj │ host_webview2.cj │ host_arkweb.cj     │
└───────────────┬──────────────────────────────────────────┘
                │ foreign func（同名同签名，三端一致）
┌───────────────▼──────────────────────────────────────────┐
│ C 桥  native/core/bridge_core.c + bridge_js.h             │
│   native/platforms/{linux,windows,harmonyos}/   ← 唯一分叉点│
└───────────────┬──────────────────────────────────────────┘
┌───────────────▼──────────────────────────────────────────┐
│ IPC  src/ipc_hub.cj（校验在调用线程，命令 spawn 到 worker） │
│      src/ipc_message.cj（报文模型）                        │
└───────────────┬──────────────────────────────────────────┘
┌───────────────▼──────────────────────────────────────────┐
│ 能力模型  src/capability.cj（清单 + 命名权限集 + scope）    │
│           src/scope.cj（路径白名单判定）                    │
└───────────────┬──────────────────────────────────────────┘
┌───────────────▼──────────────────────────────────────────┐
│ 命令  src/api_system.cj（system:*） + src/plugins/<名字>/   │
└──────────────────────────────────────────────────────────┘
```

依赖方向单向：`app.cj` → `host.cj` / `ipc_hub.cj` → `capability.cj`，禁止反向与环。
平台差异**只允许出现在两处**：仓颉侧 `@When` 条件编译、C 桥 `native/platforms/*/bridge_*.c`；
IPC、能力校验、命令分发必须跨平台共用，上层不得散落运行期平台分支。

与 Tauri 的对应关系（现行）：

| Tauri 组件 | 本框架 | 说明 |
|---|---|---|
| WRY + TAO | `src/host.cj` + `native/platforms/*` | 接口在仓颉侧，平台实现在 C 桥 |
| IPC（invoke/event） | `src/ipc_hub.cj` + `src/ipc_message.cj` | 报文见 §3 |
| capability 能力模型 | `src/capability.cj` + `src/scope.cj` | 清单 + 命名权限集 + 路径 scope |
| tauri.conf.json | `cj-tauri.toml`（清单）+ `capabilities/*.json` | 新形态工程；旧形态走 `cjpm.toml`，双轨兼容 |
| @tauri-apps/api | 注入的 `__CJ_TAURI__` | 由 C 桥在 document-start 注入 |
| tauri-cli | `cli/`（仓颉原生 CLI） | `create` / `dev` / `build` / `run` / `info` / `doctor` / `check` / `sync` |
| plugins | `src/plugins/<名字>/` | 14 个官方插件，一个插件一个子包（§7） |

## 三、IPC 协议

报文是 JSON，经宿主消息通道双向投递。**`window` 字段是路由的关键**（多窗口）：

### 3.1 JS → 仓颉：invoke / emit

```json
{ "type": "invoke", "id": 1, "cmd": "greet", "args": { "name": "world" }, "window": "main" }
{ "type": "emit",   "id": 2, "event": "tick", "payload": { "n": 1 },        "window": "main" }
```

`window` 是发起窗口的 label；**缺省 / 非字符串 / 空串一律按 `"main"` 处理**——它决定命令上下文里
`ipc.window` 的取值，进而决定「这条命令该操作哪个窗口」。

### 3.2 仓颉 → JS：resolve / reject

```json
{ "type": "resolve", "id": 1, "ok": true,  "data": "hello world" }
{ "type": "resolve", "id": 1, "ok": false, "error": "command not allowed: greet" }
```

### 3.3 仓颉 → JS：event

```json
{ "type": "event", "protocol": "1", "event": "tick", "payload": { "n": 1 }, "window": "main" }
```

`window` **缺省 = 广播到所有窗口**，定向推送时给接收窗口的 label。前端 `__CJ_TAURI__` 用 Promise +
订阅表按 `id` / 事件名分发。

### 3.4 线程模型（与初稿最大的行为差别）

`IpcHub.handleInvoke` **只做校验**：「未授权 / 未注册」在调用线程上同步拒绝；通过校验的命令
`spawn` 到 worker 线程执行，结果经 `jsSink` 回投。

- 不要把 `handler.handle` 挪回调用线程——慢命令会钉住宿主 UI 线程（`shell:exec`、原生对话框最先遭殃）；
- worker 里也**只能**经 `jsSink` 回投，不要直接调 GTK / WebKit：仓颉轻量线程的堆上协程栈会被
  JSC 的栈边界校验 abort；
- 同一命令被并发调用**不保证执行顺序**，前端按 promise id 匹配；
- 命令抛异常要留 stderr（`command rejected (<命令>)` / `command failed (<命令>)`），否则「没反应」无凭证。

### 3.5 序列化

统一用 stdx 的 `stdx.encoding.json`（标准库无 `std.json`）。**初稿里自带的 `src/json.cj` 已移除**，
现在没有任何自研 JSON 解析器。

## 四、能力安全模型

清单放 `capabilities/*.json`，默认在 `run()` 时自动扫描工作目录下该目录；显式 `loadCapabilities(dir)`
或 `addCapabilityJson(json)` 优先，且一旦调用即不自动扫描。

```json
{
  "identifier": "default",
  "windows":  ["main"],
  "commands": ["greet", "system:version", "system:ping"],
  "events":   ["tick"],
  "permissions": ["fs:readonly"],
  "scopes": { "fs": { "allow": ["$HOME/notes/**"], "deny": ["**/id_rsa"] } }
}
```

- **`commands` / `events`**：未声明一律拒绝（默认最小权限），拒绝回 `error: command not allowed`；
  事件侧未声明不投递到页面。
- **`permissions`**：命名权限集（v1.1）。插件用 `Plugin.permissions()` 声明「短集名 → 成员」，框架装配时
  注册成 `<插件名>:<短集名>`；清单引用后成员展开，与明文写命令**同权**（单层展开、不递归）。
  **集声明 ≠ 放行**——清单不引用就不生效；引用到没人提供的集名只提示不报错。
- **`scopes`**：路径白名单（RFC-003 第 4 期）。**命令放行 ≠ 参数放行**：声明了 `scopeAware()` 的插件，
  在 handler 里对页面可控的路径参数调 `IpcContext.resolveScopedPath(插件名, 原文)`。语义是
  **先 deny 后 allow**（deny 命中即拒）、allow 必须显式命中（空 allow = 该插件路径全拒）、
  模式支持 `*` / `**` / `?` 与变量 `$HOME` / `$TEMP` / `$CWD`；匹配前规范化（存在走 `canonicalize`
  顺带解析软链接，不存在走词法折叠 `.` / `..`）。
- **运行期加白**：`TauriApp.allowScopePattern(plugin, pattern)` / `isScopeAllowed(...)`——只收**具体值**，
  带 `*` / `?` 或制表换行的当场拒绝（一个通配透传进来就等于全放行）。叠加只在内存、重启即空，
  **只应在取得用户明确确认之后调**（页面点不了原生确认框，被注入的脚本也就无法自行加白）。
- 没写 `scopes` 的旧清单行为不变（全量放行 + 启动打一行 stderr 提示），不破坏既有工程。

校验层独立于宿主实现，三端复用同一套。

## 五、宿主层

### 5.1 抽象接口 `src/host.cj`

初稿的 `create/run/loadHtml/runJs/destroy` 五件事已不够用。现行接口按「生命周期 + 预置类配置 + 运行期操作
+ 能力查询」分组，主要成员：

| 分组 | 成员（节选） |
|---|---|
| 生命周期 | `start` / `startUrl` / `run` / `loadHtml` / `runJs` / `dispose` |
| 注入 | `addInitScript`（桥 JS 与插件 shim 都走这条，document-start） |
| 预置类（必须赶在 `start`/`startUrl` 之前） | `setMenu` / `setDragDrop` / `setWindowVisible` / `setMinimizeToTray` |
| 运行期 | `setMenuItemState` / `runJs` / 事件回投 |
| 能力与数据 | `hostCapabilities` / `getCookies` / 原生对话框 / 剪贴板 |

默认窗经 `app.hostOf(DEFAULT_WINDOW_LABEL)` 拿宿主（实现对默认 label 有回落，`run()` 之前也拿得到）；
多窗口一律按 `ipc.window` 解析宿主，**固定一个宿主就是串台**。

### 5.2 C 桥契约

- 导出集中在 `native/core/bridge_core.c`，**三端同名同签名**（`cj_bridge_*`），平台分叉只在
  `cj_plat_*` 原语里（`native/platforms/<平台>/bridge_<平台>.c`）。
- 仓颉侧只声明 `foreign func`；**子包（单测）调不到 `foreign func`**，需要时在框架包内包一层。
- 宿主能力位是**纯静态事实**，由平台在 `cj_plat_init` 给出，`system:host` 如实上报，不许猜：
  `CJ_CAP_MENU`=1、`TRAY`=2、`DRAG_DROP`=4、`NOTIFICATION`=8、`HOTKEY`=16、`SUBTITLE`=32。
- 新增宿主能力：先扩 `WebViewHost` 接口 → 改各平台实现 → 桥加同名导出，最后才允许上层出现调用点。
- **宿主级回调一律在仓颉侧按句柄路由**（`HostGlobals.hostRoutes` + `registerHostRoute`），不要静态单槽：
  多窗口下后装配的会覆盖先装配的。唯一例外是消息回调（报文自带 window label，装同一只派发器）。
- 原生对话框/文件拖入这类「JS→native 回调本来就在宿主 UI 线程上」的路径，**不能投递+阻塞等结果**
  （自锁）：桥按调用线程分流，已在 UI 线程就直接弹。

### 5.3 Linux 实现要点

- GTK/WebKit 的全部调用必须在 C 桥创建的原生 pthread 内（仓颉 M:N 轻量线程的协程栈会被 JSC abort）。
- 桥接脚本必须**在 document start 注入**——文档末尾注入会晚于发行态内联的 `<script type="module">`。
- 收尾**不要 `pthread_join` 宿主线程**（与运行时停处理器握手互等，实测约 1/6 挂死）：`pthread_detach`
  + 有界轮询，等不到就保留平台状态（`cj_plat_fini` 返回 0 时 `cj_bridge_destroy` 不回收句柄）。
- 销毁 WebKit 窗口必须留在 `gtk_main` 之外（`quit` 只 `gtk_main_quit()`，窗口交给主循环返回后处理）。

### 5.4 Windows 实现要点

- 菜单栏必须 `CreateMenu()` 建（`SetMenu` 只吃菜单栏句柄，塞 popup 会 `ERROR_INVALID_PARAMETER(87)`
  静默失败）；凡「设了但没生效」的宿主调用一律**检查返回值 + 事后查询复核**打进同一行日志。
- WebView2 SDK **不得高于本机 Runtime**；`*CompletedHandler::Invoke` 的参数是**借用**，对它 `Release`
  会让运行时随后踩已释放内存（进程直接没，WER 记 `0xc0000005`）。
- 尺寸自检要放 `requestAnimationFrame` 循环里：建 WebView 时视口是临时尺寸且**不发 resize 事件**。

### 5.5 鸿蒙实现要点

- **框架包不得引用 ArkUI**：`@Component` / `Web` / `javaScriptProxy` 一律留在应用侧，框架只导出
  ArkUI-free 的桥接函数（`src/arkweb_proxy.cj`）。引用 `kit.ArkUI` 会让包初始化链跳到坏地址 → 启动即 SIGSEGV。
- **`javaScriptProxy` 的返回值传不回页面**，所以「页面拉、原生答」的同步取数模型不成立：回投一律
  **由原生推**——页面发 `{"type":"pull"}` 心跳，宿主直接 `return`（不进 IPC hub），应用侧 proxy 回调
  取 `takePendingScripts()` 用 `controller.runJavaScript` 推出去。
- 平台判据只能用 **`env`**（`aarch64-linux-ohos` → `ohos`）：鸿蒙的 `os` 取值就是 `"Linux"`，
  `arch` 与桌面 aarch64 撞车。
- 菜单能力位已真机取证：框架把 `MenuModel` 翻成扁平菜单，渲染在应用侧，点击经宿主回投 `menu:click`。
- **C 桥（`cj_core_*`）在鸿蒙侧仍未落地**，宿主由仓颉侧实现。

```

├── ipc_hub.cj / ipc_message.cj
├── capability.cj / capability_loader.cj / scope.cj / plugin.cj

└── tests/                 # 单测子包（package cjTauri.tests，可访问父包符号）

├── core/                  # bridge_core.c / bridge_core.h / bridge_js.h（跨平台共享，GTK-free）
├── platforms/{linux,windows,harmonyos}/
└── tests/test_bridge_core.c   # 桩平台自检，不依赖 SDK / 图形栈

cli/                       # 仓颉原生 CLI（不是脚本）
├── src/                   # create / dev / build / run / info / doctor / check / sync
└── templates/             # app（零 Node）/ app-vue / app-react / ohos-skeleton（sync 用，不是 create 模板）

examples/                  # 各示例自包含工程（旧形态）+ music-next 等新形态工程

```

三条容易被忽视的约定：

- **`src/` 根只放框架源码**：`cjpm` 不扫描顶层 `tests/` 目录，单测放出去会静默变成 0 个用例。
- **目录里没有 `.cj` 文件时 cjpm 不递归扫子目录**：`src/plugins/plugins.cj` 是空的扫描锚点。
- **新形态工程**的骨架由 `cj-tauri sync` 派生到 `targets/`，那是生成物——手改会被覆盖。

## 七、插件体系

插件是「宿主无关能力的打包单位」，当前 14 个：`clipboard` `dialog` `fs` `http` `log` `menu` `mqtt`
`notification` `redis` `serial` `shell` `sqlite` `store` `ws`。

**契约**（`src/plugin.cj`）：必写 `name()` + `commands()`；要推事件 / 前端 shim 再写 `events()` /
`jsShim()`；需要命名权限集写 `permissions()`；要吃路径限制写 `scopeAware()`。

**三处联动**（漏一处就用不了）：

1. 实现 `Plugin`；
2. `TauriApp().plugin(XxxPlugin())`——框架自动把命令注册成 `"<插件名>:<短名>"`；
3. 能力清单 `commands` 里声明 `"<插件名>:<短名>"`。

> `commands()` 返回的 map 键**必须写短名**，前缀由框架补。在键里再写一次会得到 `redis:redis:connect`，
> 日志只显示前缀重复，而所有命令都以 `command not registered` 告终。

**为什么一个插件一个子包**：仓颉的链接粒度是「包 = 静态库」。全挤在一个包里时，应用用任何一个插件都会
把整包对象拉进链接——只用 fs 的示例被 sqlite FFI 连坐、Windows 构建也要链 `-lsqlite3`。拆开后各插件独立成
`libcjTauri.plugins.<名字>.a`，没引用就不链接。代价是**插件之间不得互相引用**（会重新引入连坐），
共用工具进核心共享层（如 `src/hexutil.cj`）。

**前端 shim** 由 `Plugin.jsShim()` 收成「一个插件一段」，经 `addInitScript()` 在 document-start 注入
（排在桥 JS 之后）。不要再往 HTML 字符串里拼 `<script>`——`runUrl()` 的页面 HTML 不在本进程，那样永远拿不到。

**默认最小权限不破**：插件只声明「我提供什么」，不自动放行。

## 八、质量门禁

| 项 | 入口 | 当前结果 |
|---|---|---|
| 框架编译（零警告） | `cjpm build` | 通过；CLI / 示例各自再跑一次 |
| 仓颉单测 | `bash scripts/test.sh`（`src/tests/`） | **349/349** |
| C 桥桩自检 | `bash scripts/test-bridge-core.sh`（`native/tests/`） | **263 项断言**，不依赖 SDK / 图形栈 |
| 静态检查 | `bash scripts/check-static.sh` | **22 PASS / 0 FAIL**，不需要 SDK（CI 跑的就是它） |
| 版本六处一致 | `bash scripts/check-version.sh` | 全 `ok`（§9 的版本纪律） |
| 实机取证 | `bash scripts/e2e/run-all.sh` | 产出 `dist/e2e-evidence/<平台>-<名字>.json` |

两条判据纪律：

- **实机结论以桥的 stderr 日志为准**（窗口创建、`js -> native` 次数、`ExecuteScript -> hr=0x00000000`），
  自检全绿不等于交互没问题——布局缺陷只能抓图人眼验。
- **「日志里没有错误行」不等于成功**：页面没接 `catch` 时失败只在页面上可见，示例/插件仍应把 reject 也回投。

## 九、与原初稿的偏离

初稿（2026-08-21）是 MVP 阶段的设计基线，以下每一项都是实际做下来改的，**读旧版描述会误导**：

| 初稿说 | 现行做法 | 为什么改 / 代价 |
|---|---|---|
| 本次只交付 Linux，鸿蒙留接口位 | **三端都落地**：Windows 与 Linux 实机跑通，鸿蒙宿主真机闭环 | 预留位留不住真实约束，先把两端做出来才看得清抽象 |
| 鸿蒙用 `arkweb_cangjie_wrapper` 预留 `host/harmony.cj` | 宿主写**仓颉侧**（`host_arkweb.cj` + `arkweb_proxy.cj`），框架禁引 ArkUI；C 桥未落地 | 框架引用 `kit.ArkUI` 会让初始化链跳坏地址、启动即 SIGSEGV；`javaScriptProxy` 返回值传不回页面，改原生推 |
| 自带 `src/json.cj` 轻量 JSON | 全部改用 `stdx.encoding.json`，`json.cj` **已删除** | 自研解析器是不必要的维护面；代价是引入 stdx 依赖，且版配必须与 SDK 配套 |
| `src/ipc/`、`src/capability/`、`src/host/` 多级目录 | `src/` 扁平单层，插件单独子包 | 仓颉按「包 = 静态库」链接，目录层级不产生隔离，插件子包才产生 |
| 仓颉直绑 webkit2gtk（`webkit_ffi.cj` / `webkit_host.cj`） | 统一走 C 桥 `libcjtbridge`，仓颉只声明 `foreign func` | 平台差异收进 `native/platforms/*`；代价是多一层跨语言边界与构建步骤 |
| 平台分支靠 `@When(backend == "ohos")` | `@When[os == "Linux"/"Windows"]` + `@When[env == "ohos"]` | 鸿蒙的 `os` 就是 `"Linux"`、`arch` 与桌面 aarch64 撞车，只有 `env` 可靠 |
| 配置是 `app.json` / `cjpm.toml` | `cj-tauri.toml` 清单 + `capabilities/*.json`；旧形态 `cjpm.toml` 双轨兼容 | 新形态要支撑「一份代码多端」（骨架由 `sync` 派生到 `targets/`） |
| CLI 是 bash 脚本 `cli/cj-tauri` | 仓颉原生 CLI，8 个子命令（含 `doctor` / `sync`） | 跨平台（Windows 没有 bash）与行为一致性 |
| 单测放顶层 `tests/` | `src/tests/`（`package cjTauri.tests`） | `cjpm` 不扫顶层 `tests/`，放外面会静默变成 0 个用例 |
| 能力模型只有 `commands` / `events` | 追加**命名权限集** `permissions` 与**路径 scope** `scopes` + 运行期加白 | 「命令放行 ≠ 参数放行」：`fs:read` 放行了不等于能读任意路径 |
| （未涉及）命令在调用线程同步执行 | `handleInvoke` 只校验，命令 `spawn` 到 worker，结果经 `jsSink` 回投 | 慢命令会钉住宿主 UI 线程；代价是并发不保序，前端按 promise id 匹配 |
| （未涉及）托盘 / 快捷键 / 通知 | 均已落地并各自有平台能力位 | 平台有就置位、没有就如实降级（`tray=0` + 一行 stderr），不许假装成功 |

## 十、风险与对策（现行）

| 风险 | 现状与对策 |
|---|---|
| 仓颉 FFI 对 GObject 回调的边界 | 已由 C 桥封装吸收：GTK/WebKit 只在桥的原生 pthread 里调用 |
| 引入 stdx 依赖 | 版本必须与 SDK 配套（1.2.0 ↔ 1.2.0.1）；混配的症状是「编译链接全过、真机启动即崩」 |
| WebView2 SDK 高于本机 Runtime | 症状是窗口空白 / `ExecuteScript` 返 `0x8007139F`；SDK 由 `native/build_win.bat` 管理，换时同代 |
| 按名字 LoadLibrary 的组件 | `WebView2Loader.dll`（单文件包内嵌释放）、`libssl` / `libcrypto`：不在导入表里，漏了表现为「只有 https 全灭」 |
| 无显示 / 无 GPU 环境 | Xvfb 回落；注意 `DISPLAY` 存在 ≠ 可用（要真去连），`xvfb-run` 会把子进程 stderr 并进 stdout |
| 鸿蒙真机取证成本 | 已验证路径写进 `docs/鸿蒙ArkWeb接入踩坑.md`；诊断必须写 hilog（`eprintln` 在设备上不可见） |
| 鸿蒙读「别人授权的文件」不通 | 纯仓颉 hap 三条路全堵（权限 / picker 绑定 / `open` 仍 13900012），已登记为 `docs/需求追踪.md` PLT-005 并撤回实验通路，等官方 |
| 鸿蒙剪贴板读被权限挡住 | `READ_PASTEBOARD` 是 `SYSTEM_BASIC`，写进骨架会让所有生成的工程装不上；如实返回不可用 |
| 平台能力位谎报 | 铁律：平台有没有是静态事实，`system:host` 如实上报，缺一行 stderr 说明，不许「先报通过」 |
