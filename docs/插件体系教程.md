## 1. 插件是干嘛的

### 1.1 没有插件时，加一个能力要改三处

假设前端想读一个文本文件。按 §2 的老规矩（`AGENTS.md` 里叫「新增命令三处联动」），你得：

1. 写一个 `CommandHandler` 实现 `handle(cmd, args, ipc)`；
2. 在装配处 `app.register("read_text", ReadTextCommand())`；
3. 在 `capabilities/default.json` 的 `commands` 里加上 `"read_text"`。

漏第 3 步前端拿到 `command not allowed`，漏第 2 步拿到 `command not registered`。
功能没问题，问题是**每个应用都要重写一遍同样的代码**——读文件、弹对话框、查系统信息，
这些能力在几十个应用里长得一模一样，却没有地方可以共享。

### 1.2 插件把它收敛成一行

```cangjie
let app = TauriApp()
    .window(WindowConfig("我的应用", 900, 640))
    .plugin(FsPlugin())          // ← 就这一行
    .register("greet", GreetCommand())
```

一个**插件** = 一组命令 + 可选事件 + 可选前端 JS。这一行做完三件事：

- 把插件声明的命令按 `<插件名>:<短名>` 注册进 IPC 表（`fs:readText`、`fs:writeText`、`fs:exists`）；
- 把插件的前端 JS（`jsShim()`）合进页面，于是前端多了一个命名空间：`window.__CJ_TAURI__.fs.readText(...)`；
- 启动时打印已装配的插件清单，**逐条提示你还没放行哪些命令**。

所以插件的价值不在「能不能调用命令」——那早就能了；价值在**可分发**（第三方不用改框架源码）、
**自带说明**（前端知道有哪些 API、报错能说清缺哪条权限）、**装配一致**（一行注册，不是三处联动）。

### 1.3 插件**不**做什么（v1 的边界，先划清楚）

| 不做 | 说明 |
|---|---|
| **不自动放行权限** | 插件只声明「我提供什么」，能不能调用仍由应用的 `capabilities/*.json` 决定（§2.4 有取舍理由） |
| **不做动态加载** | 没有 `.dll` / `.so` 形式的插件，插件是**编译进应用**的仓颉包（v1 非目标） |
| **不碰桥的公共 API** | 插件的 `jsShim()` 只能挂 `window.__CJ_TAURI__.<插件名>`，不得覆盖 `invoke` / `listen` / `emit`，也不得注册全局变量 |
| **不覆盖所有能力** | v1 只管「命令 + 事件 + 前端 JS」。托盘、全局快捷键这类宿主级能力要等宿主层先有 API |
| **不做插件市场 / 热重载** | 装插件 = 改 `cjpm.toml` 依赖 + 加一行装配 + 重新编译 |

## 2. 概念与模型

### 2.1 命名空间：`<插件名>:<短名>`

插件名就是命令/事件的命名空间。以官方 `fs` 插件为例：

| 插件名 | 命令短名 | 前端调用 | 能力清单里写 |
|---|---|---|---|
| `fs` | `readText` | `__CJ_TAURI__.fs.readText({...})` | `"fs:readText"` |
| `fs` | `writeText` | `__CJ_TAURI__.fs.writeText({...})` | `"fs:writeText"` |
| `fs` | `exists` | `__CJ_TAURI__.fs.exists({...})` | `"fs:exists"` |

**为什么是这个形状**：内置命令叫 `system:version` / `system:ping`，插件命令全名与它**完全同形**。
`IpcHub` 的分发和 `CapabilityRegistry` 的校验都是按完整字符串精确匹配的，所以插件体系接上去
**零改动**——不需要给校验逻辑加「插件」这种概念。

三条命名规矩：

- 插件名**非空、且不含冒号**（半角 `:` 和全角 `：` 都不行）。冒号是命名空间分隔符，混进来
  `"<插件名>:<短名>"` 就无法解析；装配时会抛 `invalid plugin name: ...`。
- 插件名用**小写字母与数字**（约定，非强制），如 `fs`、`dialog`、`my_tools`。
- 应用自己的命令**可以没有冒号**（现状不变）。建议约定：`system:` 归框架、`<插件名>:` 归插件、
  无冒号归应用自身。

### 2.2 `Plugin` 接口：六个方法，只有两个必须写

```cangjie
public interface Plugin {
    public func name(): String                                        // 必写
    public func commands(): HashMap<String, CommandHandler>           // 必写
    public func events(): ArrayList<String> { ArrayList<String>() }   // 有默认实现
    public func jsShim(): String { "" }                               // 有默认实现
    public func setup(app: TauriApp): Unit {}                         // 有默认实现
    // v1.1：命名权限集，默认无集
    public func permissions(): HashMap<String, ArrayList<String>> { HashMap<String, ArrayList<String>>() }
}
```

| 方法 | 作用 | 不写会怎样 |
|---|---|---|
| `name()` | 插件名（命名空间） | 编译不过（必须实现） |
| `commands()` | 命令短名 → 处理器 | 编译不过（必须实现） |
| `events()` | 声明**可能推送**的事件短名，框架登记成 `<插件名>:<短名>` | 默认无事件（合法的空实现） |
| `jsShim()` | 返回前端 JS 片段，用来定义 `__CJ_TAURI__.<插件名>` | 默认空串：前端没有命名空间，只能自己 `invoke` |
| `setup(app)` | 初始化，拿到 `TauriApp` 引用做一次性准备（例如建定时器、记引用） | 默认什么都不做 |
| `permissions()` | 声明**命名权限集**（短集名 → 成员），应用可按 `<插件名>:<短集名>` 一次放行一组（§4.4） | 默认无集：应用只能按明文命令名逐条放行 |

> 仓颉接口**支持带默认实现的方法**——这条是本项目实测确认过的（RFC 开放问题 3 的答案），
> 所以不需要 `AbstractPlugin` 之类的基类，样板插件只写两个方法。

### 2.3 一次启动里，插件在什么时候被装配

时序很重要，因为它决定了「前端第一行能不能读到插件 API」：

```text
TauriApp().plugin(FsPlugin())          ← 只是记进内存（顺手校验插件名）
        ↓
app.run(html)
  └── prepare()
        1. 注册内置 system:version / ping / echo / devtools
        2. 加载 capabilities/（自动扫描，或你显式 addCapabilityJson / loadCapabilities）
        3. hub.setCapabilities(...)         ← 权限表定稿
        4. 逐个插件：registerPluginCommands(hub, p) → p.setup(app)
        5. assemblePluginJs(plugins)        ← 把各插件 jsShim 拼成一个 <script> 块
        6. 打印「已装配 N 个插件」+ 逐条未授权提示
  └── host.start(injectPluginJs(html, pluginJs))
        ← 把上面那个 <script> 插到第一个 </head> 之前
        ↓
     页面脚本执行             ← 此时 __CJ_TAURI__.fs 已经在了
```

两个结论：

1. **`.plugin(...)` 必须在 `run()` / `runUrl()` 之前调用**。页面加载前命令表要定稿；
   `prepare()` 之后再改就晚了（再调 `run()` 会直接抛 `app already started`）。
2. 命令行 `run(html)` 模式下，插件 JS 一定**早于页面脚本**（实测页面第一行读到 `window.__CJ_TAURI__.fs`
   为 `object`）。`runUrl()` 模式下 HTML 不在后端进程里，插不进 shim，框架会在 stderr 明确提示——见 §7。

### 2.4 为什么不自动放行（这条取舍值得理解）

| 做法 | 结果 |
|---|---|
| A. 插件自带 capability，装配时并入权限表 | 一行接入即可用；但第三方包**能一次性把权限全开了**，「默认最小权限」失效，审计时说不清哪条权限是谁开的 |
| B. 插件只声明「提供什么」，放行仍由应用的能力清单决定 | 最小权限与可审计性保住；代价是使用者写完 `plugin(...)` 还得去 JSON 里加一行 |

v1 选 **B**。理由：权限模型是这个框架区别于「随便一个 WebView 壳子」的地方，不能为了少写一行 JSON 让掉它。
为了把 B 的成本压到最低，框架做了两件事：

1. **启动检查 + 明确提示**（说清缺哪条、加到哪去，见 §3.5）；
2. 权限条目用**明文命令名**，简单、可审计、可 `grep`（不引入插件自带的 permission set）。

## 3. 快速上手：5 分钟接入官方 fs 插件

目标：应用里能读写文件、判断文件是否存在。**完整可跑版本**见 `examples/plugin-fs/`，本节按它的四步走。

### 3.1 第一步：加依赖（`cjpm.toml`）

插件和框架都在同一个仓颉包体系里，所以「装插件」就是加依赖（本地开发用 `path`，发布后用版本约束）：

```toml
[package]
  name = "my_app"
  version = "0.1.0"
  cjc-version = "1.0.5"
  output-type = "executable"

[dependencies]
  cjTauri = { path = "../.." }      # 你的应用相对框架仓库的位置
```

`fs` 插件是官方插件，与框架**同包**（`src/plugin_fs.cj`），所以这一个依赖就够了——
`import cjTauri.*` 之后 `FsPlugin` 直接可用。第三方插件将来是独立包，那就再多一行依赖。

### 3.2 第二步：装配（一行）

```cangjie
package my_app

import cjTauri.*

main(): Int64 {
    let html = String.fromUtf8(File.readFrom("ui/index.html"))   // 或内联 HTML，见 examples/hello
    TauriApp()
        .window(WindowConfig("我的应用", 900, 640))
        .plugin(FsPlugin())          // ← 插件体系：一行接入
        .run(html)
    return 0
}
```

### 3.3 第三步：放行你要用的命令（`capabilities/default.json`）

这是**唯一**必须手写的地方，也是这套设计刻意保留的「安全闸门」：

```json
{
  "identifier": "default",
  "windows": ["main"],
  "commands": ["report", "system:version"],
  "permissions": ["fs:readonly"],
  "events": []
}
```

放行有两种**等价**写法，可混用、并集生效：

- `permissions`：**集名**，由插件提供（`fs:readonly` = `fs:readText` + `fs:exists`，见 §4.4）；
- `commands`：**明文全名**（`fs:readText`，不是 `readText`），旧写法一直支持；上面这份里 `report` / `system:version`
  是应用自己的命令，与插件无关。

上面这份是 `examples/plugin-fs` 的真实清单：它有意**只放行只读那一组**、把 `fs:writeText` 留在外面——
用来演示「插件声明 ≠ 权限放行」（插件带了 `fs:default`，清单不引用就一条也不生效）。
你自己的应用按需增减；要用哪个命令就加哪个，不用就不加。

> 没放行不会静默失败：启动时框架会告诉你缺哪条、加到哪去（§3.5）。

### 3.4 第四步：前端调用（不用碰 `invoke`）

插件自带前端 shim，页面脚本**第一行**就能用：

```js
// 读文本（返回 Promise<string>）
const text = await window.__CJ_TAURI__.fs.readText({ path: 'capabilities/default.json' });

// 判断存在（返回 Promise<boolean>）
const ok = await window.__CJ_TAURI__.fs.exists({ path: 'ui/index.html' });
```

框架 API（`invoke` / `listen` / `emit`）一个没变，插件的命名空间只是**多挂了一个属性**。
不喜欢 shim 也可以直接 `window.__CJ_TAURI__.invoke('fs:readText', { path: 'a.txt' })`——两者等价。

### 3.5 跑起来应该看到什么（实测输出，可对照）

**后端 stderr**（启动时；注意最后那条是**故意的**未授权提示）：

```text
[cj-tauri] 已装配 1 个插件：
  fs  fs:readText, fs:writeText, fs:exists

[cj-tauri] 命名权限集（在 capabilities 的 permissions 里按集名引用）：
  fs:readonly  fs:readText, fs:exists
  fs:default  fs:readText, fs:writeText, fs:exists

[cj-tauri] 插件 fs 的命令 fs:writeText 尚未授权，前端调用会被拒绝
[cj-tauri]   请在 capabilities 目录的 json 里把 "fs:writeText" 加进 commands
```

注意 `fs:readText` / `fs:exists` **不再单独提示**——它们由清单引用的 `fs:readonly` 覆盖了。

**页面里**（`examples/plugin-fs` 的自检输出，Linux / WebKitGTK 实机）：

```text
shim-ready-at-script-start=true            ← 插件 shim 早于页面脚本（§2.3）
fs-namespace-type=object                   ← __CJ_TAURI__.fs 已就绪
fs:exists(capabilities/default.json) => true
fs:readText OK => 147 chars; 清单用集 fs:readonly=true; 清单未写死 fs:readText=true   ← 这次读全靠那个集
fs:exists(missing) => false
DENY-OK fs:writeText: command not allowed: fs:writeText     ← 未授权对照组，被拒才对
[verify] ALL DONE
```

把 `"fs:writeText"` 加进清单再跑，最后那条就会变成正常返回 `true`。

## 4. 官方插件 API 参考

框架随包带三个官方插件：**`fs`**（文件读写，`src/plugin_fs.cj`，纯仓颉、零 C 桥）、
**`dialog`**（系统原生对话框，`src/plugin_dialog.cj`，靠 C 桥）与 **`shell`**（交给系统默认程序打开 / 执行子进程，
`src/plugin_shell.cj`，纯仓颉、零 C 桥）。§4.1–§4.4 讲 `fs`，§4.5 讲 `dialog`，§4.6 讲 `shell`。

`fs` 的前端入口是 `window.__CJ_TAURI__.fs`。

| 命令 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `fs:readText` | `{ path: string }` | `string` | 读出文件内容并按 UTF-8 解码为字符串 |
| `fs:writeText` | `{ path: string, contents: string }` | `true` | **覆盖写**：文件已存在则**截断重写**，不存在则创建（不追加、不备份） |
| `fs:exists` | `{ path: string }` | `true` / `false` | 路径是否存在（底层 `std.fs.exists`） |

### 4.1 路径怎么解析

用的是 `std.fs` 的原始路径语义，**相对路径按进程的当前工作目录解析**。
本框架的约定是「工作目录 = 项目根」（`capabilities/`、`ui/` 都按相对路径读），
所以 `{ path: "ui/index.html" }` 指的就是项目根下的 `ui/index.html`。
用绝对路径也可以。写文件时注意父目录必须已存在——`fs:writeText` 只写文件，**不建目录**。

### 4.2 会失败在哪（错误原文可直接展示给用户）

| 前端 `catch` 到的 `err.message` | 触发条件 |
|---|---|
| `command not registered: fs:xxx` | 插件没装配（忘了 `.plugin(FsPlugin())`），或命令短名拼错 |
| `command not allowed: fs:writeText` | 装配了但能力清单没放行这条命令 |
| `fs: missing argument "path"` | 参数没传（漏了 `path`，或漏了 `contents`） |
| `fs: argument "path" must be a string` | 参数传了但类型不对（例如传了数字或对象） |
| `fs:readText failed: ...` | 文件不存在、没权限、或内容不是合法 UTF-8 |
| `fs:writeText failed: ...` | 父目录不存在、磁盘只读、没权限 |

约定：插件的错误一律以 `CommandException` 抛出，**原文透传到前端**（`err.message` 就是后端那句话），
所以前端可以直接把消息显示出来，不需要自己翻译错误码。

### 4.3 想读二进制怎么办

v1 没有对应的命令（`readText` 只处理文本）。二进制读写属于「以后加进 `FsPlugin` 的新命令」，
加的时候按 §5 写命令、按 §3.3 放行即可——**已有的 `fs:readText` 放行不会自动扩散到新命令**。

### 4.4 命名权限集（v1.1）

插件可以成组发布权限，应用按集名一次引用（对标 Tauri v2 的 `fs:default`）：

| 集名 | 成员 | 用途 |
|---|---|---|
| `fs:readonly` | `fs:readText`、`fs:exists` | 只读：明确不含写 |
| `fs:default` | `fs:readText`、`fs:writeText`、`fs:exists` | 全量（含覆盖写） |

清单里写 `"permissions": ["fs:readonly"]` 与逐条写 `"commands": ["fs:readText", "fs:exists"]` **完全等价**，
两种写法可混用、并集生效（旧清单不用改）。

三条规则：

1. **集声明 ≠ 放行**：插件带了 `fs:default`，清单不引用它，`fs:writeText` 照样被拒——
   集只是「一次写多条」的语法糖，安全闸门还在清单手里；
2. **短名自动补前缀**：插件 `permissions()` 里写 `readText`，登记的就是 `fs:readText`；写全名（如 `fs:changed`）原样保留。
   集名同理——短集名 `readonly` 登记成 `fs:readonly`；
3. **未知集只提示不报错**：清单引用了没有插件提供的集名（拼错、或忘了 `.plugin(FsPlugin())`），
   启动打印 `[cj-tauri] 未知的命名权限集 "fs:readonlyy"：没有插件提供它，这一条不生效`，
   其它已写明的权限不受影响。

自己写插件时怎么声明集：见 §5.5。

### 4.5 官方 dialog 插件（系统原生对话框）

实现：`src/plugin_dialog.cj` + 两平台 C 桥（`native/bridge_linux.c` / `native/bridge_win.c`）。
前端入口：`window.__CJ_TAURI__.dialog`。一行接入：

```cangjie
let app = TauriApp()
    .window(WindowConfig("我的应用", 1000, 700))
    .plugin(DialogPlugin())
    .register("greet", GreetCommand())
```

| 命令 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `dialog:open` | `{ title?, filter? }` | `string` | 选一个已有文件；**取消返回空串 `""`** |
| `dialog:save` | `{ title?, filter? }` | `string` | 选保存路径（目标已存在会问是否覆盖）；取消返回 `""` |
| `dialog:message` | `{ kind?, title?, message }` | `true` / `false` | `kind` 取 `info`（默认）/ `warning` / `error` / `confirm`；`confirm` 点取消 → `false`，其余 → `true` |

`filter` 是「显示名:通配」串（Windows 与 GTK 的过滤串语法一致），例如
`"文本文件:*.txt;*.md;所有文件:*.*"`；不传则不限类型。**弹的是系统原生对话框**——Linux 走 GTK
（`GtkFileChooserDialog` / `GtkMessageDialog`），Windows 走 Win32 通用对话框
（`GetOpenFileNameW` / `GetSaveFileNameW` / `MessageBoxW`），不是网页里画的 div。

命名权限集（与 `fs` 一样**不自动放行**，清单引用才生效）：

| 集名 | 成员 | 用途 |
|---|---|---|
| `dialog:files` | `dialog:open`、`dialog:save` | 只要挑文件 |
| `dialog:default` | 上面两条 + `dialog:message` | 全量（含弹提示框） |

清单写法与 §4.4 一致：`"permissions": ["dialog:files"]`，或逐条写 `"commands": ["dialog:open"]`，两种可混用。
**只想挑文件的应用别引用 `dialog:default`**——「弹一个标题与正文都可控的模态框」的能力会一并给出。

一个**实机踩到过的坑**（改宿主代码时注意）：两平台的 JS→native 回调**本来就跑在宿主 UI 线程上**
（Linux = GTK 线程，Windows = 跑 WebView2 消息循环的那个线程）。所以对话框**不能**一律「投递到 UI 线程 +
阻塞等结果」——UI 线程正卡在这次调用里，投递进去的任务永远轮不到执行；现象是日志停在
`[cj-bridge] dialog: kind=…`、对话框永不出现。C 桥按调用线程分流：已在 UI 线程就直接弹，在别的线程才投递 + 等待。

可跑样板：`examples/plugin-dialog/`（三个按钮 + 启动后自动依次弹窗自检）；实机日志形如
`dialog: kind=2 title=… (caller on GTK thread)` → `dialog closed: kind=2 ok=1` →
`dialog:open => path="/tmp/dialog-pick.txt"`。

### 4.6 官方 shell 插件（交给系统默认程序 / 执行子进程）

实现：`src/plugin_shell.cj`——**纯仓颉、零 C 桥**（进程 API 来自 `std.process`，平台差异只在 `@When` 里选
`xdg-open` / `rundll32`）。前端入口：`window.__CJ_TAURI__.shell`。一行接入：

```cangjie
let app = TauriApp()
    .window(WindowConfig("我的应用", 1000, 700))
    .plugin(ShellPlugin())
    .register("greet", GreetCommand())
```

| 命令 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `shell:open` | `{ target }` | `true` | 把 URL 或本地路径交给系统默认程序（Linux `xdg-open`；Windows `rundll32 url.dll,FileProtocolHandler`，等价于 ShellExecute 且**不必**经过 `cmd /c start`） |
| `shell:exec` | `{ program, args?, cwd? }` | `{ code, stdout, stderr }` | 跑一个程序并回收结果；`code` 是退出码，两个流各截到 256 KiB（超出会标注），非 UTF-8 退化成摘要 |

**先想清楚再放行**：`shell:exec` 放行出去，就等于页面能跑**任意程序**——能力清单是唯一的闸门（v1 没有
「程序白名单」这种 scope）。只需要「点链接用浏览器打开」的应用引用 `shell:allow-open` 就够了：

| 集名 | 成员 | 用途 |
|---|---|---|
| `shell:allow-open` | `shell:open` | 只想打开链接 / 文件 |
| `shell:default` | 上面那条 + `shell:exec` | 全量（含执行子进程） |

也不必担心命令注入：框架**不经过 shell**，`program` 与每个参数都是独立 argv 元素直传子进程，参数里的
空格、引号、`&&`、`>` 都只是普通字符——`args: ["a b", "&&", "echo INJECTED"]` 的输出就是字面量
`a b && echo INJECTED`。反过来说，别在 `args` 里塞 `"-c"` 再拼一整串命令交给 `bash`：那等于自己把 shell 请回来。

一个**限制**（改这个插件前先看 RFC §8 第 8 条）：`shell:exec` 是同步阻塞的，而 IPC 处理器跑在宿主 UI 线程上，
所以子进程不退出，窗口就不重绘。长驻 / 交互式程序（编辑器、REPL、`npm run dev`）不要走它。

可跑样板：`examples/plugin-shell/`（五个按钮 + 启动后自动自检，清单刻意混用命名集与明文两种写法）；实机日志形如
`shell:open(url) => true` → `shell:exec(uname) => code=0 stdout=Linux …` → `shell:exec(exit7) => code=7 stderr=to-stderr`。

## 5. 自己写一个插件

写插件 = 实现 `Plugin` 接口 + 写一个（或多个）`CommandHandler`。本节从最小可跑的 `greet` 插件开始，
再加事件与 `setup`，最后讲怎么打包给别的应用用。
（§5.1 / §5.2 的两段样例都在 0.4.0 上**实际编译通过**（`cjpm build success`），可以直接抄。）

### 5.1 最小可跑：`greet` 插件（完整代码）

放在应用自己的包里最简单（比如 `src/greet_plugin.cj`）：

```cangjie
package my_app

import cjTauri.*
import std.collection.*
import stdx.encoding.json.*

class GreetCommands <: CommandHandler {
    public init() {}

    public func handle(cmd: String, args: JsonObject, ipc: IpcContext): JsonValue {
        var who = "world"
        if (let Some(v) <- args.get("name")) {
            match (v.kind()) {
                case JsonKind.JsString => who = v.asString().getValue()
                case _ => ()
            }
        }
        return JsonString("Hello, ${who}! 来自仓颉后端")
    }
}

public class GreetPlugin <: Plugin {
    public init() {}

    // 插件名：命令会变成 greet:hello
    public func name(): String { return "greet" }

    // 命令短名 → 处理器（框架自动补 "greet:" 前缀）
    public func commands(): HashMap<String, CommandHandler> {
        let m = HashMap<String, CommandHandler>()
        m.add("hello", GreetCommands())
        return m
    }

    // 前端 shim：只往 __CJ_TAURI__ 上挂一个命名空间，别碰 invoke/listen/emit
    public func jsShim(): String {
        return "(function () { var t = window.__CJ_TAURI__;" +
            " t.greet = { hello: function (a) { return t.invoke('greet:hello', a); } }; })();"
    }
}
```

装配与放行（**三处联动**，与「新增命令」那套一一对应，只是前两步被插件包办了）：

```cangjie
TauriApp()
    .window(WindowConfig("我的应用", 900, 640))
    .plugin(GreetPlugin())          // ① 装配（原来要 app.register(...)）
    .run(html)
```

```json
{
  "identifier": "default",
  "windows": ["main"],
  "commands": ["greet:hello"],     // ② 放行全名（这一步插件替不了你）
  "events": []
}
```

前端：

```js
const msg = await window.__CJ_TAURI__.greet.hello({ name: '仓颉' });
// → "Hello, 仓颉! 来自仓颉后端"
```

### 5.2 进阶：事件与 `setup`

如果插件会**主动推事件**给前端（例如「文件变了」「计时器到点」），做两件事：

1. `events()` 里声明事件短名——框架登记成 `<插件名>:<短名>`，并据此在启动时提示你有没有放行；
2. `setup(app)` 里记住 `TauriApp` 引用，之后任何地方都能 `app.emit(全名, payload)`；
3. 记得在能力清单的 `events` 里放行（和命令一样，**不自动放行**；没放行事件会被丢弃）。

```cangjie
public class CounterPlugin <: Plugin {
    private var app: Option<TauriApp> = None

    public init() {}

    public func name(): String { return "counter" }

    public func commands(): HashMap<String, CommandHandler> {
        let m = HashMap<String, CommandHandler>()
        m.add("tick", CounterCommands())        // counter:tick
        return m
    }

    // 声明「我可能推 counter:count」——启动时会检查这一条有没有放行
    public func events(): ArrayList<String> {
        let e = ArrayList<String>()
        e.add("count")
        return e
    }

    public func setup(app: TauriApp): Unit {
        this.app = Some(app)                    // 记引用，供下面推事件用
    }

    /** 在命令处理器里调用（示意）：往前端推一个事件 */
    func notify(n: Int64): Unit {
        match (this.app) {
            case Some(a) => a.emit("counter:count", JsonInt(n))
            case None => ()
        }
    }
}
```

对应能力清单：

```json
{
  "identifier": "default",
  "windows": ["main"],
  "commands": ["counter:tick"],
  "events": ["counter:count"]
}
```

前端收事件，用桥的 `listen`（订阅插件事件和订阅普通事件**完全一样**）：

```js
const off = window.__CJ_TAURI__.listen('counter:count', n => console.log('count =', n));
// 需要时取消订阅：off();
```

### 5.3 打包成独立包，给别的应用复用

这才是插件体系的正经用法（第三方不用改框架源码）。插件包的 `cjpm.toml` 只比普通包多一行依赖：

```toml
[package]
  name = "cj_tauri_plugin_dialog"
  version = "0.1.0"
  cjc-version = "1.0.5"
  output-type = "static"            # 被别的应用依赖，不做可执行文件

[dependencies]
  cjTauri = { path = "../cj-tauri" }   # 或发布后的版本约束
```

包名（`name`）与仓颉的 `package` 声明不必同名，但导入时用的是 `package` 名。
使用方应用：`[dependencies]` 里同时加框架和插件包，然后 `import cj_tauri_plugin_dialog.*` 再 `.plugin(DialogPlugin())`。
插件的**链接选项不在插件包里**——C 桥的 `link-option` 由最终可执行文件负责（照抄模板的 `[target.*]` 段）。

### 5.4 写 `jsShim()` 的三条纪律

1. **只挂自己的命名空间**：`window.__CJ_TAURI__.<插件名>`。覆盖 `invoke` / `listen` / `emit`、
   或注册全局变量，都会污染其他插件与框架本身。
2. **只走 `__CJ_TAURI__.invoke('<插件名>:<命令短名>', args)`**，返回 `Promise`，**不要吞异常**——
   让 `err.message` 保持后端原文，前端才能把「缺哪条权限」直接显示出来
   （参照 `FsPlugin` 的写法：`readText: function (args) { return window.__CJ_TAURI__.invoke('fs:readText', args); }`）。
3. **字符串里别出现反斜杠**（本项目实测踩过的坑）：shim 通常写在仓颉的字符串里，
   而仓颉会先处理一遍反斜杠转义——写 `\n` 会变成**真换行**，把 JS 拆断成语法错误，
   页面一行都不执行而且 stderr 毫无提示。两个办法：
   - 用 `+` 把 shim 拆成多段短字符串（`FsPlugin` 就是这么写的，读起来也清楚）；
   - 换行用 `String.fromCharCode(10)` 现算，正则改用 `indexOf`。
   写完拿 `node --check` 过一遍最稳。

### 5.5 声明命名权限集（v1.1，可选）

命令多了以后，使用者逐个放行很啰嗦，插件可以把它们打包成「集」：

```cangjie
public func permissions(): HashMap<String, ArrayList<String>> {
    let m = HashMap<String, ArrayList<String>>()
    let ro = ArrayList<String>()      // 只读集
    ro.add("readText")                // 短名 → 自动补成 greet:readText
    ro.add("exists")
    m.add("readonly", ro)             // 集名 → greet:readonly
    return m
}
```

应用清单里就能写 `"permissions": ["greet:readonly"]`，一次放行两条。

三条设计约定（照抄即可）：

1. **短名补前缀、全名原样**：成员写 `readText` → `greet:readText`；写全名（如 `greet:changed`）原样保留——
   事件也能进集，集内成员按名字同时参与命令与事件的放行判定；
2. **集不自动放行**：注册的集只有被应用清单引用才生效。插件作者**不需要（也无法）**替使用者开权限，
   与「插件只声明提供什么」的立场一致；
3. **集名用短词**：框架会补上插件前缀（`readonly` → `greet:readonly`），与 Tauri v2 的 `fs:default` 命名习惯一致。

> `readonly` 与 `default` **分开列**，想只读的人就不会连带拿到写权限——`FsPlugin` 就是这么定的。
> 集只是应用侧写法的简写，不构成新的安全边界：闸门始终是「清单里引用了没有」。

## 6. 排错：按现象查

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 启动打印 `插件 fs 的命令 fs:writeText 尚未授权` | 能力清单没放行这条命令（**这是提示不是错误**） | 把 `"fs:writeText"` 加进 `capabilities/*.json` 的 `commands` |
| 前端 `catch` 到 `command not allowed: fs:writeText` | 同上，运行时被闸门拦下 | 同上；只放你需要的那条，别图省事全放 |
| 前端 `catch` 到 `command not registered: fs:readText` | 插件没装配（忘了 `.plugin(FsPlugin())`），或命令短名拼错 | 检查装配那一行；命令短名大小写敏感（`readText` ≠ `readtext`） |
| 启动时 `invalid plugin name: "fs:x"` | 插件名里带了冒号 | 插件名只用字母数字下划线，冒号是命名空间分隔符 |
| 启动打印 `未知的命名权限集 "fs:readonlyy"` | 清单 `permissions` 里的集名拼错，或提供它的插件没装配（**提示不是错误**，这一条不生效） | 对着启动打印的可用集清单改拼写；忘了装配就补 `.plugin(FsPlugin())` |
| 引用了 `fs:default` 后 `fs:writeText` 就能用了，想收窄 | 集是「一次放行一组」，`fs:default` 含 `fs:writeText` | 换成 `fs:readonly`，或回退到明文逐条写 `commands` |
| 清单里写了集名，但启动没打印「命名权限集」那段 | 没有任何插件声明集（`permissions()` 默认返回空），该行只在有集时打印 | 正常现象；确认插件是否声明了集（`fs` 插件自带两个） |
| `__CJ_TAURI__.fs` 是 `undefined`，但 `__CJ_TAURI__` 在 | shim 没进页面（`runUrl` 模式，或 HTML 里没有 `</head>`） | 见下面「典型场景 1」 |
| `__CJ_TAURI__` 本身是 `undefined` | 桥还没就绪（页面脚本跑得比桥早，或模块作用域直接读） | 用 `waitForBridge` 等桥；桥的注入时机见使用文档 §7 的踩坑条目 |
| 页面完全白屏、一行 JS 都不跑 | 内联 JS 里有反斜杠转义被仓颉吃掉，整段脚本语法错误 | 见 §5.4 第 3 条；抽出脚本用 `node --check` 验 |
| 装了两个插件后其中一边 API 不见了 | shim 覆盖了别人（写了 `t.invoke = ...` 之类） | shim 只挂 `__CJ_TAURI__.<自己的插件名>` |
| `app already started` | 在 `run()` 之后又调 `.plugin(...)` / `.register(...)` | 所有装配必须写在 `run()` / `runUrl()` 之前 |

### 典型场景 1：`__CJ_TAURI__.fs` 是 `undefined`

按页面来源分两种情况：

- **`app.run(html)`（内联 HTML / 读文件后再 run）**：插件 shim 会被插到第一个 `</head>` 之前。
  如果你的 HTML 没有 `</head>`，框架会退化成「插到文档最前」，同时在 stderr 打印
  `[cj-tauri] HTML 里没有 </head>，插件 JS 已插到文档最前`——看到这行就补上 `</head>`。
- **`app.runUrl(url)`（dev server / 远程页面）**：HTML 不在后端进程里，框架**没法**把 shim 并进去，
  会打印 `runUrl 模式：插件 JS 无法随 HTML 注入`。此时请像脚手架模板那样等桥出现再调用：

  ```js
  function waitForBridge(cb) {
    if (window.__CJ_TAURI__ && window.__CJ_TAURI__.fs) { cb(); return; }
    setTimeout(() => waitForBridge(cb), 50);
  }
  ```

  这是 v1 的已知局限（设计见 RFC-001 §5.4），v2 计划改成宿主层「预执行脚本列表」。
- **Vue / React 应用**：别在模块作用域直接读桥（那时可能还没就绪），放到 `onMounted` / `useEffect` 里，
  或先过一遍 `waitForBridge`。

### 典型场景 2：想确认「到底装了哪些插件、哪些没放行」

不用猜——启动日志就是清单。也可以自己核对：命令全名是 `<插件名>:<短名>`，
拿它去 `capabilities/*.json` 的 `commands` 里 `grep` 一下有没有同名条目（**精确匹配**，不支持通配）。
框架侧对应的判定函数是 `CapabilityRegistry.canInvoke(name)` / `canEmit(name)`，插件装配时用的就是它们。

### 典型场景 3：加了插件后，老应用行为变了？

不该变。插件体系是**纯新增 API**：`register()` / `Capability` / `capabilities/*.json` 语义都没动，
不调用 `.plugin(...)` 的应用与以前完全一致（`examples/hello`、脚手架模板工程都未改动即通过回归）。

## 7. 与 Tauri v2 插件模型的对照

| 维度 | Tauri v2 | cj-tauri v1 |
|---|---|---|
| 插件本体 | Rust crate + 可选 JS 包 | 仓颉包（`Plugin` 实现），与框架同包或独立 `cjpm` 依赖 |
| 前端入口 | 插件自带 JS 包，`import { readText } from '@tauri-apps/plugin-fs'` | 插件用 `jsShim()` 返回片段，框架注入后是 `__CJ_TAURI__.fs.readText(...)`（零构建，不用 npm 包） |
| 命令命名 | `plugin:fs\|read_text` | `fs:readText`（与内置 `system:*` 同形） |
| 权限 | 插件发布 **permission set**，应用 capability 里引用 `"permissions": ["fs:default"]` | 同样支持：插件用 `permissions()` 声明集，应用清单里写 `"permissions": ["fs:readonly"]`（v1.1 起）；明文命令名依旧可用，两者等价、可混用 |
| 加载方式 | 编译期依赖（v2 也没有 .dll/.so 动态插件） | 同样是编译期依赖 |
| 缺权限报错 | 运行时报错 | 启动即提示「缺哪条、加到哪」+ 运行时 `command not allowed` |
| 分发 | crates.io / npm | 仓颉包依赖（v1 官方插件与框架同仓同版本） |

一句话：**架构意图一致（声明式接入 + 显式授权），实现按仓颉生态做了减法**——
没有 JS 包构建链路，shim 直接由后端注入；权限集用「插件 `permissions()` 声明 + 应用按集名引用」对齐
Tauri v2 的 permission set（v1.1 起），同时保留可 `grep` 的明文命令名（两者等价）。

## 8. 路线与版本策略

已落地：

- **命名权限集**（v1.1，2026-10-02）：插件 `permissions()` 声明集，应用清单写 `"permissions": ["fs:readonly"]`
  一次放行一组，与明文命令名等价、可混用——见 §4.4 与 §5.5（RFC 开放问题 2 的 v1.1 答案）。

已规划（不承诺顺序，见 `docs/进度记录.md` 的「下一步」）：

- **更多官方插件**：`fs` / `dialog` / `shell` 已落地（见 §4），下一批（托盘、全局快捷键等）要等宿主层先有对应
  API——按 §5 的模板写，照 `AGENTS.md` §2 的「新增插件三处联动」落地；
- **宿主层预执行脚本列表**：替掉现在「往 HTML 字符串里插 shim」的做法，`runUrl` 模式也能保证时序（RFC §5.4）；
- **插件清单机器可读**：让 `cj-tauri info` 打印已装配插件、甚至生成能力清单片段给你粘贴（RFC 开放问题 7）；
- **非命令类能力**（托盘、全局快捷键、协议处理）：需要宿主层先有对应 API，再进 `Plugin` 模型。

版本策略：**插件接口在 1.0 之前属于 experimental，可能调整**。若发生破坏性变更，会走次版本号（0.x 的 minor）
并在 `CHANGELOG.md` 的 `Changed` 段写明；官方插件与框架同仓、同版本号，一起改。
