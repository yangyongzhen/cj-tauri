# 架构演进：多平台与多窗口的地基准备

> 适用版本：0.4.0（2026-10-02）。这是一次**架构评审的结论**，不是已落地改动的记录——
> 文中的「批次 1 / 批次 2」**尚未实施**，代码即当前 0.4.0 现状。
> 评审范围：已实现的两个平台后端（Linux WebKitGTK、Windows WebView2）与仓颉侧宿主层
> （`src/host.cj`、`src/host_webkit.cj`、`src/host_webview2.cj`、`src/window.cj`、`src/app.cj`、`src/ipc_hub.cj`）。
> 架构契约见 `AGENTS.md` §2，IPC 选型与实测见 `docs/IPC-通信机制.md`。

## 0. 结论摘要

1. **平台相关部分的手写不可消除**——Tauri 亦然（wry 内部就是每个平台一个模块）。问题不是「要不要手写」，而是「手写的比例」。
2. 当前骨架把**本可共享的三块**做成了每平台一份：C 侧的队列 / 批处理 / 对话框状态机 / 注册表 / 配置存储（约 300–400 行 ×2 份），以及仓颉侧 `prepareHost()` 这类**逐字节重复**的装配逻辑。
3. **必须现在动的一处**：C 桥 ABI 是进程级单例，15 个 `cj_bridge_*` 全无句柄参数。这是唯一「越晚越贵」的项。
4. 另两处（共享 C 核心、仓颉侧窗口注册表与能力分层）应与第 3 点**同刀切**——分两次做要动两遍。
5. **菜单 / 托盘 / 拖放的实现现在不写**：没有第二个平台来验证抽象，写了就是猜；现在只定「模型 + 能力位」。

## 1. 现状盘点

### 1.1 已经共享的（保持现状即可）

| 层 | 证据 |
|---|---|
| 页面侧桥 JS | `native/bridge_js.h`（100 行）单源，两平台只差 `CJ_LIT`、post 语句、reload 语句三处 |
| IPC 协议、报文解析 | `src/ipc_message.cj` |
| 命令分发、事件路由 | `src/ipc_hub.cj`（`handleRawMessage` / `dispatchEvent` / `emitToWindow`） |
| 能力安全模型 | `src/capability.cj` + `src/capability_loader.cj` |
| 装配与注册表 | `src/app.cj`（`register` / `run` / 插件加载） |
| 窗口配置模型 | `src/window.cj`（`WindowConfig`，纯数据） |

这一层是三件套里最值钱的部分，**新增平台一行不用改**——这正是 `AGENTS.md` §2 那条「平台差异只许出现在 `@When` 与 `bridge_*.c`」的收益。

### 1.2 重复实现的（应下沉到共享层）

| 逻辑 | Linux 位置 | Windows 位置 |
|---|---|---|
| pending-JS FIFO + 批处理 + 快路径 | `bridge_linux.c:446-489`（`flush_pending_js`、`CJ_JS_BATCH_MAX`） | `bridge_win.c:549+`（`flush_js`、同名常量） |
| `cj_bridge_run_js` 入队尾部 | `bridge_linux.c:491` | `bridge_win.c:879-913` |
| 对话框请求结构体 + 单槽状态机 | `dlg_req` `:167`、`g_dlg_busy` `:178`、`cj_bridge_show_dialog` `:333-404` | `dlg_req` `:360`、`g_dlg_busy` `:372`、`:938+` |
| init-script 注册表 | `:59-61`（`g_init_scripts` / `_count` / `_cap`）、`:89` | `:83-85`、`:808` |
| 配置 setter 存储 | `set_window` `:407`、`set_icon` `:71`、`set_devtools` `:81` | `:773` / `:788` / `:800` |
| 生命周期标志与 reload 常量 | `g_ready` / `g_should_quit` `:46-47`、`CJT_RELOAD_MSG` `:37` | `:49-50`、`:304` |
| **仓颉侧 `prepareHost()`** | `host_webkit.cj:146-167` | `host_webview2.cj:147-168`（**逐字节相同**） |
| 仓颉侧对话框 / 消息回调转发 | `host_webkit.cj` | `host_webview2.cj` |

按行数估：两个 C 文件里**约 35–45% 是无平台色彩的搬箱子逻辑**，却各有各的 bug 面（`n > 0` 静默丢单条消息那个坑就是这么来的——修一份不会自动修另一份）。

### 1.3 真正平台相关的（必须手写）

| 内容 | 位置 | 性质 |
|---|---|---|
| GTK 窗口 + WebKitGTK 装配、`gtk_main` 事件循环 | `bridge_linux.c:562-638`（`gtk_thread_main`） | 平台特有，不可复用 |
| Win32 窗口类 + 消息循环 + WebView2 COM 环境 | `bridge_win.c:638-750`（`host_thread_main`） | 平台特有，不可复用 |
| COM 事件处理器（env / ctrl / msg / nav 四组 vtbl） | `bridge_win.c:122-353` | 平台特有 |
| 原生对话框（GTK / Win32 对话框） | `bridge_linux.c:248`、`bridge_win.c:416` | 平台特有 |
| 字符串编码转换（`utf8_to_wide` / `wide_to_utf8`） | `bridge_win.c:89,99` | 平台特有 |

**关键观察**：这一栏里真正「必须有平台实现」的**只有 5–8 个原语**（投脚本、唤醒 UI 线程、判 UI 线程、弹原生对话框、应用窗口配置、建销原生窗口）。其余都是装配细节，天然跟着平台走、也不该被抽象掉。

## 2. 三处地基缺陷

### 2.1 A（必须现在动）：C 桥 ABI 是进程级单例，没有句柄

**证据**：

- 15 个导出函数**全部没有**窗口/宿主句柄参数（两平台一致）：`cj_bridge_init` / `set_window` / `set_icon` / `set_devtools` / `add_init_script` / `open_devtools` / `load_url` / `reload` / `start` / `run_js` / `quit` / `is_ready` / `should_quit` / `set_dialog_callback` / `show_dialog`。
- Linux 侧单例：`g_window` `bridge_linux.c:29`、`g_view` `:30`；唯一一条 `g_idle_add` 刷新队列 `:446-489`；对话框单槽 `g_dlg_cur` `:180`；`g_gtk_thread` `:181` 单标量。
- Windows 侧单例：`g_hwnd` `bridge_win.c:42`、`g_controller` `:43`、`g_environment` `:44`、`g_webview` `:45`；`WM_CJT_FLUSH` 经 `PostMessageW(g_hwnd, …)` `:610,627` **不带窗口 id**；`wnd_proc` `:490` 没有 per-window `GWLP_USERDATA`；`g_host_thread_id` `:373` 单标量。
- COM 处理器是 4 个**静态单例对象**（`:130-133`）配 4 张 vtbl，`AddRef` / `Release` 硬编码 `return 1`（`:143-151, 185-193`）。

**为什么越晚越贵**：多窗口不是「在外面套一个循环」，而是把整条 ABI 从「全局单例」改成「句柄 + 上下文结构体」。改动线要穿过：15 个导出 × 2 平台、仓颉侧每个宿主调用点、`WM_CJT_*` 消息路由、COM 处理器的生命周期。等菜单 / 托盘 / 拖放都挂上这套 ABI 再动，就是全仓大手术。

**目标形态**：

```c
typedef struct cj_host cj_host;                       /* 不透明句柄，平台各自定义内部结构 */
cj_host *cj_bridge_create(void);                       /* 建宿主：绑窗口线程上下文 */
void     cj_bridge_destroy(cj_host *h);
void     cj_bridge_set_window(cj_host *h, const char *title, int w, int h);
void     cj_bridge_run_js(cj_host *h, const char *js); /* 其余 12 个同理加首参 */
```

单窗口阶段用「默认宿主」包一层，**对外行为逐字节不变**——这是可以做到零行为变化的重构。

### 2.2 B（与 A 同刀）：平台无关逻辑没有共享层

抽 `native/bridge_core.c` + `native/bridge_core.h`：承载 1.2 表里所有无平台色彩的逻辑。平台文件退化成「只实现原语」：

```c
/* 平台文件必须实现的（每个平台 5–8 个） */
void cj_plat_wake_ui(cj_host *h);                    /* 唤醒宿主 UI 线程 */
void cj_plat_post_js(cj_host *h, const char *script); /* 在 UI 线程执行脚本 */
int  cj_plat_is_ui_thread(cj_host *h);
int  cj_plat_show_dialog_native(cj_host *h, const dlg_req *req);
void cj_plat_apply_window_config(cj_host *h, const win_config *cfg);
int  cj_plat_create_native(cj_host *h);              /* 窗口 + WebView 装配 */
void cj_plat_destroy_native(cj_host *h);
```

预期收益：`bridge_linux.c` 657 行 → 约 300–400 行，`bridge_win.c` 1012 行 → 约 300–450 行，并且**平台边界一眼可见**（正好强化 AGENTS §2 那条规矩：平台差异只许出现在 `bridge_*.c`，其余共用）。

### 2.3 C（接口现在定，实现可缓）：仓颉侧缺窗口注册表与能力分层

| 问题 | 证据 | 目标 |
|---|---|---|
| `TauriApp` 只有单个 `host` + 单个 `config` 字段 | `app.cj:19-20` | `WindowRegistry`（label → window record） |
| 回调槽是静态变量，第二个窗口会覆盖第一个 | `host.cj:100-106`（`HostGlobals.onMessage` / `onDestroy` / `dialogResult`） | 按宿主句柄索引的表 |
| `WebViewHost` 混了 per-window 与 per-app 语义 | `host.cj:12-94`：`quit` / `shouldQuit` 是 per-app，其余 per-window | 拆 `WebViewHost`（per-window）+ `AppHost`（托盘 / 应用菜单 / 退出） |
| 前端窗口 label 硬编码 | `bridge_js.h:47-48`（`windowLabel='main'`）、`ipc_hub.cj:168` | 每窗口注入 |
| 窗口间路由 | `emitToWindow` 已带 `window` 字段（`ipc_hub.cj:189-252`）——**已备好一半** | 按 label 查注册表即可 |

菜单 / 托盘 / 拖放这一栏**只定模型、不写实现**：`MenuModel` / `TrayModel` / `DragDropPolicy` 用纯仓颉数据结构描述，配 `HostCapabilities` 能力位；平台后端只做「模型 → 原生 API」的翻译。这样菜单写一次、各平台各写翻译层——与 Tauri 的 Menu API 同思路，也避免在只有两个平台时就把抽象焊死。

## 3. 收益量化

| 层 | 现状 | 批次 1+2 之后 |
|---|---|---|
| 窗口 / WebView 装配 + 事件循环 | 手写（平台特有） | 手写（不变） |
| 平台原语 | 手写，散落在文件各处 | 手写，但边界清楚（约 5–8 个） |
| 队列 / 批处理 / 对话框状态机 / 注册表 / 配置 | **手写约 35–45%** | **0** |
| 桥 JS / IPC 协议 / 能力模型 / 命令分发 | 已共享 | 已共享 |
| 菜单 / 托盘 / 拖放的**定义** | — | 0（只写翻译层） |

**一句话**：今天新增一个平台（例如 macOS WKWebView）要照 Windows 那份复制约 900 行；做完批次 1+2 之后是约 300–400 行的「装配 + 原语」。

## 4. 落地批次与风险

| 批次 | 内容 | 时机 | 风险与前置 |
|---|---|---|---|
| **1** | C ABI 句柄化 + 抽 `bridge_core.c`（单窗口行为不变） | 待排期 | Windows 侧 COM 处理器从静态单例改 per-instance 时**必须真做引用计数**（`AGENTS.md` §4 记着 `hr=0x8007139F` 那个坑）；本机无 WebView2 头文件 → **Windows 只能编译校验**。Linux 有实机回归基线：顺序往返 / 吞吐 / 事件推送 / `emitLatest` 合并四组探针 |
| **2** | `WindowRegistry` + 按句柄的回调表 + `WebViewHost`/`AppHost` 拆分 + IPC 按 label 路由 | 待排期（纯仓颉，低风险） | 单窗口行为不变；做完多窗口通路即就绪 |
| **3** | 菜单 / 托盘 / 拖放能力位落地、ArkWeb 后端、多窗口 UI（窗口间通信、生命周期） | 等真实需求 | 需要第二个平台 / 窗口来检验抽象，否则容易设计错 |

批次 1 的实施注意：Linux 句柄化时**每个宿主必须自带 GTK 线程与窗口指针**，别让 `g_idle_add` 回调拿错宿主——这与本轮已踩过的「GTK 调用必须在原生 pthread 内」是同一类坑，句柄化只是把「哪个线程/哪个窗口」从全局变成随句柄走。

## 5. 界线：不要过度抽象

判据只有两条：

- **改了能显著降低「新增平台 / 新增窗口」的代码量，且不做就会蔓延到更多调用点的** → 现在做。落到本项目就是批次 1（ABI 句柄化）与批次 2（窗口注册表 + 回调表）。
- **没有第二个实现来验证的抽象** → 只定模型与能力位，实现等到有第二个平台时再写。菜单 / 托盘 / 拖放属于这一类。

按此判据，现在要动的**只是「形状」**：把 C 桥从单例改成句柄制、把平台无关逻辑从两份变一份、把仓颉侧的「窗口 / 宿主」概念立起来——**功能一个不加**。

## 6. 未决问题

1. 批次 1 的句柄生命周期：宿主销毁由仓颉侧显式 `destroy`，还是窗口关闭时回调自销？两者对 COM 引用计数的写法影响不同。
2. Windows 侧 `WM_CJT_FLUSH` 的 per-window 路由：用 `GWLP_USERDATA` 存句柄，还是另发一条带 id 的消息？前者改动小，后者更显式。
3. `AppHost`（托盘 / 应用菜单 / 退出）在 Linux 上落 GTK 的 `GtkApplication` 还是继续用裸 `gtk_main`——这决定托盘菜单是否要顺带引入 application 概念。
4. 批次 2 的 IPC label：改 `bridge_js.h` 让宿主注入 label，会动到已入库的 `examples/ipc-coalesce` 探针输出格式，需同步更新断言与文档。
