# 架构演进：多平台与多窗口的地基准备

> 适用版本：0.7.0（2026-10-05）。本文主体是**架构评审的结论**（为什么这么改），落地状态就地标注——
> **批次 1 已落地并随 0.5.0 发布**（C ABI 句柄化 + 抽出 `bridge_core.c` 公共核心，见 §4 中标「已落地」的验收项
> 与 `CHANGELOG.md`）；**批次 2 已落地并随 0.6.0 发布**（窗口注册表 + label 路由，设计见 §7、实机证据见 §7.7）；
> **批次 3（菜单 / 托盘 / 拖放能力位、ArkWeb、多窗口 UI）尚未实施**，§2.3 缺口表里剩下的部分写的是待做的目标状态。
> 评审范围：已实现的两个平台后端（Linux WebKitGTK、Windows WebView2）与仓颉侧宿主层
> （`src/host.cj`、`src/host_webkit.cj`、`src/host_webview2.cj`、`src/window.cj`、`src/app.cj`、`src/ipc_hub.cj`）。
> 架构契约见 `AGENTS.md` §2，IPC 选型与实测见 `docs/IPC-通信机制.md`。

## 0. 结论摘要

1. **平台相关部分的手写不可消除**——Tauri 亦然（wry 内部就是每个平台一个模块）。问题不是「要不要手写」，而是「手写的比例」。
2. 当前骨架把**本可共享的三块**做成了每平台一份：C 侧的队列 / 批处理 / 对话框状态机 / 注册表 / 配置存储（约 300–400 行 ×2 份），以及仓颉侧 `prepareHost()` 这类**逐字节重复**的装配逻辑。
3. **必须现在动的一处**：C 桥 ABI 是进程级单例，15 个 `cj_bridge_*` 全无句柄参数。这是唯一「越晚越贵」的项。
4. 另两处（共享 C 核心、仓颉侧窗口注册表与能力分层）应与第 3 点**同刀切**——分两次做要动两遍。
5. **菜单 / 托盘 / 拖放的实现现在不写**：没有第二个平台来验证抽象，写了就是猜；现在只定「模型 + 能力位」。

## 1. 现状盘点

### 1.1 已经共享的（保持现状即可）

| 层 | 证据 |
|---|---|
| 页面侧桥 JS | `native/bridge_js.h`（100 行）单源，两平台只差 `CJ_LIT`、post 语句、reload 语句三处 |
| IPC 协议、报文解析 | `src/ipc_message.cj` |
| 命令分发、事件路由 | `src/ipc_hub.cj`（`handleRawMessage` / `dispatchEvent` / `emitToWindow`） |
| 能力安全模型 | `src/capability.cj` + `src/capability_loader.cj` |
| 装配与注册表 | `src/app.cj`（`register` / `run` / 插件加载） |
| 窗口配置模型 | `src/window.cj`（`WindowConfig`，纯数据） |

这一层是三件套里最值钱的部分，**新增平台一行不用改**——这正是 `AGENTS.md` §2 那条「平台差异只许出现在 `@When` 与 `bridge_*.c`」的收益。

## 2. 三处地基缺陷

### 2.1 A（必须现在动）：C 桥 ABI 是进程级单例，没有句柄

**证据**：

- 15 个导出函数**全部没有**窗口/宿主句柄参数（两平台一致）：`cj_bridge_init` / `set_window` / `set_icon` / `set_devtools` / `add_init_script` / `open_devtools` / `load_url` / `reload` / `start` / `run_js` / `quit` / `is_ready` / `should_quit` / `set_dialog_callback` / `show_dialog`。
- Linux 侧单例：`g_window` `bridge_linux.c:29`、`g_view` `:30`；唯一一条 `g_idle_add` 刷新队列 `:446-489`；对话框单槽 `g_dlg_cur` `:180`；`g_gtk_thread` `:181` 单标量。
- Windows 侧单例：`g_hwnd` `bridge_win.c:42`、`g_controller` `:43`、`g_environment` `:44`、`g_webview` `:45`；`WM_CJT_FLUSH` 经 `PostMessageW(g_hwnd, …)` `:610,627` **不带窗口 id**；`wnd_proc` `:490` 没有 per-window `GWLP_USERDATA`；`g_host_thread_id` `:373` 单标量。
- COM 处理器是 4 个**静态单例对象**（`:130-133`）配 4 张 vtbl，`AddRef` / `Release` 硬编码 `return 1`（`:143-151, 185-193`）。

**为什么越晚越贵**：多窗口不是「在外面套一个循环」，而是把整条 ABI 从「全局单例」改成「句柄 + 上下文结构体」。改动线要穿过：15 个导出 × 2 平台、仓颉侧每个宿主调用点、`WM_CJT_*` 消息路由、COM 处理器的生命周期。等菜单 / 托盘 / 拖放都挂上这套 ABI 再动，就是全仓大手术。

**目标形态**：

```c
typedef struct cj_host cj_host;                       /* 不透明句柄，平台各自定义内部结构 */
cj_host *cj_bridge_create(void);                       /* 建宿主：绑窗口线程上下文 */
void     cj_bridge_destroy(cj_host *h);
void     cj_bridge_set_window(cj_host *h, const char *title, int w, int h);
void     cj_bridge_run_js(cj_host *h, const char *js); /* 其余 12 个同理加首参 */
```

单窗口阶段用「默认宿主」包一层，**对外行为逐字节不变**——这是可以做到零行为变化的重构。

### 2.2 B（与 A 同刀）：平台无关逻辑没有共享层

抽 `native/bridge_core.c` + `native/bridge_core.h`：承载 1.2 表里所有无平台色彩的逻辑。平台文件退化成「只实现原语」：

```c
/* 平台文件必须实现的（每个平台 5–8 个） */
void cj_plat_wake_ui(cj_host *h);                    /* 唤醒宿主 UI 线程 */
void cj_plat_post_js(cj_host *h, const char *script); /* 在 UI 线程执行脚本 */
int  cj_plat_is_ui_thread(cj_host *h);
int  cj_plat_show_dialog_native(cj_host *h, const dlg_req *req);
void cj_plat_apply_window_config(cj_host *h, const win_config *cfg);
int  cj_plat_create_native(cj_host *h);              /* 窗口 + WebView 装配 */
void cj_plat_destroy_native(cj_host *h);
```

预期收益：`bridge_linux.c` 657 行 → 约 300–400 行，`bridge_win.c` 1012 行 → 约 300–450 行，并且**平台边界一眼可见**（正好强化 AGENTS §2 那条规矩：平台差异只许出现在 `bridge_*.c`，其余共用）。

### 2.3 C（接口现在定，实现可缓）：仓颉侧缺窗口注册表与能力分层

| 问题 | 证据 | 目标 |
|---|---|---|
| `TauriApp` 只有单个 `host` + 单个 `config` 字段 | `app.cj:19-20` | `WindowRegistry`（label → window record） |
| 回调槽是静态变量，第二个窗口会覆盖第一个 | `host.cj:100-106`（`HostGlobals.onMessage` / `onDestroy` / `dialogResult`） | 按宿主句柄索引的表 |
| `WebViewHost` 混了 per-window 与 per-app 语义 | `host.cj:12-94`：`quit` / `shouldQuit` 是 per-app，其余 per-window | 拆 `WebViewHost`（per-window）+ `AppHost`（托盘 / 应用菜单 / 退出） |
| 前端窗口 label 硬编码 | `bridge_js.h:47-48`（`windowLabel='main'`）、`ipc_hub.cj:168` | 每窗口注入 |
| 窗口间路由 | `emitToWindow` 已带 `window` 字段（`ipc_hub.cj:189-252`）——**已备好一半** | 按 label 查注册表即可 |

菜单 / 托盘 / 拖放这一栏**只定模型、不写实现**：`MenuModel` / `TrayModel` / `DragDropPolicy` 用纯仓颉数据结构描述，配 `HostCapabilities` 能力位；平台后端只做「模型 → 原生 API」的翻译。这样菜单写一次、各平台各写翻译层——与 Tauri 的 Menu API 同思路，也避免在只有两个平台时就把抽象焊死。

## 3. 收益量化

| 层 | 现状 | 批次 1+2 之后 |
|---|---|---|
| 窗口 / WebView 装配 + 事件循环 | 手写（平台特有） | 手写（不变） |
| 平台原语 | 手写，散落在文件各处 | 手写，但边界清楚（约 5–8 个） |
| 队列 / 批处理 / 对话框状态机 / 注册表 / 配置 | **手写约 35–45%** | **0** |
| 桥 JS / IPC 协议 / 能力模型 / 命令分发 | 已共享 | 已共享 |
| 菜单 / 托盘 / 拖放的**定义** | — | 0（只写翻译层） |

**一句话**：今天新增一个平台（例如 macOS WKWebView）要照 Windows 那份复制约 900 行；做完批次 1+2 之后是约 300–400 行的「装配 + 原语」。

## 4. 落地批次与风险

| 批次 | 内容 | 时机 | 风险与前置 |
|---|---|---|---|
| **1** | C ABI 句柄化 + 抽 `bridge_core.c`（单窗口行为不变） | 待排期 | Windows 侧 COM 处理器从静态单例改 per-instance 时**必须真做引用计数**（`AGENTS.md` §4 记着 `hr=0x8007139F` 那个坑）；本机无 WebView2 头文件 → **Windows 只能编译校验**。Linux 有实机回归基线：顺序往返 / 吞吐 / 事件推送 / `emitLatest` 合并四组探针 |
| **2** | `WindowRegistry` + 按句柄的回调表 + `WebViewHost`/`AppHost` 拆分 + IPC 按 label 路由 | 待排期（纯仓颉，低风险） | 单窗口行为不变；做完多窗口通路即就绪 |
| **3** | 菜单 / 托盘 / 拖放能力位落地、ArkWeb 后端、多窗口 UI（窗口间通信、生命周期） | 等真实需求 | 需要第二个平台 / 窗口来检验抽象，否则容易设计错 |

批次 1 的实施注意：Linux 句柄化时**每个宿主必须自带 GTK 线程与窗口指针**，别让 `g_idle_add` 回调拿错宿主——这与本轮已踩过的「GTK 调用必须在原生 pthread 内」是同一类坑，句柄化只是把「哪个线程/哪个窗口」从全局变成随句柄走。

**批次 1 顺带统一的两处**（本轮评审静态读出的不一致，已列为验收项，**两项均已落地并实机验收**）：

- **`quit()` 的 `onDestroy` 语义跨平台不一致**：Windows 的 `WM_CJT_QUIT` → `DestroyWindow` → `WM_DESTROY` **会**触发 `g_on_destroy`（`bridge_win.c:530-534`）；Linux 的 `cj_bridge_quit()` 直接置标志 + `gtk_main_quit()`、**不触发**（`bridge_linux.c:509-514`）。应用侧写 `onDestroy` 做清理，会在一端不执行。验收项：两平台「主动 `quit`」与「用户关窗」走同一条通知路径。
  **已落地**：Linux 的 `quit` 不再自己 `gtk_widget_destroy`，只 `gtk_main_quit()`，窗口交给 `gtk_main` 返回后的收尾销毁——`destroy` 信号照旧触发 `onDestroy`（收尾里那次 `cj_core_window_destroyed` 只是幂等兜底），与 Windows 的 `DestroyWindow → WM_DESTROY` 语义对齐。（**为什么销毁要挪到主循环之外**：见下一条末尾。）
- **Linux 收尾路径疑似重复销毁 / 悬垂指针**：`on_destroy` 未把 `g_view` / `g_window` 置 NULL（`bridge_linux.c:542-550`），而 `gtk_main()` 返回后的收尾仍对它们做 `g_object_unref` / `gtk_widget_destroy`（`:628-637`）。静态读出来是 UB，实机多轮未崩（这类 UB 常不立刻崩）——**未实机复现，只记疑点**。验收项：收尾前判存活或把指针置 NULL，并在关窗退出路径上复跑现有探针、确认无 GTK 警告。
  **已落地**：`on_destroy` 起把 `p->view` 与 `p->window` 一并置空，收尾只收还活着的对象。实测复跑出现的关键事实是一条**新坑**：在主循环**内**销毁 WebKit 窗口，会让 libwebkit2gtk 的**退出期析构函数**在自己的 `g_object_unref` 里 abort（`StartMainTask → exit → __run_exit_handlers → libwebkit2gtk … → abort`，退出码 134，与框架代码无关，gdb 一眼可见）；AB 对照：不销毁窗口 5/6 干净、销毁窗口 5/6 abort。销毁时机挪到主循环之后即 6/6 干净退出——两条一起改完，退出路径连同 `quit()` 一起验收通过。

**批次 1 的 Windows 侧静态复核**（2026-10-02，本机无 Windows 运行时，纯静态读 `bridge_win.c` 864 行 + `bridge_core.h/.c` 契约）：

| 契约项 | 结论 |
|---|---|
| `cj_plat_fini` 返回值语义 | ✅ 两平台一致：Windows 是「`WaitForSingleObject(p->thread, 5000)` 有界等待 + `thread_done` 标记」，Linux 是「有界轮询 + 同一标记」；都不是无限 join，宿主线程没跑完就 `return 0`，`cj_bridge_destroy` 据此保留句柄与状态 |
| COM 处理器是否 per-instance | ✅ 四个处理器（env / ctrl / msg / nav）已内嵌进 `plat_host`，`cj_plat_init` 逐个 `p->xxx.h = h` 并挂 vtbl——不再是进程级静态单例 |
| COM 引用计数 | ⚠️ **有意**保持 `AddRef`/`Release` 恒返回 1（AGENTS §4 的既有要求：WebView2 会 Release 这些回调对象，真释放即 use-after-free / `hr=0x8007139F`）；要长期持有的对象由调用方**显式 AddRef**——已核实两处：`p->environment->…AddRef`（`bridge_win.c:213`，不持有时环境对象被回收 → 导航不完成）、`p->controller->…AddRef`（`:260`）；临时对象照常 `Release`（`:284` 的 settings） |
| 主动 `quit` → `onDestroy` 次数 | ✅ 语义对齐、**实现有意不同**：Windows 是 `WM_CJT_QUIT → DestroyWindow → WM_DESTROY → cj_core_window_destroyed`（**在主循环内**销毁，Win32 正常且必需）；Linux 是 `quit` 只 `gtk_main_quit()`、窗口留给主循环之后的收尾（**不能**在循环内销毁，见上一条的 WebKit 退出期 abort）。两边都由 core 的 `destroy_notified` 保证恰好一次——别为了「对齐」把 Linux 挪回循环内 |
| 句柄回收条件 | ✅ 唯一入口是 core 的 `cj_bridge_destroy → cj_plat_fini`，两平台都在 `fini` 返回 1 时才 `free` 平台状态与句柄 |

复核顺带修掉一处**文档与实现不符**：`bridge_core.h` 原先写 `cj_plat_fini` 释放「COM 环境引用」，但 Windows 按「活到进程退出」口径**不**释放 COM（只置空指针）——已改为如实描述，并把「只做有界等待、不做无限 join」的理由写进契约注释。

遗留（没跑运行时，故未验证、只记疑点）：COM 对象本就「活到进程退出」，而 `plat_host`（内含四个处理器）会在 `fini` 返回 1 时 `free`——退出瞬间 WebView2 侧理论上仍可能持有已释放的处理器指针。只存在于退出路径、未观测到问题，**待 Windows 实机复核**。

## 5. 界线：不要过度抽象

判据只有两条：

- **改了能显著降低「新增平台 / 新增窗口」的代码量，且不做就会蔓延到更多调用点的** → 现在做。落到本项目就是批次 1（ABI 句柄化）与批次 2（窗口注册表 + 回调表）。
- **没有第二个实现来验证的抽象** → 只定模型与能力位，实现等到有第二个平台时再写。菜单 / 托盘 / 拖放属于这一类。

按此判据，现在要动的**只是「形状」**：把 C 桥从单例改成句柄制、把平台无关逻辑从两份变一份、把仓颉侧的「窗口 / 宿主」概念立起来——**功能一个不加**。

## 6. 建议方案（评审结论）

> 以下是四个决策点的**建议**，均未实施，作为批次 1 / 批次 2 的实施依据。
> 这里写成定论而不是选项，是为了实施时不必再推演一遍；有异议就改这一节。

### 6.1 句柄生命周期：关闭与释放分离

窗口关闭 **不等于** 释放句柄。

1. 关闭时原生侧只做三件事：置 `h->window_gone = 1`、释放原生 / COM 资源、触发 `onDestroy` 回调；**句柄壳保留**，交给仓颉侧。
2. 释放走仓颉侧显式 `cj_bridge_destroy(h)`；句柄内存**由 C 侧 `malloc`、C 侧 `free`**（`create` 分配、`destroy` 回收）——跨 FFI 绝不能「这边分配那边释放」，Windows 上 CRT 与仓颉运行时不是同一个分配器。
3. `destroy` **幂等**（重复调用安全）：`quit()` 与窗口关闭可能都走到释放，调用方不该被迫维护状态机。
4. 原生资源**不能等仓颉侧**：`g_controller` / `g_environment` 持有 hwnd 与 webview，必须在窗口销毁时收掉（现状见 `bridge_win.c:740-745`），否则 COM 循环引用泄漏。
5. 释放**不阻塞等宿主线程**（批次 1 已落地）：平台层收尾 `cj_plat_fini` 返回 `int`——`1` = 状态已释放、句柄可回收；`0` = 宿主线程还在跑（它进过仓颉运行时），此时 `cj_bridge_destroy` **连句柄一起留着**、不 `free`。理由：宿主线程收尾要进仓颉运行时，仓颉线程阻塞在 `pthread_join` 上会与运行时的「停处理器」握手互等（实测约 1/6 概率挂死）；进程随即退出，泄漏一次状态远比死锁安全。有界轮询等待宿主线跑完是允许的（不碰 join），等到了就正常回收。

**理由**：「原生资源随关闭走、句柄壳随 `destroy` 走」两侧都不省——只做前者，仓颉侧可能仍持有已释放的原生资源；只做后者，窗口关闭后 COM 引用永不下降。

### 6.2 flush 路由：`GWLP_USERDATA` 存宿主，不做「带 id 的消息」

1. `CreateWindowExW` 的 `lpParam` 传 `h`（现状传 `NULL`，`bridge_win.c:714-717`），在 `WM_NCCREATE` 里 `SetWindowLongPtrW(hwnd, GWLP_USERDATA, (LONG_PTR)h)`——`WM_NCCREATE` 是唯一能安全拿到 `lpParam` 的时机（早于 `WM_CREATE`）。
2. flush 一律投给宿主自己的窗口：`PostMessageW(h->hwnd, WM_CJT_FLUSH, …)`（现状用全局 `g_hwnd`，`bridge_win.c:610,627`）。
3. 同类一起改：`WM_SIZE` 现在裸用 `g_controller`（`bridge_win.c:492-498`）→ `h->controller`。

**理由**：`PostMessage` 本身就按窗口寻址，每个宿主投自己的窗口，**路由天然正确、id 是多余的**；「带 id 的消息」要另维护全局注册表与生命周期同步，等于把操作系统免费提供的能力重做一遍，还会引入 id 失效 / 复用的经典坑。而我们本来就需要 per-window 数据（宿主指针），挂在窗口上零额外代价。

**注意**：① 消息可能在窗口销毁后才被派发 → `wnd_proc` 里 `h == NULL || h->window_gone` 直接返回；② `lParam` 留着别占用（将来窗口级重绘合并还用得上）。

### 6.3 Linux 主循环：继续裸 `gtk_main`，托盘用 appindicator 且可选编译

**先纠正本文档早先的提法**：`GtkApplication` 与「能不能做托盘」**没有因果关系**。GNOME Shell 原生不显示 XEmbed / legacy tray 图标，GTK3 上实际可行的路径是 `libayatana-appindicator3`——它是独立库（托盘自己走 DBus），与主循环是 `gtk_main` 还是 `g_application_run` 无关。

本机实测（2026-10-02）：

| 项 | 结果 |
|---|---|
| GTK | 3.24.41（在） |
| `ayatana-appindicator3-0.1` | ❌ pkg-config / 头文件 / 运行时 `.so` 全缺 |
| legacy `appindicator3-0.1` | ❌ 同样全缺 |
| `libayatana-appindicator3-dev` | 可装，apt candidate `0.5.93-1build3`（需用户自装） |

1. **现在不引入 `GtkApplication`**。它带来的是 GAction / 应用菜单、单实例、应用生命周期，只有「要桌面菜单栏 / 单实例」时才值钱；现在引入等于把刚验证过的 `gtk_init` + `gtk_main` + `on_destroy`→`gtk_main_quit`（`bridge_linux.c:562-638`、`:542-550`）整套启动退出路径换成 `g_application_run`，收益为零、风险是动到已实测的退出语义。

### 6.4 IPC label 注入：不影响 `ipc-coalesce` 探针

**修正本文档早先的表述**：原先写「会动到探针输出格式、需同步更新断言」——**说重了**。核实结果：探针前端只用 `window.__CJ_TAURI__.invoke` / `listen`（`examples/ipc-coalesce/src/main.cj:107-140`），四行 `PROBE-*` 字符串里没有 label / window 字段 → 注入 label 不改探针输出，**无需改断言**。

### 7.2 新文件与接口签名

`src/window_registry.cj`（单一职责拆分，AGENTS §2）：

```cangjie
/** 一个窗口：label 唯一，config 是它创建时的窗口配置快照 */
public class WindowRecord {
    public let label: String
    public let host: WebViewHost
    public let config: WindowConfig
    // 构造：三个字段全给定；label 非空、唯一由注册表把关
}

/** label → 窗口记录。单窗口阶段只有 "main"，多窗口时它是唯一权威来源 */
class WindowRegistry {
    func add(record: WindowRecord): Unit   // 重复 label 抛异常，不静默覆盖
    func get(label: String): Option<WindowRecord>
    func labels(): ArrayList<String>
    func remove(label: String): Unit
    func size(): Int64
}
```

`src/host.cj`：接口一拆二，**不变的部分不搬家**（避免无谓的契约破坏）：

```cangjie
public interface WebViewHost {   // per-window：start/startUrl/addInitScript/setWindowConfig/
                                 // setDevTools/openDevTools/showFileDialog/showMessageDialog/
                                 // runJs/setMessageHandler/reload/quit/shouldQuit/dispose
    public func label(): String  // 新增：本窗口的 label，默认 "main"
}

public interface AppHost {       // per-app：只有退出与跨窗口查表
    public func quit(): Unit
    public func waitForExit(): Unit
    public func hostOf(label: String): Option<WebViewHost>
}
```

- 收循环归 `AppHost.quit()`（应用主循环本来就是跨窗口的），阻塞等待归 `AppHost.waitForExit()`
  ——调用方要的是「阻塞到退出」，不是「轮询一个布尔」。
- **实现偏差（就地更正）**：没有把 `quit()` / `shouldQuit()` 从 `WebViewHost` 摘掉。它们是「本窗口循环」
  的低层原语，宿主实现里本来就要用（`TauriApp` 收循环就是逐个窗口调它），摘掉只会把收尾顺序推回上层；
  上表「移出为 `AppHost`」按此理解。**应用级入口仍只有 `AppHost`**——新代码写 `app.quit()`。
- **最终签名**：`TauriApp` 自己实现 `AppHost`（装配期就知道注册表，不必再套一层后端对象）；
  `hostOf(label)` 是**唯一**按 label 取宿主的入口——原计划另加 `webviewHost(label)` 重载，落地时取消：
  两个入口做同一件事，只会让人猜该用哪个。`app.webviewHost()` 保留（默认窗口的宿主）。
  现有调用点只有 `plugin_dialog.cj:72`（取默认窗口，不受影响）与临时探针 `/tmp/probe_quit{2}`（不进仓）。

### 7.3 label 从哪来：懒读 + 报文携带（默认仍必须是 `"main"`）

桥 JS（`native/bridge_js.h`）三处小改，不引入新通道：

1. `var windowLabel = 'main';` → 懒解析，首次读到即缓存（**变量名以 `native/bridge_js.h` 为准**）：

```js
var cachedLabel = null;
function labelOf() {
  if (cachedLabel === null) {
    var v = (typeof window !== 'undefined') ? window.__CJ_TAURI_LABEL__ : null;
    cachedLabel = (typeof v === 'string' && v.length > 0) ? v : 'main';
  }
  return cachedLabel;
}
```

   落地时把「非字符串 / 空串」也一并归到缺省 `"main"`：注入脚本的值是**转义后**拼出来的
   （`app.cj` 的 `registerDefaultWindow()` 用 `JsonString(label)`），而页面里同名全局被别人写成
   `false` / `0` 时同样必须回落——否则下面第 3 条的 `if (msg.window && …)` 过滤会拿 `false` 去比对。

   **懒读是关键**：注入脚本与桥 JS 同在 document-start，谁先谁后由平台决定，而 `labelOf()` 只在
   「发报文 / 收事件」时调用——那时两段脚本都已执行完，顺序无关。
2. 出向报文 `invoke` / `emit` 各加一个 `window: labelOf()` 字段（**协议增量**：`parseEnvelope`
   只认已知字段、忽略多余字段，旧前端不受影响）。
3. `_dispatch` 的过滤改用 `labelOf()`（语义不变，只是取值不再硬编码）。

仓颉侧：`InvokeRequest` / `EmitRequest` 各多一个 `let window: String`（解析缺省 `"main"`）；
`ipc_hub.cj:168` 的 `IpcContext("main", this)` 改为 `IpcContext(req.window, this)`。
**默认值必须是 `"main"`**——§6.4 记的兼容红线：示例与探针里写死的 `"main"` 一旦对不上，就是收不到
事件且不报错。

### 7.4 事件派发：`jsSink` 带 label

```cangjie
public var jsSink: (String, String) -> Unit   // (json, 目标 label；空串 = 广播)
```

`TauriApp.prepare()` 里按注册表派发：label 为空 → 遍历所有窗口各投一份；非空 → 只投该窗口，
查不到就打一条 stderr（**不静默**：写错的 label 最难查）。单窗口下与今天等价——只有一个 `"main"`，
两条路径投到的是同一个宿主。

## 8. 多窗口 PoC 实测结论（2026-10-02 起，2026-10-03 补 Windows）：约束是 WebKitGTK 专属——Linux 须走单主循环，Windows 已通过

批次 2 把 label 路由铺好了，但「一个进程里两个窗口」到底立不立得住，一直只是判断。本节把它做成实测。

### 8.1 探针与做法

- `examples/multi-window/`（入库的探针工程）：同一进程两窗口（`main` + `second`），两页是**同一份 HTML**，
  角色由自己的 label 推出来（`DRIVER = label === 'main'`）；驱动窗轮询 `boots` 等到两个窗口都 boot 后
  触发后端 `fire`（广播 1 条 + 定向 2 条），两窗各自把收到的条数报回 stderr，逐行可按断言核。
  `MW_MODE=single` 是对照开关（只起主窗）；`run.sh` 自带断言与 Xvfb 起停。
- 用手动第二宿主（`addWindow`）而不是先写通用多窗口 UI：§5 判据——没有第二实现验证的抽象只定模型。
- 探针只用了批次 2 已有的面：`addWindow(label, config, html)`、`label()`、应用级 `emitToWindow`。

### 8.2 分层对照（结论的全部证据都在这张表）

| 对照 | 结论 |
| --- | --- |
| 纯 GTK，N=1 线程 `gtk_init`+建窗+`gtk_main` | `exit=0`，6s 干净退出 |
| 纯 GTK，**N=2** 线程各自一套（**串行起**，间隔 300ms） | **`exit=0`**，两窗都活着 → GTK 本身不反对两条主循环 |
| 纯 GTK + WebKit，N=1 | `exit=0` |
| 纯 GTK + WebKit，**N=2**（串行起，间隔 1.5s，每线程各一个 `WebKitWebView`） | **不可用**：`/tmp` 变体 `exit=134`（`Gtk-CRITICAL gtk_text_attributes_ref` / `Pango-CRITICAL pango_layout_new` → `Aborted`）；入库变体 `exit=139`（SIGSEGV）+ `Gtk-CRITICAL`，**8/8 失败** |
| cj-tauri 双窗（探针，`MW_MODE` 缺省） | **`exit=134`** `realloc(): invalid next size`（3/3 次）；**gdb 下改为挂死**（不崩，两页都没能 boot） |
| cj-tauri 单窗（`MW_MODE=single`） | `exit=0`：`BOOT jsLabel=main` → `GATE boots=1` → `FAIL second window never booted` → `quit` → `after run` |
| **Windows**：cj-tauri 双窗（探针，`run.bat` 缺省，2026-10-03） | **`exit=0`，8/8 断言全过**：两窗各自 `BOOT jsLabel=main booted=1` / `jsLabel=second booted=2`（身份 = 注入的 label）、`GATE boots=2`、驱动窗 `COUNTS … broadcast=1 target_main=1 target_second=0`、观察窗 `COUNTS … broadcast=1 target_main=0 target_second=1` |
| **Windows**：cj-tauri 单窗对照（`MW_MODE=single`，2026-10-03） | **`exit=0`，7/7 断言全过**：`BOOT booted=1` → `GATE boots=1` → `FAIL second window never booted` → `requested quit` → `after run` |

最小对照是**独立 C 程序**（无仓颉、无 cj-tauri 代码，`gcc … $(pkg-config --cflags --libs webkit2gtk-4.1)`），
收敛在 `native/tests/gtk_threading_probe.c`，跑法见 `scripts/test-gtk-threading.sh`。
踩过的坑：首版是「主线程 `sleep` 到点就 `return`」，两条线程卡在 `gtk_init` 里出不来时它也照样返回 0，
**把卡死误报成干净退出**（日志里连 `window up` 都没有）——一度让我以为「N=2 有时是好的」。现在改成
等「N 个窗口都起来」、超时给独立退出码 `3`，`0` 才是真干净。

### 8.3 判定

1. **不是 GTK 的锅**：纯 GTK 两条主循环并存跑满 6s 干净退出。
2. **不是我方桥/仓颉的锅**：桥的 GTK 初始化路径逐行核过——`cj_plat_init` 只 `calloc` 一份 `plat_host`、
   不碰任何进程级 GTK 状态；`gtk_thread_main` 里每宿主线程各 `gtk_init` 一次（`bridge_linux.c:469`），
   与最小对照同构；且最小对照里**没有我们的代码照样崩**。双窗日志显示两个句柄、两份标题、
   两份 label 注入（35 / 37 字节）都各归其主——缝本身是好的。
3. **根因：WebKitGTK 不能被两条线程各自使用**。同一进程里两个 `WebKitWebView` 分处两条线程就是不
   **被支持的用法**，表现随机但几乎必发：入库的最小对照修好判定逻辑后 **8/8 致命失败**——多数是
   `exit=139`（SIGSEGV）+ `Gtk-CRITICAL`，早先 `/tmp` 变体是 `exit=134`（GTK/Pango 断言 → abort），
   另有一次是两条线程都卡在 `gtk_init` 里出不来。**串行起（间隔 1.5s）也逃不掉**，所以既不是单纯的
   「初始化撞车」，也不是靠时序能回避的竞态。
   cj-tauri 侧的 `realloc(): invalid next size` 是被写坏的堆**延迟发现**（检测点在仓颉主线程，
   不是损坏点）；gdb 下时序变化表现为挂死——与上面几种表现同源。
4. **这条约束是 WebKitGTK 专属，不跨平台**。Windows（WebView2）用**同一份装配**实测通过（2026-10-03）：
   双窗 **8/8 断言全过、`exit=0`**、单窗对照 **7/7 通过**——Win32 允许每窗一条 UI 线程 + 自己的消息循环，
   WebView2 的 controller 只被创建它的线程访问（`WM_CJT_FLUSH` 按 hwnd 路由、`GWLP_USERDATA` 存 host），
   批次 2 的 label 路由在两条宿主线程上各归其主。故 **§8.4 的「单主循环」是 Linux 专属前置**。
   Windows 首轮还暴露并修掉三个真 bug（`build_win.bat` 漏编 `bridge_core.c`、`wnd_proc` 缺 return
   导致建窗失败且 `GetLastError()=0`、`run.bat` 括号解析），见 `CHANGELOG.md` `[Unreleased]` 与
   `docs/进度记录.md` §3.2。
   ⚠️ **§7.5 的残余项已按「能测的先测掉」收口**（同日实机，双窗 `run.bat` 的断言由 8 条**扩到 18 条**、
   全过、`exit=0`）：
   探针补了两个阶段——阶段 2 两窗**同时**向各自宿主开原生消息框（硬证据 `window=main ASK … inflight=2`：
   第二条 ask 进栈时第一条**还没出栈**；自动确认脚本的 `FIRST batch: 2 dialog(s) open` 独立佐证两框并存），
   阶段 3 **只关 `second`** 并证明应用没跟着返回（`CLOSE-WINDOW which=second requested` →
   `ALIVE second=1 main=0` → `CLOSE-PHASE alive=second=1 main=0`）。于是两条由「潜在」变实测事实：
   对话框状态在 C 核里本就是 **per-host**（`h->dlg_busy` / `dlg_lock` / `dlg_cur`）**跨宿主不互斥**；
   退出是**逐窗判**的（`app.cj` 的 `allWindowsExited` 逐宿主轮询 `shouldQuit`），少一个窗口不会提前返回。
   仍**没被清掉**的两处是代码层结论（不是「没测」）：① `HostGlobals.onDestroy` 既是静态单槽、
   又**根本不在 `WebViewHost` 接口上**——应用侧没有安装点，现在恒为 no-op，要真用得先把它移进
   `WebViewHost` 并带上宿主身份；② 文件类对话框的结果走共享单槽 `HostGlobals.dialogResult`，
   两窗同时开文件框时**先返回者读到的可能是后返回者写的值**（本用例用 message 框绕开了它：message 框的
   结果就是返回值，不经槽位）。这两处应与「回调带宿主 id」一起做，别当成已解决——按 §5 判据属
   「不做会蔓延」的正确性项。

### 8.4 下一步（Linux 专属前置；等真要上多窗口 UI 时再做）

- **Windows 侧没有任何前置**：同一份装配 2026-10-03 实测双窗通过（见 §8.3 第 4 条），下面这条只对 Linux 成立。

- **Linux 宿主改「单主循环 + 多窗口」**：一个进程一条 GTK 线程、唯一的 `gtk_main`；N 个窗口与
  `WebKitWebView` 都在这条线程里创建与访问。`cj_plat_*` 从 per-host 改为「进程级一个循环 + 每宿主
  一份窗口状态」，`cj_plat_wake_ui` 的 `g_idle_add` 自然只有一条循环可投。仓颉侧**几乎不动**：
  `WebViewHost` 仍 per-window、批次 2 的 label 路由不变，只是 `start` 不再各起线程。
- **§7.5 的「回调带宿主 id」仍是这件事的地基**，但其中「能测的一半」已于 2026-10-03 测掉（§8.3 第 4 条）：
  多窗口下**同时**开原生框与只关一个窗口都已验过（`inflight=2` / `ALIVE second=1 main=0`）。剩下的不是
  「测」而是「装」——`onDestroy` 是静态单槽且不在 `WebViewHost` 接口上（应用侧装不进去、恒 no-op），
  文件框结果还走共享单槽 `HostGlobals.dialogResult`；单主循环下 N 个窗口共用一条循环时这两处才会真撞车，
  故应与单主循环**一起**做。
- **判据**：§5 优先级里「Windows 实机」这一项**已于 2026-10-03 完成**；「多窗口 UI」的前置成本现在要
  **按平台分开算**——Windows 上只剩 UI 本身（外加 §7.5 残余项），Linux 上仍要背「单主循环」这次重构，
  故它**仍排在菜单 / 托盘 / 拖放之后**，只是不再被「Windows 也没验过」整体压住。
  探针留在仓内：它是这条约束的**复现器**，也是单主循环落地后的验收用例；在 Windows 侧它还兼**反例保护伞**
  ——将来若有人照 Linux 的做法改成单主循环，`run.bat` 能立刻发现 Windows 面被改坏。
