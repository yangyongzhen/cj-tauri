# 源码结构（`src/` 分层与依赖方向）

> 本文件回答的是「代码在哪、归谁管、能往哪依赖」。**为什么长这样**见 `docs/设计决策记录.md`（ADR），
> **做到哪了**见 `docs/需求追踪.md`，改代码前必读的门禁与契约见 `AGENTS.md` §1 / §2。
> 口径：本文件只描述**已经落地**的形态，不写计划；仓库里没有的文件不要在这里出现。

## 1. 一句话

`src/` 根是一个包（`package cjTauri`），下面按「能不能独立成包」分成两类目录：
**能独立成包的已经拆走**（`platform/`、`plugins/<名字>/`、`tests/`），**拆不动的留在根目录按文件分职责**。
根目录文件之间互相引用，所以**不能**再按目录往下拆——仓颉的包等于目录，包依赖图必须是 DAG，
而根目录这批文件是互相引用的（拆任何一组出去都会立刻形成环，见 §6）。

## 2. 仓库分层

| 目录 | 职责 | 依赖方向 | 硬约束 |
| --- | --- | --- | --- |
| `src/` | 框架本体（一个包） | → `src/platform/`、`src/plugins/*` | 根只留框架源码（见 §5） |
| `src/platform/` | 各平台宿主实现与宿主工厂注册 | → `src/`（父包） | 平台分叉只在这里与 `native/` |
| `src/plugins/<名字>/` | 一个插件一个子包 | → `src/`（父包） | 插件之间**不得互相引用** |
| `src/tests/` | 单测（`package cjTauri.tests`） | → `src/` 的 `public` 符号 | 必须留在 `src/` 下 |
| `native/` | C 桥（`core/` 共享层 + `platforms/<os>/`） | — | FFI 导出两平台同名同签名 |
| `cli/`、`examples/` | 脚手架 / 示例（各自独立包） | → `src/` | 各跑各的 `cjpm build` |

## 3. `src/` 根：36 个文件按职责分组

行数是量级参考（`wc -l`），不是契约。

### 3.1 装配与启动（应用怎么被描述、怎么跑起来）

| 文件 | 内容 | 备注 |
| --- | --- | --- |
| `app.cj` | `TauriApp` 类声明、`ExtraWindowSpec`、配置与注册 API（窗口 / 插件 / 命令 / 能力 / scope） | 类体只放**声明与装配**，见 §4 |
| `app_run.cj` | `run` 三入口、`runWith` 骨架、`prepare`、窗口启动、清单导出（`CJ_TAURI_MANIFEST`） | `extend TauriApp` |
| `app_events.cj` | `emit` / `emitLatest` / `emitToWindow`、`listenEvent`、shell 事件分发、`deliverJs` | `extend TauriApp` |
| `app_host_ops.cj` | 宿主能力预置：菜单、托盘、全局快捷键、拖放、窗口可见性、日志落盘 | `extend TauriApp` |
| `app_spec.cj` | `AppSpec`：声明式装配（`build()` 的返回类型） | 与 `launch.cj` 配对 |
| `launch.cj` | `launch(spec)`：按目标分派装配 | 平台知识留在 L0 |
| `platform_host_provider.cj` | `HostProvider`：宿主工厂注册表（`resolveHost` 的来源） | 新增平台从这里接 |

### 3.2 宿主（一个窗口 vs 整个应用）

| 文件 | 内容 |
| --- | --- |
| `host.cj` | `WebViewHost`（一个窗口）、`AppHost`（整个应用）、`HostCapabilities`、宿主级回调路由表 |
| `host_webkit.cj` / `host_webview2.cj` / `host_arkweb.cj` | 三个平台的宿主实现（Linux / Windows / 鸿蒙） |
| `window.cj` | `WindowConfig`、`PageSource`、`AssetResolver` 等窗口与页面声明 |
| `window_registry.cj` | `WindowRecord`、`WindowRegistry`：`label → 宿主` 的唯一权威来源 |

`host.cj` 同时定义 `WebViewHost` 与 `AppHost` 两个接口——**新增宿主能力先扩接口，再改三个平台实现，
最后在 C 桥加同名导出**（两平台导出名必须一致）。

### 3.3 IPC 与 JS 通道

| 文件 | 内容 |
| --- | --- |
| `ipc_message.cj` | `InvokeRequest` / `EmitRequest` / `IpcMessage`：报文模型与协议版本字段 |
| `ipc_hub.cj` | `IpcHub`（校验 + 异步分发）、`CommandHandler`、`IpcContext`、`CommandException` |
| `jsutil.cj` | 生成 JS 字面量 / 转义等小工具 |

`IpcHub.handleInvoke` **只做校验**：「未授权 / 未注册」在调用线程同步拒绝，通过校验的命令 `spawn`
到 worker 线程。别把 handler 挪回调用线程（会把慢命令钉在宿主 UI 线程上）。

### 3.4 能力与安全

| 文件 | 内容 |
| --- | --- |
| `capability.cj` | `Capability`、`CapabilityRegistry`、命名权限集展开、运行期 scope 叠加层 |
| `capability_loader.cj` | 能力清单加载 / `capabilities/` 目录扫描 |
| `scope.cj` | `ScopeRule`、`parseScopeRule`、`scopeAllows`（先 deny 后 allow，匹配前规范化） |

判定逻辑**只在这里**。插件与平台实现都调共享层，不许各判一份。

### 3.5 宿主能力模型（模型在仓颉侧，交给平台执行）

| 文件 | 内容 |
| --- | --- |
| `menu.cj` | `MenuItem` / `MenuModel` / `MenuItemKind` |
| `tray.cj` | `TrayModel` |
| `hotkey.cj` | `Hotkey` / `HotkeyModel`（同一套 accel 词法，两平台共用） |
| `dragdrop.cj` | `DragDropPolicy` |
| `shell_event.cj` | shell 事件信封解析与 `kind → 前端事件名` 映射 |

模型文件不含平台分支；「怎么落地」归宿主实现，「给不给」归 `HostCapabilities`。

### 3.6 桥接、平台分派与工具

| 文件 | 内容 |
| --- | --- |
| `log_bridge.cj` | 日志落盘的 FFI 包装（`@When[env != "ohos"]`，无桥平台如实降级） |
| `clipboard_bridge.cj` | 剪贴板的 FFI 包装（同上口径） |
| `process_hidden.cj` | `BackgroundProcess`：后台静默子进程（无控制台窗口） |
| `arkweb_proxy.cj` / `arkweb_script.cj` | 鸿蒙 ArkWeb 的桥接导出与脚本投递（**ArkUI-free**） |
| `logging.cj` | 日志路径 / 预算 / 环境变量解析（纯仓颉，无 FFI） |
| `embedded_assets.cj` | 内嵌资产（单文件包解 base64 的来源之一） |
| `hexutil.cj` | `hexToBytes` / `bytesToHex`（多插件共用，故在根） |
| `urlutil.cj` | URL / dev server 地址处理（`rewriteForDev` 等） |
| `version.cj` | `CJ_TAURI_VERSION`（`system:version` 的返回值） |
| `api_system.cj` | 内置 `system:*` 命令（`version` / `ping` / `echo` / `devtools` / `host`） |

「FFI 归谁」的判据是**谁调用谁包内**：核心宿主消费的 FFI 留在根（`log_bridge` / `clipboard_bridge`），
插件自用的 FFI 随插件走（如 `src/plugins/sqlite/sqlite_ffi.cj`）。

## 4. `app.cj` 的四个分片

`app.cj` 原本 969 行、把「描述应用」「启动应用」「收发事件」「预置宿主能力」混在一个文件里。
现在按职责切成四个文件，**同一个包、同一个类**——对外 API 一行未变：

| 文件 | 放什么 | 判据 |
| --- | --- | --- |
| `app.cj` | 类声明与字段、`init`、配置与注册（`window` / `assets` / `addWindow` / `register` / `plugin` / 能力 / scope）、`hostOf` / `quit` / `waitForExit` | 「应用是什么」与**接口成员** |
| `app_run.cj` | 一次 run 的节奏：`prepare` → 插件 shim → 默认窗口 → 附加窗口 → 等退出 → 收宿主编；外加清单导出 | 「怎么跑起来、怎么退出去」 |
| `app_events.cj` | 后端投前端、前端订阅、shell 事件钩子与分发、`deliverJs` | 只围绕**事件**这一个职责 |
| `app_host_ops.cj` | 菜单 / 托盘 / 快捷键 / 拖放 / 可见性 / 日志的预置 API 与运行期微调 | 「必须赶在页面加载前定稿」那一类 |

切分不追求「文件行数相等」，只要求**每条函数放进去之后，问一句「它为什么在这里」有一句话的答案**。

## 5. 同包 `extend` 拆分的四条边界（实测，2026-10-24）

想在同一个类上换成多文件，仓颉只给 `extend`。四条边界都是编译期能撞到的：

1. **`extend` 碰不到 `private` 成员**——`private` 是**类作用域**，跨文件的 `extend` 读不了
   （报 `error: can not access field 'n'`）。所以被跨文件使用的字段与方法只能放宽成**包内可见**
   （不写修饰符）。代价是包内封装变弱；对包外（应用 / 插件 / 单测子包）完全不可见，对外 API 不变。
2. **`extend` 能访问类体成员**，方向是单向的：`extend` → 类体可以，**类体 → `extend` 报
   `'<成员>' is not a member of class '<类名>'`**。所以「类体方法调用 extend 新增方法」这条路不能走。
3. **接口成员只能由类体实现**：`AppHost` 要求的 `quit` / `waitForExit` / `hostOf` 写在 `extend` 里
   不算实现，编译报 `unimplemented interface function 'waitForExit'`——它们必须留在类体内，
   连带的判定函数（如 `allWindowsExited`）也只能同侧。
4. **多个 `extend` 块之间可以互调**（同一文件或不同文件都行），这是四个分片能成立的前提。

`app.cj` 因此保留了「字段 + 接口成员 + 只被类体调用的判定」这一小撮，其余按职责分出去。
新增成员时先看归哪一片，再确认它**不被类体调用**（第 2 条）——否则放回 `app.cj`。

## 6. 依赖方向与禁止项

```
app.cj ─┬─→ app_run.cj / app_events.cj / app_host_ops.cj   （extend，同包）
        ├─→ host.cj / ipc_hub.cj ─→ capability.cj          （单向）
        └─→ window.cj / window_registry.cj
```

- **单向**：`app` → `host` / `ipc_hub` → `capability`；禁止反向与循环依赖（要跨层协作就注入回调）。
- **核心不引用插件**：`src/plugins/*` 单向依赖根包；根包 import 插件会让「只用一个插件」
  把整包对象拉进链接（拆子包的初衷就是解这条）。
- **平台差异只有两处**：`@When` 条件编译与 `native/bridge_*.c`。上层不写运行期平台分支。
- **新增文件按单一职责拆**：一个文件能一句话说清「它管什么」才算合格。

## 7. 三条不能碰的硬约束

1. **`src/tests/` 必须留在 `src/` 下**——`cjpm` 不扫描顶层 `tests/` 目录，挪出去会静默变成 0 个用例。
2. **`src/plugins/plugins.cj` 不能删**——目录里没有 `.cj` 文件时 `cjpm` 不递归扫子目录，
   删了它所有插件子包会静默消失（`scripts/check-static.sh` 第 6b-2 项白名单它）。
3. **平台判据用 `@When[env == "ohos"]`**——鸿蒙的 `os` 取值是 `"Linux"`、`arch` 也不可用
   （桌面 aarch64 Linux 同样是 `aarch64`），详见 `native/platforms/harmonyos/README.md`。

## 8. 什么时候还该拆 / 不该拆

**该拆**（成本低、收益确定）：一个文件 > 800 行且职责能用一句「A 与 B 是两件事」拆开；
新增的一大组函数只围绕一个职责，且不被类体调用（§5 第 2 条）。

**不该拆**（现在不划算）：按目录把根包拆成多个子包。根包这批文件互相引用（`ipc_hub` / `host` / `app` /
`plugin` / `capability` 之间是双向的），而子包**不能回引父包**——那会是一条 `cyclic dependency`。
真要拆得先抽 trait 打破环，再按 3.0.0 的不兼容变更流程走，并且要跑 Windows / Linux / 鸿蒙三平台实机取证。
**为观感付这个代价不值得**：现在拆到位的是 `platform/`、`plugins/<名字>/`、`tests/` 这三处真正能成包的地方。
