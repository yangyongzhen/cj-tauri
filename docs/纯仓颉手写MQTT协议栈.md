# 纯仓颉手写 MQTT 3.1.1：二进制协议栈没有想象中可怕

> 本文是 cj-tauri（仓颉版 Tauri，[AtomGit](https://atomgit.com/qq8864/cj-tauri)）开发手记系列的第三篇。代码在仓内 `src/plugins/mqtt/`（`mqtt_codec.cj` 编解码 661 行 + `plugin_mqtt.cj` 插件 1446 行），E2E 对端证据见 `examples/mqtt-client`。QQ 技术交流群：92381027。

## 为什么不找现成库

给 cj-tauri 加 MQTT 能力时，第一个念头是找仓颉的 MQTT 库——找了一圈没有。第二个念头是包一层 C 库（libmosquitto 之类），但这违背了框架自己的纪律：**平台差异才允许进 C 桥，业务协议不进**。MQTT 是纯应用层协议，写进 C 桥等于把一份和平台无关的代码摊到两份构建脚本里维护。

于是只剩一条路：自己写。MQTT 3.1.1 的报文格式只有十几种包、定长头 + 可变头 + 载荷三层，比 HTTP 简单，比 WebSocket 直白。真正要花心思的不是格式本身，而是仓颉是一门**有 GC、有协程栈、字节语义和 C 不同**的语言——下面按坑的重量排序。

## 一、字节语义：迭代 String 得到的是 UInt8

这是本仓反复入档的第一坑，写协议栈时它以最高烈度回归：仓颉迭代 `String` 得到的是 **UTF-8 字节**（不是码点、不是 Rune），`String.size` 同样是**字节数**。

对 MQTT 这反而是利好：协议里所有长度字段（剩余长度、主题名长度、载荷长度）都是**字节计数**，中文主题「车间/温度」按字节算长度才对。但有两处要清醒：

- 判断「是不是合法主题通配符」（`+` / `#`）时，逐字节比 `'+'`（0x2B）即可，ASCII 字符在 UTF-8 里不与前导字节混淆——这是 UTF-8 自设计保证的，可以放心按字节扫；
- 报文里「2 字节大端长度 + UTF-8 字符串」的读取要自己拼：`(b[i]<<8) | b[i+1]` 得到长度，再取后面那么多字节。**没有现成的 `readU16`**，这类小函数我们写了六个，全部 `public`，单测直接构造字节序列喂进去。

剩余长度编码（MQTT 特有的变长整数，每字节低 7 位有效、最高位续传）是全协议唯一有点「算法味」的地方，正反两个方向各 15 行，配了 12 个边界用例（1 字节到 4 字节的每一条边界：127/128、16383/16384、2097151/2097152、268435455 溢出拒收）。

## 二、QoS 1/2 的状态机：用 SyncCounter 计数、用 Future 等结果

协议栈的「难」不在编码，在**未决报文的管理**：QoS 1 的 PUBLISH 要等 PUBACK，QoS 2 要走 PUBREC→PUBREL→PUBCOMP 四步握手，中途还可能重发。我们的落法：

- 每个未决报文记 `(packetId, 发出时间, 状态)`，单飞线程扫描超时重发；
- 仓颉并发原语比想象中少：等待并发任务**不要去 `Thread` 上找 `join`**——`spawn { => ... }` 返回 `Future<T>`，取结果用 `future.get()`；计数用 `SyncCounter`（加一是 `add(1)` 不是 `inc()`）。这些 API 形状和主流语言不同，第一次写全靠猜是猜不对的；
- **同步连接命令在 worker 线程上阻塞等 CONNACK**（带超时），而命令分发本来就是异步的（`IpcHub.handleInvoke` 校验后 spawn 到 worker）——所以页面等 `mqtt:connect` 的 promise 不会冻 UI，这是框架白送的。

## 三、双 socket 与双通道：订阅消息怎么到页面

发布订阅我们用了**两条 TCP 连接**：一条给「命令面」（connect/subscribe/publish 请求-应答式），一条给「数据面」（收 PUBLISH 推送）。单连接也能做，但把请求-应答和异步推送挤在同一个读循环里，报文路由的状态机会缠在一起；分开后每条连接的读线程职责单一，代价是多一个文件描述符——对调试工具这个定位，值得。

页面侧同样双通道：

- **事件**：`mqtt:message` 事件实时回投每条收到的 PUBLISH——适合滚动时间线；
- **recent 取走即清**：页面来不及听时（初始化中、事件风暴），报文缓存在插件侧，`mqtt:recent` 命令一次取走并清空。**「事件 + 缓冲回放」两条腿**比单靠事件可靠——事件丢了就是丢了，缓冲兜底。

这条经验后来成了仓内插件的一致范式（Redis 插件的消息通道同款）。

## 四、对端证据：自写 mock broker，两边日志对账

「我能编码 PUBLISH」不等于「broker 认」。E2E 用了仓内一贯的取证法：**自写一个 ~200 行的 mock broker**（Python），把「客户端真的连上、真的订阅、broker 真的收到发布」落在**应用进程之外**的对端日志里。27 条断言两侧对账：应用侧说「我发了」，对端日志必须有 `rx topic=... qos=1 payload=...`；对端推了消息，应用侧时间线必须出现同一条。QoS 2 的四步握手、保活 ping、断线重连，各有对端证据。

这里有个取证细节值得单说：**needle 别跨字段**。最初断言写的是整行前缀 `PUBLISH rx topic=x qos=1 payload=y`，实际日志中间还夹着 `retain=/dup=/pid=/bytes=`，字面量匹配当场落空，表象是「对端没收到报文」——第一遍 23/25 全栽在这一条。needle 截到字段边界为止，载荷另立一条断言。

## 五、零依赖的代价与收益

代价：`mqtt_codec.cj` 661 行 + 插件 1446 行，加单测与 E2E，这轮投入约等于包一个 C 库的三倍。

收益：**仓颉生态多了一份纯仓颉的 MQTT 3.1.1 实现**（编解码层完全独立于插件，可单独复用）、构建零外部依赖（不用系统装 libmosquitto、Windows 不用抄 DLL）、协议行为完全在仓内可调（比如 mock broker 演练的边界行为）。对「国产语言生态需要原始积累」这个阶段，第三条收益比前两条都值钱。
