# 设计决策记录（ADR）

> 本文件记录**已经生效的架构与工程选择**：决定是什么、当时还考虑了什么、为什么这么选、代价在哪、
> 什么条件出现时应该重新评估。它回答的是「为什么长这样」，与 `docs/需求追踪.md`（现在做到哪了）、
> `docs/进度记录.md`（哪一轮做了什么）互为补充。
>
> 记录口径：每个决策一节，标题是**结论**不是话题；「代价」必须写真实成本（含已经踩出来的坑），
> 不允许只写好处；「复评触发」写可观察的条件，不写「将来再看」。**只写本仓自己的判断依据，
> 不写与其他项目的比较**——引用外部做法时只描述做法本身。

## D-001 宿主用同进程 C 桥

**状态**：生效。

**决定**：仓颉侧通过 `foreign func` 直接调用 C 桥（`native/core` + `native/platforms/<os>`），
WebView 与仓颉运行时同处一个进程；不引入「独立宿主进程 + 跨进程报文传输」的形态。

**当时考虑的备选**：把宿主（窗口 + WebView + 平台事件）做成独立进程，框架侧通过 JSON Lines
经 stdin/stdout 或 socket 通信。

**为什么**：目标场景是「仓颉后端 + 系统 WebView 的桌面应用」，同进程省掉序列化、进程生命周期、
超时与重启预算三块复杂度，命令调用是一次函数调用的开销，调试可以直接 gdb 进桥。
跨进程形态的收益（WebView 崩溃不带走宿主、把 WebView 当低信任边界）在本场景不构成主要风险面：
WebView 加载的是本应用自己的页面，远程内容一律走能力清单管控。

**代价（真实的，且都已收口）**：

- 仓颉轻量线程（M:N）的堆上协程栈会被 JSC 的栈边界校验 abort → 平台调用必须在 C 桥创建的
  原生 pthread 内执行；命令 worker 只能经 `jsSink` 回投，不许直接摸 GTK/WebKit。
- Linux 退出期：`pthread_join` 等宿主线程会与运行时「停处理器」握手互等（约 1/6 概率挂死）
  → 改 `pthread_detach` + 有界轮询；等不到就保留平台状态（泄漏一次状态远比死锁安全）。
- Linux 销毁 WebKit 窗口必须留在 `gtk_main` 之外，否则退出期析构在 `g_object_unref` 里 abort。
- 把栈对象投递到 UI 线程后 `free` → `munmap_chunk()`；`g_idle_add` 回调必须返回
  `G_SOURCE_REMOVE`，否则寄存器垃圾触发 GLib 重入。

以上每条都已写进 `AGENTS.md` §4，属于「付过的学费」，换架构等于把学费重付一遍。

**复评触发**：① 接入 HarmonyOS（ArkTS 侧天然是另一进程叙事）；② 需要加载第三方可信度更低的
插件进程；③ WebView 崩溃成为用户可见的主要故障源（有证据，不是猜测）。

## D-002 IPC 报文带协议版本字段

**状态**：生效（0.8.0 起，`CJ_IPC_PROTOCOL = "1"`）。

**决定**：事件与回执信封、以及 `system:version` 的返回值，都带 `protocol` 字段，取值来自
`src/version.cj` 的单一常量。**只增字段、不改语义**，旧页面解析不受影响；删字段或改语义必须抬版本。

**当时考虑的备选**：报文不带版本，靠框架版本号间接推断；或引入完整的 schema 校验（带 schema 生成器）。

**为什么**：报文形状实际是**跨层契约**——C 桥注入的页面侧脚本要解析它、CLI 要靠它消费应用清单、
将来跨进程/跨语言形态要复用同一形状。没有版本字段时，错配只能表现为「行为悄悄漂移」；
有字段则能给出可诊断信号。完整 schema 校验对当前规模是过度设计，先要最小可诊断信号。

**代价**：常量要在三层（信封构造、`system:version`、文档）保持一致 → 用单测锁住
`system:version.protocol == CJ_IPC_PROTOCOL`；旧页面被注入的 `protocol` 字段是无害多字段，
但**任何消费方都不能假设「字段集合固定」**。

**复评触发**：出现第一处不兼容的报文形状变更（那时把版本抬到 "2" 并同步桥注入脚本、CLI、
文档，而不是就地改字段）。

## D-003 平台差异只允许出现在 `@When` 与 C 桥

**状态**：生效。

**决定**：平台分支只能落在两处——仓颉侧的 `@When` 条件编译与 C 桥的 `native/platforms/<os>/`；
IPC、能力校验、命令分发必须跨平台共用。新增宿主能力先扩 `WebViewHost` 接口，再各平台实现，
最后 C 桥加**同名同签名**导出。

**当时考虑的备选**：把平台差异在应用层用运行期 `if (platform == ...)` 散开。

**为什么**：散开之后能力校验会在两条代码路径上各有一份，安全语义迟早分叉；同名导出让上层
调用点无分叉，也让「某个平台没实现」在编译/链接期就暴露。

**代价**：跨平台文件不能按单平台的未使用告警清 import（`@When` 另一分支可能正是唯一用它的地方，
实际踩过：Windows 侧清掉 `ArrayList` 让 Linux 侧编炸）；新增平台要从照抄 Windows 桩的同名导出开始，
起步成本比「先写个分支」高。

**复评触发**：出现第三个及以上平台且同名导出维护成本明显上升时。

## D-004 能力状态分级标注，`supported` 门槛绑定可复核证据

**状态**：生效。

**决定**：需求追踪矩阵用五级状态（`planned` → `validation-only` → `experimental` → `implemented`
→ `supported`），**按能力逐个标注**而不是按平台一刀切；`supported` 的判据是「有可复核的外部证据」
（桥 stderr、截图、外部可观察行为），单测与桩自检全绿**不够**。

**当时考虑的备选**：把 `supported` 的门槛抬到「签名 + 安装器 + updater + 完整 E2E 全过」，
不满足就一律不标。

**为什么**：门槛过低会让矩阵失去意义，门槛过严同样会——如果所有条目都因为「还差签名与安装器」
而停在同一个状态，矩阵就不再能区分「已经能在真机上用的」和「只有代码骨架的」。分级标注保留区分度，
同时用「证据必须可复核」守住不吹牛这条底线；没实机验证的平台（Windows 桩）如实标 `validation-only`
并写清缺什么。

**代价**：需要人工保证每个 `supported` 都指得到证据 → D-005 用机器对账来兜。
证据是「某台机器某一天跑出来的」，不能从仓库里复现，所以必须记平台与运行时版本。

**复评触发**：发布流程（签名/安装器/updater）真正落地后，可以给「已发布平台」加一级更强的状态，
而不是把现有 `supported` 的定义整体抬高。

## D-005 实机证据 JSON 化，且证据本身过门禁

**状态**：生效（0.8.0 起）。

**决定**：实机验证的结论用 `scripts/e2e-evidence.sh` 落成
`dist/e2e-evidence/<平台>-<名字>.json`：平台、Runtime 版本、**每条断言的命中次数**、UTC 时间、
命令退出码、总览。断言按「整行前缀」在桥日志里 grep，未命中即退出码 1。
`scripts/check-static.sh` 第 7 项校验证据结构合法且 `summary.ok` 为真。

**当时考虑的备选**：继续只留日志 + 截图，靠人读；或者把证据写进 Markdown 正文。

**为什么**：日志与截图能证明「跑过」，但无法被机器对账，矩阵里「证据在哪」只能靠人记；
Markdown 正文则无法被门禁校验。JSON 让「这份证据是不是绿的、断言命中几条」变成一条命令的事。

**代价**：证据里是本机日志的绝对路径与当机版本 → `dist/` 进 `.gitignore`，证据只在本地对账，
**进仓库的仍是人的结论**；记录时必须同时写清「哪台机器、什么运行时版本」，否则半年后无法复现判断。
另一个真实代价：断言 needle 若写成会在正文里撞词的中缀，会得到假的通过 —— 所以约定用整行前缀
（`[cj-bridge]` 这类），改日志格式时必须同步核对 needle。

**复评触发**：出现第二种需要归档的证据形态（截图/性能数据）时，扩展 schema 而不是新起一个格式；
「谁来产出这份证据、能不能重跑」由 D-013 回答。

## D-006 fs scope：先 deny 后 allow，规范化后再匹配

**状态**：生效。

**决定**：能力清单可给插件写 `scopes`（`allow` / `deny` 模式表）。语义：**先 deny 后 allow**，
deny 命中即拒；allow 必须显式命中（空 allow = 该插件路径全拒）；匹配前先规范化（存在走
`canonicalize` 顺带解析软链接，不存在走词法折叠 `.` / `..`）；`**` 可以匹配零个目录
（`/a/**/b` 匹配 `/a/b`）。没写 scope 的旧清单行为不变，启动打一行提示。

**当时考虑的备选**：只做 allow 列表（无 deny）；或先 allow 后 deny；或在各插件实现里各判一份。

**为什么**：deny 优先是安全默认——用户可以「先全放开再挖掉敏感文件」（`**/id_rsa`），
反过来则做不到；先 allow 后 deny 会让 deny 形同虚设。规范化必须前置，否则 `..` 与软链接
都能绕过字符串前缀比较。判定逻辑放共享层（`src/scope.cj`）而不是平台实现，避免两平台各判一份
后语义分叉。`**` 匹配零目录是按「路径通配的通行口径」定的，否则 `$CWD/capabilities/**`
匹配不到目录本身，用户写出来的规则会在最常用的那一种形状上失效。

**代价**：`%2e%2e` 这类编码**不做**解码（当字面量文件名），因为「解码后再比较」会引入
多层编码歧义；这点与「先解析 percent encoding 再规范化」的做法不同，必须在文档与用例里写清楚，
否则会被读成漏判。Windows 侧的差异（大小写、UNC、盘符、设备路径）尚未验证，如实标 planned。

**复评触发**：Windows 实机轮里出现真实越界或误拒案例时，按案例补规则与用例，不预先猜。

## D-007 命令分发异步化，校验留在调用线程

**状态**：生效。

**决定**：`IpcHub.handleInvoke` 只做校验——「未授权 / 未注册」在**调用线程上同步拒绝**，
通过校验的命令 `spawn` 到 worker 线程执行，结果经 `jsSink` 回投。同一命令并发调用不保证顺序，
前端按 promise id 匹配。

**当时考虑的备选**：全部同步执行（实现最简）；或全异步（连校验也排队）。

**为什么**：同步执行会让慢命令（`shell:exec`、原生对话框）钉住宿主 UI 线程；把校验也异步化
则会让「未授权」的拒绝延迟并且可能乱序，安全信号的即时性比吞吐更重要。worker 绝不直接碰
GTK/WebKit，只能经 `jsSink` 回投——否则触发 D-001 里的栈边界 abort。

**代价**：并发调用无序，需要前端按 id 匹配（有单测锁）；没有流式输出、没有超时与取消，
所以命令里不能等长驻或交互式进程；handler 抛异常必须自己打一行 stderr（`command rejected` /
`command failed` 两种前缀便于分流），否则「没反应」时端到端日志里毫无凭证。

**复评触发**：出现第一个真正需要「可取消 / 可超时」的长任务（如网络下载、大文件复制）时，
在报文层补取消语义（而不是在某个插件里各写一套）。

## D-008 插件只声明「我提供什么」，放行一律由能力清单决定

**状态**：生效。

**决定**：插件通过 `Plugin` 接口声明 `name()` / `commands()` / `events()` / `permissions()` /
`jsShim()` / `scopeAware()`；装配时框架把命令注册成 `<插件名>:<短名>`，**但不自动放行**。
是否可用完全由应用 `capabilities/*.json` 的 `commands` / `events` / `permissions` / `scopes` 决定。

**当时考虑的备选**：插件自己声明所需权限并自动生效。

**为什么**：插件是第三方代码，让它自己决定权限等于把授权交给被授权方。声明与放行分离后，
「装了这个插件」与「这个插件能做什么」是两个独立决定，应用可以只授权其中一部分。
命名权限集（`fs:readonly` 这类）只是把成员列表打包，展开后与明文名字**同权**，不额外提权。

**代价**：新增命令/插件要三处联动（实现 + 装配 + 清单声明），漏一处就得到
`command not allowed` / `command not registered`——这是刻意保留的显式成本；
旧清单全写明文的行为不变，但会打一行 `warnUnscopedPlugins` 提示，用户会看到两套写法并存。

**复评触发**：若将来出现「插件市场」形态，需要在那之上再加一层签名与发布者信任，而不是放松这一层。

## D-009 插件实现走 `src/plugins/` 单个扁平子包

**状态**：生效。

**决定**：所有插件实现与只被插件使用的 FFI 桥放 `src/plugins/`（`package cjTauri.plugins`）；
`src/` 顶层只留框架核心。核心宿主消费的 FFI 声明留在核心包（判定标准是「谁调用谁包内」）。
`scripts/check-static.sh` 按**包边界**守这条线，而不是靠文件名前缀。

**当时考虑的备选**：每个插件一个子包（多包 workspace）；或继续平铺在 `src/`。

**为什么**：平铺没有物理边界，插件迟早会开始引用核心内部符号；每个插件一个子包则把
「跨包可见性」问题放大 N 倍（子包可见父包的 public，反向禁止）。单个扁平子包拿到绝大部分收益：
边界可被门禁检查、内部符号（`HostGlobals` / `IpcHub(`）在子包里一眼可见，而跨包摩擦只有一处。

**代价**：跨包后不再同包可见，单测与示例直接构造的符号必须 `public`（编译器会逐个点名）；
`clipboard_bridge.cj` 这类 FFI 留在核心包，属于「归属要按调用方判断」的例外，需要在文档里写清判据。

**复评触发**：插件数量增长到子包内文件名冲突或编译时间明显上升时。

## D-010 CLI 判「命令可用」以命令自身退出码为准

**状态**：生效。

**决定**：`cj-tauri doctor` 检查 cjc / cjpm / pkg-config / gcc 时，一律执行命令看**退出码**，
不用路径存在性判断；退出码 127 单独提示「二进制在 PATH 里但运行时加载不了」（缺 `LD_LIBRARY_PATH`）。
doctor 自身退出码：0 = 必需项全过（`warn` 不算失败），1 = 有 `FAIL`。

**当时考虑的备选**：用 `command -v` / 路径存在性判断，快且无副作用。

**为什么**：cjc / cjpm 本身是仓颉程序——二进制在 PATH 里但没设 `LD_LIBRARY_PATH` 时照样加载不了运行时
（exit=127、无输出），而路径查得到。**「存在的文件」与「能跑的命令」是两件事**，判据必须用后者；
这条同时也是本仓一条更普遍的纪律：判工具可用性看副作用与退出码，不看声明。

**代价**：doctor 会真的启动子进程（有耗时、有副作用），所以它不适合放进每次构建的热路径；
另外输出的对齐是手工拼的，`warn`/`FAIL` 的长度不同会对不齐——可读性优先，不引入格式化依赖。

**复评触发**：doctor 被接进 CI 且耗时成为问题时，改为并行探测或按需探测。

## D-011 托盘能力暂缓

**状态**：生效（裁定）。

**决定**：不做托盘。`docs/需求追踪.md` 的 PLG-009 保持 `planned`，能力位如实报 `tray=0`。

**当时考虑的备选**：Linux 侧引入 `libayatana-appindicator3` 依赖实现托盘；或只做 Windows 侧。

**为什么**：托盘的价值（后台常驻与快捷入口）对本仓当前的示例与用户面不构成刚需，而 Linux 侧
要多一个系统级三方依赖，只做 Windows 又会造成能力位在两个平台语义不一致——**半做的托盘比没有托盘更糟**。
菜单与文件拖入这类「必须赶在页面加载前定稿」的能力已经交付，托盘留到有明确需求时再排。

**代价**：桌面应用常见的三项（菜单/托盘/快捷键）少一项，用户可能需要自行用窗口菜单替代；
能力位里 `tray=0` 是长期的、显式的不支持，而不是遗漏。

**复评触发**：出现真实用户需求（且愿意接受 Linux 侧的三方依赖），或鸿蒙形态需要托盘等价物时。

## D-013 实机验证过程资产化：仓内 fixture + 平台守卫

**状态**：生效（0.8.0 起）。

**决定**：实机验证的**过程**（而不只是结论）收进仓库，四个部件各管一件事：

- `scripts/e2e/lib.sh`：公共层——平台守卫、断言登记、证据收口、应用启停（切工作目录、日志重定向、
  有界轮询就绪、先子后父递归 kill）；
- `scripts/e2e/fixture-app/`：探针应用（页面**从磁盘读**，改探针页不用重编译仓颉），
  探针命令 `probe:echo` 把一轮往返的结论打一行 stderr；
- `scripts/e2e/test-<平台>-*.sh`：平台入口，声明自己的目标平台；
- `scripts/e2e/run-all.sh`：聚合入口，把**通过 / 跳过 / 失败分开计数**，并标注「本轮没有任何平台真的跑了」。

配套纪律（`check-static` 第 9 项守前两条）：入口必须 `source lib.sh`、必须调用 `e2e_require_platform`；
宿主平台与目标平台不匹配时**默认 FAIL 而不是跳过**，确实要在别的机器上跑全套才显式
`CJ_TAURI_E2E_SKIP_OTHER=1`，CI 用 `CJ_TAURI_E2E_REQUIRE=linux` 声明「本机必须跑」。

**当时考虑的备选**：① 继续每轮写 `/tmp` 脚本（只把结论 JSON 化，即 D-005 的状态）；
② 引入通用测试框架（bats / pytest 一类）做驱动。

**为什么**：现写脚本的问题**不是麻烦，而是不可复现**——证据 JSON 里记了平台与断言命中次数，
但生成它的脚本已随 `/tmp` 消失，既无法重跑，也无法在后续改动后回归；断言沉淀不下来，
同类验证每轮都要重新想一遍。而「跳过」与「通过」在退出码上同形（都是 0），
这正是本仓历史上出过假绿的地方，所以平台判定必须由公共层统一负责，并且**把错机变成失败**。
不引入通用框架：驱动层真正要的能力就三样（起进程 / 轮询日志 / grep 计数），
而框架还要重新解决 Xvfb 回落、进程树收尾、证据格式这些本仓已有答案的问题。

**代价**：多一个 cjpm 工程（探针应用）要跟着框架一起编；断言 needle 绑定日志措辞，
改日志格式要同步改入口（与 `AGENTS.md` §4「改日志格式时一并核对断言 needle」同一约定）；
探针应用与示例一样依赖「工作目录 = 工程根」才能读到 `capabilities/` 与 `ui/`。
落地时踩到两处真坑（已收进 `AGENTS.md` §4 与 skill）：`DISPLAY` 存在 ≠ 显示器可用
（要**真探测**再决定是否回落 Xvfb），以及 stdx 动态库不在 SDK 目录里（漏它时应用启动即退、
只留一行 `cannot open shared object file`）。

**复评触发**：入口数增长到需要参数化（矩阵）或并行执行时，再考虑上框架；
出现第二类证据形态（截图 / 性能）时扩 D-005 的 schema 而不是新起格式。

## D-014 MQTT 以框架插件交付，协议用纯仓颉 `std.net` 自实现

**状态**：生效。

**决定**：MQTT 客户端按框架插件交付（`src/plugins/plugin_mqtt.cj`，插件名 `mqtt`；命令
`connect` / `subscribe` / `unsubscribe` / `publish` / `disconnect` / `status` / `recent`；
事件 `mqtt:message` / `mqtt:state`）。协议实现落在仓颉侧：用标准库 `std.net` 的 TCP socket
自己写 MQTT 3.1.1 的报文编解码与 QoS 状态机，**不进 C 桥**。

**当时考虑的备选**：①放应用层（示例自己 `register("mqtt:connect", …)`），框架不碰协议；
②协议下沉到 `native/core`，照 serial 走 `cj_bridge_*` 导出；③引入第三方仓颉 MQTT 包。

**为什么**：
- 先例已经定在这儿：`serial` 就是框架插件，命名空间命令 / 事件回投 / 命名权限集 / 能力清单
  这套机制对**协议类能力**完全够用。放应用层等于让每个想连 MQTT 的应用重写一遍协议，
  也拿不到框架的单测与门禁。
- 协议本身**没有平台差异**（纯字节编解码 + TCP 读写）。按 D-003 的反面：没有平台差异就没有
  理由下沉到 C 桥——下沉要多一份 C 实现、多一处平台守卫、多一组 FFI 声明，换来的只是「C 快一点」，
  而 MQTT 的性能瓶颈在网络上，不在编解码。
- `std.net` 已在 `examples/modbus-poll` 实证可用（`TcpSocket(host, port)` / `connect(timeout:)` /
  `readTimeout` / `writeTimeout` / `noDelay` / `read` / `write` / `close`），MQTT 要的原语一个不缺；
  超时读还让读线程能周期性地做保活与关闭检查，不必额外引入 select。
- 第三方包路线不成立：仓颉生态里没有可用的 MQTT 实现，且 AGENTS §3 要求引入第三方仓颉包先登记
  ——为一个几百行的协议背一个依赖不划算。

**代价**：协议与它的维护成本留在框架里（含 QoS 1/2 状态机）；socket 能力由框架插件持有，
因此**应用不在能力清单里显式声明就完全碰不到网络**（最小权限不破，但写错清单时的排查面变大，
靠 `warnUnauthorizedPlugins` 的启动提示兜）。边界如实：只做 **MQTT 3.1.1（协议级别 4）的明文 TCP**，
**不做 TLS（1883 之外的 MQTTS）、不做 WebSocket 传输、不做 MQTT 5.0 的属性与原因码**；
连不上时给明确错误，不静默重试。

**复评触发**：出现 MQTTS / WebSocket 传输或 MQTT 5.0 的真实需求；或协议实现膨胀到需要独立分发
（届时拆成独立仓颉包并按 AGENTS §3 登记）。

## D-015 调试类能力同时给事件通道与可拉取缓冲

**状态**：生效。

**决定**：收报文同时走两条路——推 `mqtt:message` 事件（前端实时列表），并写入有上限的环形缓冲，
由 `mqtt:recent` 拉取并清空（兜底 + 对账）。示例页面以事件为主，`recent` 用于「失活回来补齐」
与无人值守脚本取证据。

**当时考虑的备选**：只推事件；只做轮询拉取（照 `examples/modbus-poll` 的 `mb:trace`）。

**为什么**：两条路各自的缺口都很具体。只推事件时，页面没在能力清单里声明 `events`、或标签页失活 /
重载，消息就静默丢了，而调试工具最不能接受的就是「日志里没有」被读成「没发生」（本仓吃过这个教训）。
只轮询则按固定间隔 invoke，既拉长看到消息的延迟，又把「有没有消息」变成轮询频率的函数。
同一份缓冲既供事件又供拉取，代价只是同一条消息多投一次。

**代价**：消息在内存里留一份（上限 500 条，单条正文按 256 KiB 截断），高吞吐订阅下缓冲会持续被打满
（**如实上报丢弃计数，不假装无损**）；同一条消息页面可能看到两次（事件一次、`recent` 一次），
约定用报文里的 `seq` 去重，示例页面照此实现。

**复评触发**：出现真实高吞吐场景（>1000 msg/s）时，把拉取通道改成可配置开关，且只保留统计、
不保留正文。

## D-016 Redis 客户端以框架插件交付，只给具名命令、不给原始命令透传

**状态**：生效。

**决定**：Redis 客户端按框架插件交付（`src/plugins/plugin_redis.cj`，插件名 `redis`；RESP2 编解码
单独一层 `src/plugins/redis_codec.cj`）。协议用标准库 `std.net` 的 TCP socket 自己实现，**不进 C 桥**。
命令面**只给具名命令**（连接会话、服务器信息、键空间、按类型的读写、发布订阅五组，命令名 `<插件名>:<短名>`），
并附两个命名权限集：`redis:readonly`（连接 + 查询 + 读取 + 订阅）与 `redis:default`（全量）；
事件 `redis:message`（订阅消息）/ `redis:state`（连接状态变迁）。
**不提供「原始命令透传」通道**（即不给一条能执行任意 Redis 子命令的命令）——这一条是明确裁定的边界。

**当时考虑的备选**：①只在示例内自实现（照 `examples/modbus-poll` 的做法，框架一行不动）；
②协议下沉 `native/core` 走 `cj_bridge_*`（照 serial）；③引入第三方仓颉 Redis 包；
④给一条 `redis:command` 透传通道，把 CLI 式「任意命令」搬进页面。

**为什么**：
- 形态判据同 D-014：协议**没有平台差异**（纯字节编解码 + TCP 读写）就没有理由下沉 C 桥；
  `std.net` 的原语已被 `examples/modbus-poll` 与 MQTT 插件两处实证够用。
- 与 mqtt 的区别在**能力面**：一条 Redis 连接能干的事跨的权限域比 MQTT 宽得多（读、写、删、管理混杂）。
  所以「框架插件」与「命令面收窄」是配套的两个决定：插件只声明「我提供什么」，放行仍由能力清单决定；
  而**没有透传通道时，「能用哪些命令」就等于清单里那几个名字**——最小权限模型不会因为一条通配通道失效。
- 放应用层等于让每个想连 Redis 的应用重写 RESP2 与连接管理，也拿不到框架的单测与门禁。
- 第三方包路线不成立：仓颉生态里没有可用的 Redis 实现，且 AGENTS §3 要求引入第三方包先登记
  ——为几百行协议背一个依赖不划算。

**代价**：协议与它的维护成本留在框架里（RESP2 编解码 + 命令通道与订阅通道两条线程）；
socket 能力由框架插件持有，**应用不在能力清单里显式声明就完全碰不到网络**（最小权限不破，
写错清单时排查面变大，靠 `warnUnauthorizedPlugins` 的启动提示兜）。
命令面收窄有**真实的可用性成本**：页面上做不了「任意命令」，遇到没有被具名化的子命令
（`OBJECT`、`MEMORY USAGE` 的细分、模块命令等）只能改框架补命令，或由应用自己另开通道
（那就享受不到插件的能力清单）。这是刻意换来的最小权限，不是遗漏。
边界如实：只做 **RESP2**（不做 RESP3 的 map/set/push 与 `HELLO 3`）、只做**明文 TCP**
（不做 TLS `rediss://`）、不做 **Cluster / Sentinel**（不跟随 MOVED/ASK 重定向、不做哨兵发现）、
不做 `MONITOR`、不做导入导出（`DUMP`/`RESTORE`）；支持 `SELECT` 多库，但不做集群下的多库。

**复评触发**：出现 RESP3（`HELLO 3` / 客户端缓存）或 TLS `rediss://` 的真实需求；
或「缺某条子命令」连续几轮都要为同一个子命令改框架——届时先补具名命令，而不是开一条透传口子。
