## 1. 环境搭建（已验证）

### 1.1 仓颉 SDK 1.0.5 安装

- 官方下载页 `/download/1.0.5` 的下载链接是 JS 动态加载的，实际直链格式：
  ```
  https://cangjie-lang.cn/v1/files/auth/downLoad?nsId=142267&fileName=cangjie-sdk-linux-x64-1.0.5.tar.gz&objectKey=698acf46bd66ae22b62330b0
  ```
  无需登录即可下载（2026-08 验证）。`objectKey` 各版本不同，可从下载页 JS bundle
  `https://csdnimg.cn/release/devpress-cangjie/public/js/chunk/organization/download/version.*.js` 中 grep 出全部版本直链。
- 解压到 `/opt/cangjie/cangjie`，目录结构：`bin/cjc`、`tools/bin/cjpm`、`runtime/lib/linux_x86_64_cjnative/`、`lib/`。
- **环境变量（必须）**：
  ```bash
  export CANGJIE_HOME=/opt/cangjie/cangjie
  export PATH=$CANGJIE_HOME/bin:$CANGJIE_HOME/tools/bin:$PATH
  export LD_LIBRARY_PATH=$CANGJIE_HOME/runtime/lib/linux_x86_64_cjnative:$CANGJIE_HOME/third_party/llvm/lib:$LD_LIBRARY_PATH
  ```
  缺 `LD_LIBRARY_PATH` 时 cjc/cjpm/产物都报 `libcangjie-runtime.so: cannot open shared object file`。
- 验证：`cjc --version` → `Cangjie Compiler: 1.0.5 (cjnative)`；`cjpm --version` → 1.0.5。

### 1.2 桌面 WebView 依赖（Linux）

- WebKitGTK 4.1 + GTK3 dev：`apt-get install -y libwebkit2gtk-4.1-dev libgtk-3-dev`
- 验证：`pkg-config --modversion webkit2gtk-4.1 gtk+-3.0`
- 服务器环境无 GPU：WebKit 自动回退软件渲染（`libEGL warning: DRI3 error` 无害）。
- **X display 可用性**：`DISPLAY=localhost:10.0` 可直接跑 GUI（本机已验证）。

### 1.3 stdx 扩展标准库（提供 JSON）

- 仓颉 1.0.5 **标准库无 `std.json`/`std.serialize`**！JSON 解析/序列化在 stdx 扩展库。
- 用官方技能库装配脚本（自动按 cjc 版本下载匹配 stdx 并写 cjpm.toml）：
  ```bash
  python /path/to/CangjieSkills/scripts/setup_stdx.py --project <project-root>
  ```
  stdx 1.0.5.1 装到 `~/.cangjie/stdx/`，cjpm.toml 自动加 `[target.x86_64-unknown-linux-gnu.bin-dependencies]`。
- JSON API（stdx.encoding.json）：
  - 解析：`JsonValue.fromStr(s)`（语法错抛 JsonException；1.0.5.1 接受 0x/0b/0o 前缀，不能当严格校验器）
  - 取值：先 `kind()` 判别形态，再 `asObject()/asArray()/asInt()/asString()/asBool()`，形态不匹配抛异常
  - 对象：`JsonObject().put(key, JsonValue)`；读取 `obj.get(key): Option<JsonValue>`（`operator []` 缺键抛异常）
  - 序列化：`toJsonString()`（带缩进）；`toString()`（紧凑）
  - 构造字面量：`JsonString(s)` / `JsonInt(i)` / `JsonBool(b)` / `JsonNull` / `JsonArray(list)`

## 2. 仓颉语言语法要点（实测）

| 主题 | 结论 |
|---|---|
| 包名 | 必须小驼峰（`cjDemo`），`cjpm-demo` 之类含连字符的会被拒 |
| `type` | **关键字**，参数名不能用（用 `` `type` `` 转义或改名 wtype） |
| 顶层变量 | 不允许 `static` 修饰；用类静态成员：`class G { static var x: Int64 = 0 }` |
| `LibC.malloc<T>` | **返回 `Option<CPointer<T>>`**（文档写 CPointer，实测 Option），需 `if let x <- opt` 解包；`LibC.free` 收 `CPointer<UInt8>` |
| if-let | 语法是 `if (let x <- expr)`；多绑定 `if (let a <- x; let b <- y)` |
| Option 解包 | `getOrThrow()` / `??` / 模式匹配 `case (Some(a), Some(b)) =>` |
| unsafe | 调用 foreign 函数必须在 `unsafe {}` 块内；`@C` 回调体内也要 |
| `@C` 回调 | 顶层 `@C func` 可直接作为 `CFunc` 传给 foreign；回调不能捕获闭包，经全局/静态状态中转 |
| `CFunc` 签名 | 必须与 C 侧实际调用约定一致；GObject 信号回调统一声明 3 参 `(CPointer<Unit>, CPointer<Unit>, CPointer<Unit>)` |
| CString | `LibC.mallocCString(str)` 创建，`.toString()` 转 String（非法 UTF-8 抛异常），用完 `LibC.free` |
| stderr 输出 | `eprint("...")`（std.core，默认 flush）；`println` 走 stdout 有缓冲，崩溃前可能看不到 |
| sleep | 顶层 `sleep(dur: Duration)`；`Duration.millisecond * 100` 构造 100ms（`Duration(sec, nanos)` 构造签名不直观） |
| unittest | `@Test` 宏（1.0.5）；断言用 `@Assert(actual, expected)`（**没有 assertEquals**） |
| 整数转 hex | 无现成 `toHexString`；可 `UInt64(x).toString()` 拿十进制 |

## 3. 核心坑：仓颉 cjnative + WebKit/JSC 崩溃（最关键）

### 3.1 现象

仓颉程序（`cjpm` 构建的 cjnative 可执行）中直接调用 webkit2gtk：
- 创建 WebView / 执行 JS 时 **SIGABRT**，堆栈：
  ```
  WTFCrashWithInfoImpl ← JSC::sanitizeStackForVM ← JSGlobalContextCreateInGroup
  ```
- 或 webkit 内部 `Aborted`（`webkit_web_view_load_html` 路径）。

### 3.2 根因（已用探针证实）

- 仓颉线程是 **M:N 用户态轻量级线程**（Maple 运行时），`main` 也在**堆上分配的协程栈**执行。
- 实测：`pthread_getattr_np` 报告主线程栈 `base=0x7ffd... size=8MB`，而仓颉 `main` 内实际 SP=`0x770f...`（堆地址），**SP 不在 pthread 栈范围内**。
- JSC 的 `sanitizeStackForVM` 用 WTF::Thread 记录的线程栈边界校验当前 SP，不匹配 → abort。
- 佐证：纯 C 程序（同机同 X）跑 webkit 完全正常；C 程序 dlopen 仓颉运行时再跑 webkit 也正常（主线程未被 MRT 包装）。

### 3.3 解决方案（已验证可行）：C 桥 + 原生 pthread

```
仓颉 main（协程栈，仅装配逻辑）
   │ FFI 调用
   ▼
C 桥 libbridge.so
   │ pthread_create 原生线程（标准 8MB 栈，SP 合法）
   ▼
GTK 线程：gtk_init → 建窗口 → WebView → 注入 JS → gtk_main
   │ 消息回调（GTK 线程内）
   ▼
C 桥转发 → 仓颉 @C 回调（CJ_MCC_C2NStub 跨线程进入仓颉，实测安全）
```

**铁律：所有 WebKit 调用（创建、load_html、run_javascript）必须在 GTK 原生线程内执行**。
仓颉侧要执行 JS 时，经 C 桥 `g_idle_add` 投递到 GTK 线程，不能在仓颉线程直接调。

### 3.4 工程要求

- C 桥编译：`gcc -shared -fPIC -fstack-protector-all bridge.c -o libbridge.so $(pkg-config --cflags --libs webkit2gtk-4.1)`
- cjpm.toml：`link-option = "... -lbridge -L native"`；运行时 `LD_LIBRARY_PATH` 指到 libbridge.so 目录
- **注意**：C 代码里不要用 C++ lambda（gcc 编译 C 会失败，且 grep error 计数易误判"成功"——必须看 `ls -la` 时间戳确认产物更新）
- `g_signal_connect` 是宏，FFI 绑定须用 `g_signal_connect_data(..., destroy_data, flags)`；`destroy_data` 传空回调不能传 null
- 需链接 `-lgobject-2.0`（g_signal_connect_data 所在库）

## 6. 实施阶段新踩坑（2026-08-21 下午，全部已解决）

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 6.1 | **String 迭代是 UInt32 码点** | `for (c in s)` 里 `c.toString()` 输出 "116" 而非 "t" | `Rune(cp).toString()` 还原字符；注意 `Rune(97)` 构造可用，`String.fromRune` 不存在 |
| 6.2 | **原生→JS 投递覆盖** | 多条 `g_idle_add` 只执行最后一条（单槽位 `g_pending_js`） | C 桥改 **FIFO 链表队列**，每条 JS 独立节点，idle 逐个执行 |
| 6.3 | **postMessage 传对象而非字符串** | `window.postMessage(obj, '*')` 前端 `e.data` 是 `[object Object]`，`JSON.parse` 抛错被 catch 吞 | 前端 `_dispatch` 兼容：`typeof e.data === 'string' ? JSON.parse : e.data`；仓颉侧直接嵌 JSON 字面量（JSON 本身是合法 JS 对象字面量） |
| 6.4 | **注入脚本时序** | user script 是 `AT_DOCUMENT_END`，页面内联 `<script>` 先执行，`__CJ_TAURI__` 未定义抛错中断后续脚本 | 前端轮询等待桥就绪：`if (!window.__CJ_TAURI__) { setTimeout(retry, 100); return; }` |
| 6.5 | **Rune/字符字面量** | `case '"'` 匹配 String 迭代的 UInt32 时永不命中 | 用码点 `case 34`（引号）/`case 92`（反斜杠）/`case 10`/`case 13` |
| 6.6 | **stdx 路径** | CLI 探测 `find ~/.cangjie/stdx -name stdx` 匹配到空 | 用 `find ... -path "*/dynamic/stdx"` 优先，`*/static/stdx` 兜底 |
| 6.7 | **文件读取** | `File.readString` 不存在 | `String.fromUtf8(File.readFrom(path))`（std.fs） |
| 6.8 | **`toJsonString` 带缩进换行** | 转义后嵌入 JS 字符串字面量报语法错误（跨行字符串） | 不转义为字符串字面量，直接作为 JS 对象字面量嵌入 `window.postMessage(<json>, '*')` |

### 6.9 调试方法论

- C 桥 stderr 日志（`[bridge]` 前缀）+ 前端 `postMessage` 探针（`cjprobe` handler）逐层定位；
- 前端依赖桥的代码必须等桥就绪，否则静默失败（无报错）；
- `println` 走 stdout 有缓冲，崩溃/被杀时看不到——诊断用 `eprintln`（stderr 即时）；
- 前端 `.then` 未触发时先查消息是否到达（`JS message` 日志）再查 `_dispatch` 分支。

### 6.10 已验证的最终链路（端到端）

```
页面 script（等待 __CJ_TAURI__ 就绪）
  → invoke('greet', {name}) → postMessage → C 桥 on_script_message
  → CFunc 进仓颉 → IpcHub.parse → capability 校验 → CommandHandler.handle
  → IpcMessage.resolve → jsSink → cj_bridge_run_js（FIFO 队列）
  → g_idle_add → GTK 线程 run_javascript → window.postMessage
  → 前端 _dispatch → Promise.resolve → .then 回调
```
