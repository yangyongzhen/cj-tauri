#### 3.2.1 同日补测：两窗回调并发（2026-10-03）

批次 2 只验到「各宿主各自 boot + 广播/定向投递」，没碰两个窗口**同时**落回调时的共享状态。探针补了两个
阶段，`run.bat` 默认模式从 8 条断言扩到 **18 条，全过、`exit=0`**（单窗对照 6 条、`CONTROL PASS`）：

| 断言（桥 stderr 逐字） | 它证明什么 |
| --- | --- |
| `window=second ASK which=second kind=info inflight=1`、`window=main ASK which=main kind=info inflight=2` | 两窗各自向**自己的宿主**要原生消息框；第二条进栈读到 `inflight=2`，说明第一条**还没出栈**（框要等人关才返回）——两个框真的同时在开。谁先进由调度决定，**不钉窗口**（首轮教训：钉顺序的断言会假红） |
| `ASK-DONE which=main ok=true`、`ASK-DONE which=second ok=true` | 两框都返回；自动确认脚本的 `FIRST batch: 2 dialog(s) open` 独立佐证「同一时刻两个 `#32770` 都开着」 |
| `CLOSE-WINDOW which=second requested` → `ALIVE second=1 main=0` → `CLOSE-PHASE alive=second=1 main=0` | 只关 `second`（0=还在跑 / 1=已退出 / 2=未注册）：应用**没有**因为少一个窗口就返回——`after run` 仍在其后打出、两宿主各一次 `host destroyed`、`exit=0` |

原生框得有人点：新增 `examples/multi-window/dismiss-dialogs.ps1`（`run.bat` 双窗模式自动起、单窗模式不起），
按「窗口类 `#32770` **且**属于目标进程」双重筛选后 Post `WM_COMMAND/IDOK`，并在**看到第一个框后等 4s**
再作答——那 4s 正是两框重叠的窗口，也是 `inflight=2` 能被观测到的原因。

**结论**：对话框状态在 C 核里本就是 **per-host**（`h->dlg_busy` / `dlg_lock` / `dlg_cur`，跨宿主不互斥）、
退出也是**逐窗判**的（`app.cj` 的 `allWindowsExited`）——这两条由「潜在」变实测事实。**当时仍未清**的是
代码层两处（不是「没测」）：`HostGlobals.onDestroy` 是静态单槽且**不在 `WebViewHost` 接口上**（应用侧
装不进去、当时恒 no-op）、文件框结果走共享单槽 `HostGlobals.dialogResult`（两窗同时开文件框时，先返回者
读到的可能是后返回者写的值——本用例用 message 框绕开了它，因为 message 框的结果就是返回值、不经槽位）。
→ **两处均于 2026-10-07 收口**（按「回调带宿主身份」做：句柄随首参回传 + 一张 `HostRoute` 路由表 +
`setDestroyHandler` 进接口），见 §3.2.9。

**本轮踩到的两个新坑**（已记进 `AGENTS.md` §4）：

1. **`.bat` 里不要用 `find`**：从 Git Bash 起 `cmd //c run.bat` 时，PATH 里 MSYS 的 **GNU find** 排在
   Windows `find.exe` 前面，`find /c /v ""` 会被它当成路径去遍历整个盘（实测把脚本挂到 300s 超时，
   输出满屏 `Permission denied`）。行数统计改用 `findstr` + `for /f`；`pause` 守卫同样换成 `findstr`。
2. **仓颉字符串插值里的 `${main}` 会撞同名函数**：`let main = …` 搭配 `"${main}"` 编译报
   `unexpected main function in string interpolation`，变量换个名字即可。

**首轮暴露并修掉的三个真 bug**（都是「代码写了、从没在 Windows 跑过」的直接后果）：

1. `native/build_win.bat` **漏编 `native/bridge_core.c`**——批次 1 抽 core 时只改了 `build_linux.sh`，
   Windows 脚本仍只编 `bridge_win.c`，桥里 `cj_core_*` 符号全缺（本机此前吃的是批次 1 之前的旧 DLL，
   所以一直「看着像能跑」）。补齐后重建，DLL 导出 17 个，与源码一致。
2. `native/bridge_win.c` 的 `wnd_proc` 在 `switch` 之后**缺 `return DefWindowProcW(...)`**——批次 1 新加的
   `WM_NCCREATE` 分支 `break` 后落到函数末尾，返回值不确定 → `CreateWindowExW` 返回失败且
   `GetLastError()=0`（**没有错误码可查**，症状是窗口根本不出现、页面从不 boot）。该处正是 mingw 那条
   `-Wreturn-type` 警告（`bridge_win.c:596`）所指；加回 return 后建窗即成功。
3. `examples/multi-window/run.bat` 第 52 行 `echo … (cjpm build) …` **括号未转义**——cmd 在 `if` 块里
   把括号当块边界，报「此时不应有 ...」后直接退出。

**探针顺手改成顺序无关**（首轮实机暴露的脆弱点）：原判定依赖「两窗都上报 `boots=2`」，对启动顺序与
各窗耗时敏感；现改为页面一 boot 就上报、驱动窗**有界等待**对端（超时才判失败），判定不再依赖固定延迟。

**顺带记下的平台事实**：`plugin-shell` 的 `shell:open` 在 Windows 上会真的拉起默认浏览器访问
`atomgit.com`；`shell:exec` 里 `uname` / `sh` / `echo` 能跑通，是因为进程继承了 Git Bash 的 `/usr/bin`
（**纯 Windows PATH 下这些命令应当找不到**，不是 bug）。

**三条踩坑（语言 / 库层，已记 `AGENTS.md` §4）**：

1. **`stdx.net.http` 的 `ClientBuilder` 不带默认 TLS**：后台是 `http://`，所以这条一直没暴露；
   一加 https 封面就整轮抛 `HttpException: TLS must be configured when HTTPS requests are sent.`
   （首轮取图全败）。修法是显式 `ClientBuilder().tlsConfig(TlsClientConfig())`（仍走系统证书库校验）。
2. **两个签名坑**：`readToEnd(resp.body)` **编译不过**（它要 `T <: InputStream & Seekable`，而 `resp.body`
   的静态类型只有 `InputStream`）→ 自己按块读到 EOF；取响应头只有 `resp.headers.getFirst(…)`（没有 `get`）。
3. **防盗链的失败形状是「HTTP 200 + 0 字节」**：图源按 `Referer` 放行，页面 `<img src>` 直连必全灭，
   且**页面侧无解**（浏览器只允许 `Referrer-Policy` *减少* Referer、不能替换；何况内联页来源是 opaque）
   → 只能由宿主命令带正确 Referer 取回、转 `data:` URL 交还。该命令参数是页面可控字符串，
   **必须做地址白名单**，否则等于开放 SSRF。

**上游接口现状（2026-10-05 实测）**：`hotmovie` / `soonmovie` / `topmovie` / `usmovie` / `detailmovie` /
`searchmovie` 可用；`newmovie` / `weekmovie` 返 `code=0 + message=403 Forbidden`（限流）；
`mvsource/{sid}` **503 / Request Timeout**（解析服务不可达）⇒ **播放链路本轮未能端到端验证**，
示例把「业务级失败」（200 但 `data` 空）与「传输级失败」（503）分开显示，并把拿到的地址列出来供复制到
系统播放器。上游恢复后 `movie:source` 无需改动，但**播放按钮传的 `sid` 取自影视 `id`（两者都是豆瓣 id）
这一条要核对一次**。

### 5.1 Windows（WebView2，M1/M2/M3 的验收机）

- 仓颉 SDK：`D:\Program Files (x86)\Cangjie`；`CANGJIE_HOME` 用 Windows 形式，
  `PATH` 里要加 SDK 的 `bin` / `tools/bin` / `runtime/lib/windows_x86_64_cjnative` / `tools/lib`
  以及 `native/`（`libcjtbridge.dll` 所在）。
- 跑 CLI / 测试一律带 SDK `PATH`，否则表现为**退出码 127 且无输出**（动态链接找不到运行时 DLL）。
  Git Bash 里 PATH 要用 POSIX 形式（`/d/...`），不能用 `D:/...`。
- **npm 冷启动极慢**：`npm run dev` 把 Vite 拉起来最慢约 85–150 秒（Vite 自身只要 0.3 秒）。
  想快可直接 `node ui/node_modules/vite/bin/vite.js`。
- **bash 工具单次调用结束时，这次调用里起的后台进程会一起被收掉** —— 不要指望「上一步起 Vite、下一步改文件」，
  一次调用里把「起服务 → 等就绪 → 改文件 → 取证 → 收尾」做完整。
  `cmd //c start …` 与 PowerShell 的 `Start-Process` **都躲不过**这次回收（实测「+6s 还在、调用一结束就没了」）；
  要让探针 / 窗口**活过本次调用**（例如留给人手测菜单），得让**服务侧**创建进程：
  `MSYS_NO_PATHCONV=1 powershell -NoProfile -Command "Invoke-CimMethod -ClassName Win32_Process -MethodName Create -Arguments @{CommandLine='cmd.exe /c run-manual.bat'; CurrentDirectory='<工程根>'}"`
  ——实测进程落在 **Console 会话 1**（窗口可见、跨调用存活）；cwd 必须给工程根（`capabilities/` 按相对路径读）。
- MSYS：`pgrep` 看不到 Windows 原生进程（判残留要用 `tasklist`）；`hdc file recv` 的远端绝对路径要加
  `MSYS_NO_PATHCONV=1`；`start` 的内联引号会被吃掉。
- 真机（3QC0124B20000048）用 `aa start` 要求屏幕已解锁，开发者模式下无法自动解锁，需人工解锁后再测。

  用更精确的模式（如 `pkill -f "tmp_dev_vue/ui/node_modules"`）或把清理脚本放到 `/tmp` 再执行。
- 想模拟「终端 Ctrl-C」不能用后台 `&` 起 CLI：bash 会把 SIGINT 设成 SIG_IGN 并被子进程继承，
  现象是「怎么打都不死」，会把有问题的实现误判成没问题；用
  `timeout -s INT <秒> bash cli/cj-tauri.sh dev` 更接近真实前台语义。
