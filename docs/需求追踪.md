# 需求追踪矩阵

按**能力**组织的需求盘点（采用「ID / Owner / 验收场景 / 状态 / 证据」的矩阵形态，
与按时间线组织的 `进度记录.md`、按分期的 `RFC-插件路线图.md` 互补。Owner 指**代码所有权
边界**（精确到文件），不是个人承诺；状态依据当前源码、门禁与实机证据判断。

## 状态定义（五级）

- `planned`：需求已定义，当前没有足够的源码和测试证据。
- `validation-only`：有源码与单测/桩自测，但缺少目标平台实机验证。
- `experimental`：仅覆盖实验平台或不稳定路径。
- `implemented`：源码、平台接入、测试与文档基本齐全，但仍未满足发布矩阵。
- `supported`：实机验证通过且证据可复核（桥 stderr / 截图 / 系统行为取证）。

> 证据锚点：`docs/进度记录.md` 各节记录取证方法；实机截图与日志在 `/tmp/cj-tauri-shots/`
> （`INDEX.md` 注明每张图证明哪条结论；该目录是会话产物，入库的持久证据以 git 提交里的
> 进度记录/CHANGELOG 描述为准）。**桩自检 / 单测全绿不等价于实机通过**——这是本矩阵与
> `scripts/test.sh` 的分工。

## 维护规则

- 行为变更落地时，**同轮**更新本矩阵对应行的状态与证据（与 CHANGELOG 同级纪律）；
- 状态只许沿 `planned → validation-only → experimental → implemented → supported` 单向推进，
  回退必须写明回归原因（在进度记录中留节）；
- `supported` 必须给得出**可复核证据**（桥 stderr 行 / 截图 / 外部系统行为），
  「单测全绿」不是 supported 的充分条件；
- 新平台接入（如 HarmonyOS）先落契约行（planned），实现后再逐项推进。
