# 鸿蒙 PC 上的窗口尺寸，我把合适的默认值改坏了两次

> 上一篇写的是「应用能不能起来」。这篇写它起来之后的第一件小事：窗口该多大。
> 结论先说：**在鸿蒙 PC 上，别自己定尺寸**，系统给的那扇桌面窗就是合适的。但我是绕着圈才认下这句的，
> 中间两版自定尺寸都算得上「主动把好东西改坏」。

![三栏布局铺开的 ohos-music，窗口是系统给的那一扇](images/example-ohos-music.jpg)

## 第一件：它不是窗口小，它是被当成手机应用了

第一次装上去，页面渲染完全正常——但窗口是**竖屏兼容窗**，实测约 600 宽，歌单和播放器挤成一列，
桌面上一眼就是个手机应用。同一套页面在 Windows / Linux 上一直是三栏。

这里有个很容易带偏的想法：以为是页面响应式没写对。其实窗口形状由**声明**决定，页面的响应式只能在
给定的视口里自适应。`module.json5` 的 `deviceTypes` 只写了 `phone` / `tablet`，鸿蒙 PC 就按「手机应用兼容窗」
处理；写 `2in1` 才是桌面形态。

但把 `2in1` 塞进去，立刻被构建链拦住：

```
> hvigor ERROR: Failed :entry:default@GeneratePkgModuleJson
Configuration Error 01103012
> Only phone and tablet devices are supported for Cangjie applications,
deviceTypes configuration is invalid: 2in1
```

这句「Only phone and tablet devices are supported」看着像「仓颉应用不支持鸿蒙 PC」，我差点就信了。
真因是插件里有一条**可关的校验**——去翻 `cangjie-build-support` 的源码，答案就一行：

```js
this.supportDevices = ["default", "phone", "tablet"];
checkCangjieDeviceTypes(e){
  const n = e?.cangjieOptions?.checkDeviceTypes;
  if (void 0 === n || !0 === n) { /* …校验… */ }
}
```

开关就在工程里改（`entry/build-profile.json5`）：

```json5
"cangjieOptions": { "path": "./cjpm.toml", "checkDeviceTypes": false }
```

`module.json5` 写 `["2in1", "tablet", "phone"]` 之后，`assembleHap` 过、安装过，窗口变成桌面形态。
**教训一条**：插件报「某平台不支持」时，先读源码看它是不是留了口子，别急着改架构。

## 第二件：我开始了「自定尺寸」的两次作死

窗口终于是桌面窗了，但我当时觉得「默认给的不一定好看」，于是开始改。三版，一路是往下走：

| 版本 | 写法 | 屏上实际尺寸 | 观感 |
|---|---|---|---|
| 第一版 | `resize(1440, 900)` | 1440×900 px，占 3120 屏宽的 **46%** | 太小 |
| 第二版 | 屏幕 86%×84% | `2683×1747` | **一开窗就最大化**，太满 |
| 第三版 | 逻辑 1000×700 vp × 密度 | `1900×1330` | 还是「弹出来就变」 |
| 收口 | 不干预，只打日志 | `2090×1394`（系统默认） | 就这样挺好 |

### 第一版：把 px 当 vp 了

```cangjie
windowStage.getMainWindow().resize(1440, 900)   // 日志照打「resized」，也不抛异常
```

我以为单位是 vp，想要一个 1440 宽的逻辑窗口。实际读出来是 1440 **px**——在 3120×2080 的屏上只占 46% 宽。
判据不靠眼睛：`hidumper -s WindowManagerService -a '-a'` 读窗口矩形，得到 `[515 281 1440 900]`，
**数字和传进去的一模一样**，这才定死单位是 px。

### 第二版：按屏幕比例算，一不小心就最大化

改成读屏幕尺寸按比例算：`86% × 84%`，屏上 `2683×1747`——用户的原话是「一开窗就最大化了」。

### 第三版：逻辑 vp × 密度，仍然在跳

那就按逻辑尺寸来：目标 1000×700 vp，乘 `densityPixels` 换算，再按屏幕 82% 封顶。屏上 `1900×1330`。
数字看着挺规矩，问题出在用户下一句话：

> 「刚启动时弹出来的窗口大小合适，为何后来又变了？」

## 转折：原来系统给的默认值一直是对的

这句话把方向掰过来了。我一直在调「改成多大」，从没问过「不改是多大」。于是补了一行日志——
**在 resize 之前**，先把系统刚建好的窗口矩形打出来：

```cangjie
let mainWin = windowStage.getMainWindow()
let r = mainWin.getWindowProperties().windowRect
Hilog.info(1, "CjTauri", "system initial rect=[${r.left} ${r.top} ${r.width} ${r.height}]")
```

读到的是 `[515 281 2090 1394]`：**2090×1394 px ≈ 1100×734 vp**，正好约屏宽 2/3，居中、留白合理。
也就是说：系统按桌面形态先给了一扇挺合适的窗，而我的 `resize()` 在 `onWindowStageCreate` 里紧接着把它改掉，
用户看到的就是「先弹一个尺寸、随即跳成另一个」。前两版我把这个跳变误当成「默认太小」。

改成不干预之后，三处代码（脚手架模板、`ohos-music`、`ohos-movie`）的 `main_ability.cj` 收口到同一段，
只剩一行日志当凭证：

```cangjie
// 不 resize、不 moveWindowTo：系统给的这扇桌面窗就是默认大小。
let screen = getDefaultDisplaySync()              // ohos.display，宽高单位是 px
let screenW = Int64(screen.width)
let screenH = Int64(screen.height)
// densityPixels 是 Float32：直接跟 Float64 相乘会报 invalid binary operator，
// 先化成整数百分比（本机 190%）再参与运算
let densityPct = Int64(screen.densityPixels * 100.0)
let mainWin = windowStage.getMainWindow()         // 变量别叫 main：main 是关键字
let r = mainWin.getWindowProperties().windowRect
Hilog.info(1, "CjTauri", "main window keeps system default ${r.width}x${r.height} px at density ${densityPct}% on screen ${screenW}x${screenH}, rect=[${r.left} ${r.top} ${r.width} ${r.height}]")
```

真机 hilog 只剩这一行、没有第二个尺寸：

```
main window keeps system default 2090x1394 px at density 190% on screen 3120x2080, rect=[515 281 2090 1394]
```

顺带两个数字上的坑：**密度是 190%，不是 200%**，别按「2 倍屏」想当然（3120/1.9 ≈ 1642 vp 逻辑宽）；
`densityPixels` 在 `.cj.d` 里看着像 `Float64`，实际是 `Float32`，跟 `Float64` 直接相乘编译不过——
报错还只是 `invalid binary operator`，有时候会连带把同一段的 `Hilog.info` 报成参数列表不匹配。

## 取证手法：这次真正值钱的东西

尺寸这类问题有个共同点：**你要证明「窗口有没有被人改过」，就必须在改之前也留一条读数**。
只打最终值，用户说「我看到的不是这个大小」时，你手上一条凭证都没有。

还有一条：`resize()` 之后立刻读 `getWindowProperties().windowRect`，读到的是**过渡值**
（本轮读到过既不是旧尺寸也不是新尺寸的 `[515 281 2090 1394]`）。要判「到底生效没有」得等系统应用完再读——
30 次 × 10ms 有界轮询到与请求一致，行尾标 `after N polls`。

这两条是通用的，不止用于窗口：凡是「调用返回成功但现象不符」的宿主 API，都该按「调用前读数 + 调用后复核」
这一对来收口，并且把 API 的返回值一起打进同一行日志。

## 现在的口径

- **默认不动窗口。** 想固定尺寸再自己 `resize(w, h)`，两个坑记着：收 px 不收 vp；`densityPixels` 是 Float32。
- 前提是 `deviceTypes` 为 `2in1` 且 `checkDeviceTypes=false`。写成 phone / tablet 时系统按手机应用塞进
  竖屏兼容窗（约 600 宽），那时候**才**需要自己定尺寸。
- 应用侧要做等比缩放是另一回事：整页 `zoom` 会撞视口单位不跟着缩的坑，那是应用自己的选择，框架不插手。
