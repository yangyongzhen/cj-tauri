# cj-tauri

A scaffold CLI for building desktop apps in the [Cangjie language](https://cangjie-lang.cn) — it brings
Tauri's trio to Cangjie: a Cangjie backend (statically compiled) plus a system WebView frontend
(HTML/CSS/JS), with the same three pieces Tauri has — a WebView host, a bidirectional IPC bridge
(`invoke` / `resolve` / `event`), and a capability-based security model (capability allowlists).

- Repository and full documentation: <https://github.com/yangyongzhen/cj-tauri>
- Current version: **2.1.1** (fixed in this release: sync now keeps the launcher on the framework path
  the business package declares (no more cjpm module conflicts after editing the path), the desktop
  launcher locates assets/ two levels up so it runs straight from targets/, and new **serial command
  groups** — `TauriApp.registerSerial` — execute same-group commands strictly in arrival order, which
  ai-chat's web-tab commands now use; plus the hello-world example and starter guide)
- Current status: **Windows (WebView2), Linux (WebKitGTK) and HarmonyOS PC (ArkWeb) all run on real
  hardware**; on the HarmonyOS side the menu capability bit and `fs` / `mqtt` / `redis` / `sqlite` /
  `store` / `http` have been verified on a device

## Prerequisite: the Cangjie SDK

**This package does not replace the Cangjie SDK.** Your app backend is Cangjie code, and
`cj-tauri dev` / `build` invoke the SDK's `cjc` / `cjpm` to compile it. So install the SDK first
(verified with version **1.2.0**, including **stdx**) and make it discoverable:

```bash
# Linux
export CANGJIE_HOME=/opt/cangjie/cangjie

# Windows cmd
set CANGJIE_HOME=D:\Program Files (x86)\Cangjie
```

When `CANGJIE_HOME` is unset, the package probes the usual install locations (Windows
`D:\Program Files (x86)\Cangjie`, Linux `/opt/cangjie/cangjie`). Three more variables are needed
in some situations:

| Variable | When you need it |
|---|---|
| `CJ_TAURI_ROOT` | Running outside the cj-tauri repo when the framework root can't be located (`create` writes the framework path into your project) |
| `CANGJIE_STDX` | Your app's `cjpm.toml` expands the stdx path via `${CANGJIE_STDX}`; the package probes the framework/project toml for it and falls back to this variable |
| `CANGJIE_STDX_OHOS` | Only when building a HarmonyOS project (the HarmonyOS build of stdx; `build-hap.sh` locates its dynamic libraries through it) |

Self-check once it's installed:

```bash
npx cj-tauri info        # prints the resolved framework / project / stdx / SDK / cjpm / C bridge
```

Without the SDK the package prints a clear hint and install instructions instead of throwing
`cjpm: command not found`. Note that `npx cj-tauri --version` works without the SDK.

## Usage

```bash
npx cj-tauri create myapp --template app     # inline HTML, zero Node (the default template)
cd myapp
npx cj-tauri sync                            # derive the targets/ skeletons from the manifest (first run; idempotent)
npx cj-tauri dev                             # build the C bridge + cjpm build + open the window

npx cj-tauri create myapp-vue --template vue      # Vue 3 + Vite (frontend project under assets/ui/)
npx cj-tauri create myapp-react --template react  # React 18 + Vite

npx cj-tauri create myohos --template ohos        # HarmonyOS PC: same business code + targets/ohos
npx cj-tauri create myohos --template ohos --bundle com.example.myapp --label "My App"

npm i -g cj-tauri                  # or install globally and call cj-tauri <subcommand> directly
```

**One body of business code, skeletons derived per target** — `create` only generates the manifest and
the business side; the platform skeletons are what `sync` produces:

```
myapp/
├── cj-tauri.toml           # app manifest — the single source of truth (id/version/window/assets/capability dir)
├── cjpm.toml               # business package (a static library; skeletons reference it by path)
├── src/main.cj             # business assembly point build(): AppSpec (zero platform knowledge)
├── assets/
│   ├── ui/index.html       # frontend page (any web stack)
│   └── capabilities/default.json   # capability allowlist (commands / events / permission sets)
└── targets/                # generated by cj-tauri sync (don't hand-edit; check reports drift)
    ├── desktop/            #   desktop executable (the launcher calls build())
    └── ohos/               #   HarmonyOS hap project (DevEco + build-hap.sh)
```

| Subcommand | What it does |
|---|---|
| `create <name> [--template app\|vue\|react\|ohos]` | Generate the unified project (manifest + `src/` + `assets/`); `--bundle` / `--label` only matter for the `ohos` template, otherwise they're derived from the project name |
| `sync [desktop\|ohos]` | Derive the `targets/` skeletons from the manifest (both ends by default; idempotent) |
| `dev` | Build the C bridge + `cjpm build` + launch the app; Vite templates take over their dev server (HMR) |
| `build` | Build the C bridge + `cjpm build`; on HarmonyOS run `bash build-hap.sh` inside `targets/ohos` |
| `run` | Run the built artifact; on HarmonyOS `bash build-hap.sh --install` (build + install + launch) |
| `check` | Validate `cj-tauri.toml` (id / window / assets present) + `targets/` skeleton drift + three-way plugin comparison |
| `info [--json]` | Environment self-check (run this first when troubleshooting); `--json` prints only the plugin manifest, machine-readable |
| `doctor` | Environment self-check with a verdict per line (each line says what to do if it's missing) |
| `help` | Help |

## HarmonyOS PC (`--template ohos`)

The same framework with a different host: desktop uses WebView2 / WebKitGTK, HarmonyOS PC uses **ArkWeb**,
while the page layer, the command layer and capability validation stay untouched. `--template ohos` still
generates that **unified project** (`cj-tauri.toml` + `src/` + `assets/`), only the manifest carries the
HarmonyOS side (`[app] id` is the `bundleName`); the DevEco project is a product of `sync`, landing in
`targets/ohos/`:

```bash
npx cj-tauri create myohos --template ohos --bundle com.example.myapp --label "My App"
cd myohos
npx cj-tauri sync ohos             # derive targets/ohos (DevEco skeleton + the page and capability manifest in rawfile)
cd targets/ohos
bash build-hap.sh --install        # build the hap + install via hdc + aa start
```

`targets/ohos/` is a standard DevEco project (`entry/` + `AppScope/` + `build-profile.json5` +
`hvigorfile.ts`), and the HarmonyOS-specific layer is thin:

| Path | Purpose |
|---|---|
| `entry/src/main/cangjie/main_ability.cj` | UIAbility: `ArkWebRuntime.configure(filesDir)` → `spawn { run() }` off the UI thread → wait for the host to register, then `loadContent` |
| `entry/src/main/cangjie/app_host.cj` | the `@Component` ArkWeb host + bidirectional bridge (**must live in the app module**; a framework package referencing ArkUI crashes at startup); calls the business `build()` in your `assets/` |
| `entry/src/main/resources/rawfile/` | `index.html` and the capability manifest (real files copied in from `assets/`) |
| `build-hap.sh` | the single build entry: probes DevEco / stdx, runs hvigor with `--no-daemon`, optional `--install` |

Two prerequisites:

- **DevEco Studio 6.1** (with the Cangjie plugin) and signing already configured. `build-hap.sh` finds the
  install root via `DEVECO_WIN` (default `D:\oh\DevEcoStudio`) and the HarmonyOS build of stdx's dynamic
  libraries via `CANGJIE_STDX_OHOS`; when either is missing the script says exactly which one.
- A device with **developer mode + USB debugging** on, so `hdc` lists it; `aa start` needs the **screen unlocked**.

The project defaults to desktop form factor: `deviceTypes` in `module.json5` is `2in1`, and
`cangjieOptions.checkDeviceTypes = false` in `entry/build-profile.json5` (the plugin only allows
`phone` / `tablet` by default, and writing `2in1` fails with `01103012`). The window **does not touch the
size** and keeps the system default rectangle (measured at `2090×1394`, about two thirds of the screen
width and centered).

Known limitations: signing is configured in DevEco (the command line does not auto-sign, and changing the
`bundleName` requires re-signing); two projects under the same debug signature evict each other's install;
single window with no native dialogs yet (those two capability bits honestly return 0); there is no usable
C bridge, so host capabilities like `launchHidden` / serial / tray are not available on HarmonyOS. After
editing pages or the capability manifest under `assets/`, re-run `cj-tauri sync ohos` (`targets/` is
generated, and `check` reports it as drift).

How to prove it works on a device (hilog, `CjTauri` tag):

```
host registered after N polls label=main
host pageUrl label=main url="file:///.../files/cj-tauri-main.html"
page begin label=main
main window keeps system default 2090x1394 px at density 190% on screen 3120x2080
```

## What this wrapper layer does

- **One cross-platform entry point**: Windows / Linux / Git Bash all use the same `cj-tauri` command, with
  no more separate `.bat` and `.sh`;
- **Environment self-check**: locating `cjpm` and the SDK runtime libraries, and assembling `PATH` /
  `LD_LIBRARY_PATH`, all happen here;
- **Obtaining the CLI itself**: the packaged prebuilt binary is preferred (`prebuilt/<platform-arch>/`);
  otherwise the CLI sources are copied to `~/.cache/cj-tauri/<version>/`, built once with the local
  `cjpm build` and cached — nothing is written into the install directory, so a global install can stay
  read-only;
- **Data directories**: `$XDG_CACHE_HOME/cj-tauri` on Linux (default `~/.cache/cj-tauri`),
  `%LOCALAPPDATA%\cj-tauri` on Windows.

Known limitation: the first `dev` / `build` builds the C bridge into the **framework directory's `native/`**
(that's where the app's `cjpm.toml` link options point), so the package install directory must be writable;
if you installed under a read-only path, run from inside the repository instead.

## Changes in 2.1.1

- **Serial command groups** (issue #6-4): `IpcHub.registerSerial(cmd, handler, group)` /
  `TauriApp.registerSerial` — commands in the same group execute strictly in **arrival order**,
  while other groups and plain commands keep the concurrent semantics. Guaranteed by structure:
  dispatch happens on the bridge's message-callback thread, so enqueue order is arrival order,
  and each group has a single worker draining the queue under one lock. ai-chat's five web-tab
  commands are enrolled in the `webtab` group (the front-end queue stays — page emission order
  and host execution order are two halves of the same guarantee).
- **sync keeps the launcher on the business package's framework path** (issue #6-1): the launcher's
  `cjTauri` dependency now reads the path the business package declares in its own `cjpm.toml`
  (relative paths absolutized against the project root), so editing that path no longer causes
  a cjpm module conflict between two framework copies.
- **The desktop launcher locates its assets** (issue #6-2/3): `assets/` and `capabilities/` are
  found by walking up two levels, so running the binary straight from `targets/desktop/` no longer
  dies with "asset not found"; sync's next-steps output names the runtime library path
  (`<framework>/native` for `libcjtbridge.so`).
- New `examples/hello-world` (smallest runnable app, generated by this CLI) and
  `docs/hello-world-入门教程.md` — a starter guide written from an actual npx-create-to-window run.

For the full list see `[2.1.1] - 2026-10-26` in the repository's `CHANGELOG.md`.

## Changes in 2.1.0

- **New**: in-window multi-WebView views (`webview:*` — several page views inside one window with an LRU
  cap of 4, which is what drives ai-chat's nine web-version tabs); the four commands `fs:mkdir` /
  `fs:rename` / `fs:copy` / `fs:stat` (with overwrite and two-path scope validation); the `http` plugin's
  HarmonyOS transport layer (over the `ohos.net.http` system stack, which brings https back); `sqlite` /
  `serial` landing on HarmonyOS; a `notification` capability bit in `system:host`; a pointer to the SDK
  download in the CLI's `doctor`.
- **Fixed**: the Linux C bridge `duplicate member 'h'` compile error (the embedded view's geometry field
  collided with the host pointer), ai-chat's embedded view not following the widening after the sidebar
  collapses, and the documented state of the HarmonyOS host capability bits (the menu bit is verified on a
  device, so it's no longer all zeros).
- Verified on a HarmonyOS device: `fs` / `mqtt` / `redis` / `sqlite` / `store` / `http` and the menu
  capability bit.

For the full list see `[2.1.0] - 2026-10-25` in the repository's `CHANGELOG.md`.

## Changes in 2.0.0

- **Breaking**: removed the dead public APIs `setHostFactory` / `requireInjectedHost` (the framework's
  single-slot host injection). Apps still calling them will fail to compile — and those calls never took
  effect anyway (`requireInjectedHost` had no callers at all). Multi-host injection goes through
  `registerHost(HostProvider)` (with priorities); the HarmonyOS host is built in.
- **Fixed**: projects generated by `sync` wouldn't compile on Windows (TOML paths keeping backslashes
  triggered `errLexEscape`, the HarmonyOS entry's `compile-option` had unescaped inner quotes, and
  `url=\"…\"` in the generated sources was one escape level short); `cj-tauri check`'s three-way
  comparison was always skipped on Windows because of the `main.exe` artifact name; the `modbus-poll`
  example was missing the serial plugin import.
- **Gates**: version validation grew from five sites to six (adding the website's `website/index.html`),
  and the images / diagrams that share a source with `docs/` now get a byte-for-byte comparison — the
  website is an independent copy that previously sat outside the gate, which is exactly why it went stale.

For the full list see `[2.0.0] - 2026-10-23` in the repository's `CHANGELOG.md`.
