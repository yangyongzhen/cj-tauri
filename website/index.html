用仓颉写桌面应用， 前端还是 HTML/CSS/JS

cj-tauri 就是仓颉语言里的 Tauri：后端静态编译成原生可执行文件，前端跑在系统 WebView里 （Windows 走 WebView2、Linux 走 WebKitGTK），中间是一条 IPC 双向桥加一套能力白名单。 不捆绑 Chromium，产物 5.5–9.5 MB，双击即用。

三件套

WebView 宿主 + IPC 双向桥 + 能力安全模型

与 Tauri 对应的三件套：宿主负责开窗与注入，桥负责一问一答与事件回投，能力模型负责「谁能调什么」。 平台差异被压到两处——仓颉侧 @When 条件编译与 C 桥的 native/bridge_*.c， 其余全部跨平台共用。

WebView 宿主

开原生窗口、在 document-start 注入桥接脚本，不捆绑 Chromium。Linux 走 WebKitGTK 4.1、 Windows 走 WebView2、鸿蒙 ArkWeb 预留架构位；菜单、文件拖入、原生对话框、托盘、 全局快捷键这类宿主能力一律赶在页面加载前定稿。

host.cj · host_webkit.cj · host_webview2.cj

IPC 双向桥

前端只经 window.__CJ_TAURI__ 的 invoke / listen / emit 与后端对话（形状对齐 @tauri-apps/api）。命令在调用线程只做校验，通过后派到 worker 线程执行， 结果按 promise id 回投——慢命令不会把宿主 UI 钉住。

src/ipc_hub.cj · json over postMessage

能力安全模型

命令与事件必须写进 capabilities/*.json 才放行：默认最小权限，插件只声明「我提供什么」、 不自动放行自己。之上还有命名权限集与路径 scope（先 deny 后 allow，匹配前先规范化路径， 越界被拒会在桥 stderr 留证据）。

src/capability.cj · src/scope.cj

为什么是 cj-tauri

六件能拿证据说话的事

下面没有「计划支持」：体积是对着随仓库分发的产物量的，依赖是从 PE 导入表读出来的， 示例跑完会自己给自己下结论。

静态编译的后端

仓颉无虚拟机，运行时就静态链在产物里——从没装过 SDK 的机器也能直接跑。协议层两百行左右，可审计。

零 Chromium 捆绑

八份产物实测 4.69 – 9.79 MB，PE 导入表里全是 Windows 系统 DLL—— 第三方运行时（msvcp* / vcruntime* / libgcc* / libwinpthread*）一个都没有。

默认最小权限

清单里没声明的命令一律拒绝，而且拒绝会留日志、不静默。页面可控的路径参数可以钉在工作区内 （allow / deny 通配 + 变量），先判 deny 再判 allow。

插件体系

十四个官方插件：文件、原生对话框、子进程、串口、键值存储、剪贴板、通知、原生菜单、MQTT、Redis、 HTTP、WebSocket、日志落盘、SQLite。 插件声明命令、事件与前端 shim，真正放不放行仍由清单说了算。

全链路可验证

桥逐行写 stderr，页面把自检断言回投，每个示例都带一条无人值守 E2E 入口并把证据 JSON 落进 dist/e2e-evidence/。「日志里没有错误行」从不当作成功。

配套脚手架

一条 CLI：create / dev / build / run / info / doctor，npx cj-tauri 即可用。 模板覆盖零 Node 的 HTML、Vue 3、React 18；dev 接管 Vite dev server， HMR 在原生窗口里生效；doctor 逐行说明缺什么、怎么补。

架构

一条 JSON 从页面走到原生

页面看不到任何平台代码：它只 postMessage 一份 JSON，桥负责校验，worker 执行 handler， 结果按 promise id 回投。平台相关的代码只可能在两处出现，下面这张图随仓库版本化，不会和实现对不上。

01前端

普通 HTML/CSS/JS（用模板时就是 Vue / React）。注入的 window.__CJ_TAURI__ 上挂 invoke / listen / emit，形状对齐 @tauri-apps/api。

02IPC 消息桥

src/ipc_hub.cj 同步做「注册 / 授权」两项校验，通过后把 handler 派到 worker 线程。 未注册或未授权当场拒绝，并在 stderr 留下可 grep 的一行。

03能力模型

src/capability.cj 启动时扫 capabilities/ 下的所有 json：命令、 事件、命名权限集、路径 scope 全在共享层解析，两个平台不各判一份。

04宿主 + C 桥

Linux 的每个 GTK/WebKit 调用都在 C 桥创建的原生 pthread 里执行（仓颉轻量线程的堆上协程栈会被 JSC 的栈边界校验 abort）；Windows 在宿主线程跑 WebView2 消息循环。两平台导出同一套 cj_bridge_* 名字，上层没有平台分叉的调用点。

代码

三个文件，一个桌面应用

仓颉侧写一个命令、清单里放行一行、页面上 invoke 一次——没有别的仪式，也不用改构建脚本。

src/main.cjCangjie
// 1) 实现命令：handle 在 worker 线程上执行，返回的 JsonValue 回投给页面
public class GreetCommand <: CommandHandler {
    public func handle(cmd: String, args: JsonObject, ipc: IpcContext): JsonValue {
        return JsonString("Hello, ${argString(args, "name", "world")}!")
    }
}

main(): Int64 {
    // 2) 装配：建窗口 + 注册命令；capabilities/ 由 run() 自动扫描
    let app = TauriApp()
        .window(WindowConfig("hello", 1000, 700))
        .register("greet", GreetCommand())
    // 3) 启动：run() 自己不返回，窗口关闭后收尾
    app.run(HTML)
    return 0
}
capabilities/default.jsonJSON
{
  "identifier": "default",
  "windows": ["main"],

  // 命令级白名单：没写在这里的命令一律 command not allowed
  "commands": ["report", "notes:env", "system:version"],
  "events": [],

  // 命名权限集：一次放行一组，与明文写法同权（集声明 ≠ 放行）
  "permissions": ["fs:default", "store:default"],

  // 路径 scope：命令放行 ≠ 参数放行；先判 deny，再判 allow
  "scopes": {
    "fs": {
      "allow": ["$CWD/notes", "$CWD/notes/**"],
      "deny":  ["**/*.secret.md"]
    }
  }
}

// 调后端命令：与 @tauri-apps/api 同形，返回 Promise

插件

十四个官方插件，全都要显式放行

插件只声明「我提供什么」（命令、事件、前端命名空间），放不放行仍由能力清单说了算。 其中 MQTT 与 Redis 的协议是纯仓颉实现，想评估这个框架的工程底子可以直接读它们。

fs

读 / 写 / 列目录 / 删除，受路径 scope 约束

dialog

原生打开、保存、消息框

shell

打开链接、子进程（argv 直传，不过 shell）

serial

串口收发，带探针自检闭环

store

键值存储，写盘走 tmp + rename

clipboard

系统剪贴板读写

notification

系统通知（Linux 实机取证，Windows 桩如实报）

menu

原生菜单栏，点选事件回投前端

mqtt

MQTT 3.1.1，协议纯仓颉实现

redis

RESP2 客户端，纯仓颉实现

http

页面可控的出网口，主机白名单（没写 = 全拒）

ws

WebSocket 长连接，白名单口径与 http 同构

log

仓颉与桥的诊断落进同一份文件，按预算轮转

sqlite

FFI 直连系统 libsqlite3，不经 C 桥

三层控制：命令 / 事件白名单、命名权限集（fs:readonly、sqlite:default …）、 以及按插件的路径 scope（allow / deny 通配）。少一层调用就不发生——而且拒绝会打上可 grep 的前缀， 不静默失败。

实测数据

这些数字都有脚本能现场复核

仓颉是提前编译的，没有虚拟机要预热、产物里也没有解释器。下面这些数字来自随仓库分发的产物与桥自己的 stderr 日志，口径写在文档里，连还没量到的那一格也照实标出来。

5.50–9.50 MB

四份随仓库分发的单文件 exe（typing-poem / modbus-poll / movie / music）

0 个第三方 DLL

从 PE 导入表读出来的——只有 Windows 系统 DLL，没有 msvcp*/vcruntime*/libgcc*

54ms 中位数

Linux 冷启动（进程启动 → 桥打出窗口标题行），3 次取样 48/54/57 ms

261 单测 / 8 E2E

仓颉侧单元测试 + 共享 C 核心的桩平台自检，另有 8 条无人值守 E2E 入口

还没量到的：Windows 侧冷启动（本机是 Linux，这一格就空着，不拿 Linux 的数字替它说话）， 以及 Windows 侧的剪贴板 / 通知 / 串口能力位。方法已经写进脚本，缺的是机器。

系统托盘与全局快捷键

两平台都跑通：Linux 走可选编译的 libayatana-appindicator3（没装依赖照样构建、能力位如实报 0）+ X11 XGrabKey；Windows 走 Shell_NotifyIconW 与 RegisterHotKey，不引入新依赖。两侧都经同一条 shell 通道回投，「最小化到托盘」是宿主基元而不是页面逻辑。
